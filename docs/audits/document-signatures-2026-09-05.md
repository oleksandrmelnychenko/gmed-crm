# Повторний аудит Skribble — 05.09.2026

## Результат

Перевірено підключення інтерфейсу до API, серверного фонового процесу та
збереження результатів. Виправлено втрату незбережених даних у вікнах,
повторну доступність відправлення під час невдалої синхронізації та
оновлення токена після HTTP 403. Локальні перевірки нижче пройшли.

Це перевірка коду та тестів із підставним HTTP-провайдером. Підключення
реального облікового запису й повний цикл DEMO/QES у Skribble не виконувалися.
Розгортання та застосування міграцій у робочому середовищі не виконувалися.

## Перевірені шляхи

| Функція | Реалізація та перевірка |
| --- | --- |
| Налаштування | Окрема сторінка й вкладене вікно, ролі CEO/IT Admin, GET/POST/check/disconnect. Початкове невдале читання не показує помилку; помилки явних дій відображаються. |
| API-ключ | Сервер перевіряє вхід перед збереженням, шифрує ключ, не повертає його клієнту. Після збереження поле очищується; браузерний тест перевіряє відсутність ключа в localStorage. |
| Незбережені зміни | Підтвердження закриття лише для змінених облікових даних/підписантів. Скасування зберігає форму, повернення початкових значень прибирає підтвердження. Заміна PDF теж захищена від втрати введених підписантів. |
| Відправлення | Перевірка PDF, актуальної версії та прав View/Download/Edit; максимум шість різних адрес. Для шаблонів договору/замовлення потрібні обидві сторони. Outbox зберігається до HTTP 202; серверний POST не повторюється автоматично. |
| Невизначений результат | Після таймауту або POST кнопка заблокована до успішного отримання поточного стану. Помилка GET не дозволяє повторне відправлення. Сервер шукає створений запит за UUID та перевіряє його ідентичність. |
| Статуси та відкликання | Фоновий worker зареєстрований при старті сервера, перевіряє активні запити й повторює невдалу синхронізацію. Відкликання підтверджується наступним станом провайдера. Відключення/заміна акаунта блокуються за наявності активних запитів. |
| Результат | Сервер перевіряє всіх підписантів, QES/DEMO та EIDAS, завантажує PDF і PDF-протокол. Архівування й зміна стану транзакційні; для застарілого джерела та DEMO передбачені окремі результати. Кнопки скачування обох файлів перевірені в браузері. |
| Доступ | Маршрути й навігація зареєстровані; документні дії відкривають потрібний PDF. Браузерні сценарії перевіряють 403, недоступний PDF і перегляд без можливості відправляти/відкликати/налаштовувати. |

## Виправлення цього аудиту

- Прибрано примусове `dirty={false}` та безумовне закриття у вікнах
  підключення й підписання. Стан змін порівнюється з початковими/збереженими
  значеннями. Успішне збереження встановлює нову базу порівняння.
- Додано блокування повторних одночасних дій та очікування актуального
  стану після серверної операції. Скачування файлів не запускає зайве
  оновлення стану підпису.
- Валідація адрес і довжини імен у UTF-8 узгоджена з сервером.
- Кеш токена скидається після 401 і 403. Наступна синхронізація виконує
  повторну автентифікацію без автоматичного повторення POST створення.
  Коди помилок звірені з [офіційною схемою Skribble Sign API v2](https://api.docs.skribble.com/api/sign-v2/~schemas)
  та [документацією автентифікації](https://api.docs.skribble.com/authentication).

## Виконані перевірки

- Rust: **4 пройшли**, 1 PostgreSQL-сценарій **пропущений** (потрібен окремий
  `TEST_DATABASE_ADMIN_URL`, у цьому сеансі його немає).
- Vitest: **20 пройшли** у чотирьох файлах — API підписів/документів,
  табличні документні дії та доступ до маршрутів.
- Playwright: **12 пройшли**; усі HTTP-виклики перехоплені тестовими
  відповідями, запрошення реальним підписантам не надсилалися.
- TypeScript `tsc -b` та ESLint змінених файлів — без помилок.
- Перевірені ширини 390 та 1440 px; знімки у `artifacts/design-qa/signature-*.png`.

Команди з кореня репозиторію:

```powershell
cargo test -p gmed-server --lib document_signatures:: --offline
```

З `frontend/`:

```powershell
node node_modules/typescript/bin/tsc -b
node node_modules/vitest/vitest.mjs run src/pages/documents/data/document-signature-api.test.ts src/pages/documents/data/document-api.test.ts src/components/data-table/document-preview-column.test.ts src/lib/staff-route-access.test.ts
node node_modules/@playwright/test/cli.js test tests/e2e/document-signatures.spec.ts --project=chromium
```

Для цього аудиту Playwright запускався з тимчасовою конфігурацією на
локальному Vite `127.0.0.1:5187`, оскільки npm відсутній у PATH. Тимчасові
конфігурація та сервер прибрані після завершення.

## Що ще не підтверджено

1. Повний живий цикл: вхід до конкретного німецького акаунта, отримання
   запрошень, ідентифікація підписантів, завершення підпису та повернення
   справжніх PDF/протоколу. Першу таку перевірку слід виконати в DEMO.
2. Повторний прогін транзакційного тесту на ізольованому PostgreSQL;
   результати попереднього прогону описані в архітектурному документі,
   але не зараховані до перевірок цього аудиту.
3. Бізнес-статуси договору, замовлення та згод не змінюються автоматично
   від підписання PDF. Для цього потрібна однозначна прив'язка документа
   до відповідного об'єкта та окреме правило переходу стану.
4. Незалежна криптографічна перевірка підпису PDF не реалізована;
   поточна перевірка спирається на авторизований API й протокол Skribble.

Деталі архітектури: [document-signatures-germany_ua.md](../architecture/document-signatures-germany_ua.md).

## Жива перевірка через DEMO

Skribble надає безкоштовні Demo API keys для тестування; підписи через них
не мають юридичної сили та виконуються без 2FA.
[Офіційна інструкція зі створення ключа](https://docs.skribble.com/business-admin/api/apicreate.html).
Демо-ключі також доступні під час 14-денного пробного періоду, згідно з
[поясненням Skribble](https://www.skribble.com/en-eu/blog/sbb-api-integration/).

1. Увійти до власного німецького Skribble Business або
   [зареєструвати пробний акаунт](https://my.skribble.de/business/signup/?lang=de).
2. Відкрити **Admin area → API keys → Create API key → Demo**.
3. У GMED вибрати **Тестовый — DEMO**, ввести отримані API username
   (`api_demo…`) та ключ у форму підключення, натиснути перевірку/збереження.
4. Використати синтетичний PDF і погоджені адреси тестових підписантів.
   Перевірити отримання запрошень, підпис обома сторонами, автоматичну
   зміну стану та скачування PDF/протоколу. Звірити позначку TEST і те,
   що робочий документ не став юридично підписаним.
5. Окремим тестовим запитом перевірити відкликання та відмову, відновлення
   після тимчасового розриву зв'язку, відсутність дублікатів і збереження
   результату після повторного входу.

Такий прогін підтверджує живий технічний цикл DEMO. Реальна QES-ідентифікація,
2FA та робочі тарифи потребують окремої перевірки. Готові чужі/спільні
облікові дані в інтеграції не закладені.
