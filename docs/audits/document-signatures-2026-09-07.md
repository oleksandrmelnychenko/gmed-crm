# Перевірка електронного підпису — 07.09.2026

Перевірено поточну реалізацію Skribble: підключення, підписантів, відправлення,
синхронізацію, PDF/протокол, права доступу та показ результату. Знайдено дві
проблеми в обробці помилок і видалення файлів. На наступний запит користувача
внесено виправлення, описані наприкінці звіту. Нижче збережено первинні знахідки.

## Знайдені проблеми

### P2 — HTTP 429 залишає відхилене відправлення заблокованим

У `crates/server/src/document_signatures/provider.rs:212` перелік остаточних
відмов не містить HTTP 429. Відповідь про перевищення ліміту переходить через
`bounded()` у `provider_http_error`, а обробник створення
(`document_signatures/mod.rs:233`) записує `submission_unknown` без ID Skribble.
Пошук неіснуючого запиту повертає порожній список, і `sync_claim()` зберігає
невизначений стан без кінцевого переходу.

Наслідок: після відхиленого через ліміт запиту цей PDF не можна відправити
повторно. Відкликання теж недоступне без ID провайдера; відключення або зміна
акаунта блокуються наявністю активного запиту. Саме очікування зняття ліміту
не відновлює цей процес.

Рекомендація: розпізнавати підтверджену відмову через ліміт як невиконане
створення, зберігати відповідний код і дозволяти явну повторну спробу після
зняття ліміту. Автоматично повторювати POST після справжнього таймауту не слід.
Окремо перевірити задокументований HTTP 406, якого теж немає в цьому переліку.

HTTP 429 і код `error.rate_limit.exceeded` задокументовані в
[офіційній схемі Skribble](https://api.docs.skribble.com/api/sign-v2/~schemas);
429 також зазначений серед відповідей
[створення запиту](https://api.docs.skribble.com/api/sign-v2/signature).

Висновок підтверджений трасуванням коду. Додатковий локальний тест із HTTP
провайдером підготовлено в `.audit/signature-review/`, але його компіляцію
заблокувала Windows Application Control (os error 4551). Він не зарахований
до виконаних перевірок.

### P2 — після видалення підписаного PDF запит далі показує збережений результат

Звичайний `POST /documents/{id}/delete` перевіряє використання документа в
рахунках, але не його участь у `document_signature_requests`.
У `crates/server/src/routes/documents.rs:21979` починається видалення файлу;
після транзакції байти фізично видаляються, а `storage_key` обнуляється.
Ця дія доступна в інтерфейсі й для підписаної версії.

Водночас запит підпису залишається `completed` із заповненим
`result_document_id`. Вікно підписання продовжує показувати «PDF и отчёт
сохранены» та пропонує відкрити/скачати вже видалений PDF. Фоновий процес і
ручне оновлення не обробляють завершені запити (`document_signatures/mod.rs:369`).
Протокол може лишатися доступним, але локального підписаного PDF вже немає.

Рекомендація: узгодити видалення зі зберіганням доказів — захистити результат
від звичайного видалення або явно відображати видалений результат у стані
підпису й прибирати недоступні дії. Не відновлювати навмисно видалені файли
автоматично без визначеного правила.

Висновок підтверджений аналізом серверного маршруту й інтерфейсу; видалення
справжніх документів не виконувалося.

## Виконані перевірки

- Rust: 6 тестів пройшли; 1 інтеграційний тест PostgreSQL пропущено, бо немає
  окремого `TEST_DATABASE_ADMIN_URL`.
- Vitest: 20 тестів у 4 файлах пройшли — API підписів/документів, документні
  дії таблиці та доступ до маршрутів.
- Playwright: усі 26 сценаріїв пройшли; фінальний код завершення 0.
  Покрито RU/DE, мобільний/настільний інтерфейс, налаштування, вибір
  підписантів, PDF, помилки читання, невизначене відправлення, відкликання,
  права й показ результатів. HTTP-відповіді тестові.
- TypeScript `tsc -b` та ESLint файлів електронного підпису пройшли.
- Переглянуто знімки результату на настільному екрані та мобільної форми.
  Артефакти: `output/signature-audit-2026-09-07/`.

Playwright запускався з тимчасовою копією сценаріїв, у якій змінено лише
шляхи знімків, та конфігурацією для локального Vite на порту 5187.
Тимчасові файли конфігурації/сценаріїв і локальний сервер прибрано.

Реальний Skribble, надсилання запрошень і QES у цьому аудиті не запускалися.
Звіт про попередній успішний живий DEMO-цикл від 6 вересня перевірено як
контекст, але не зараховано до сьогоднішнього прогону.

## Виправлення за результатами аудиту

- HTTP 429 отримує окремий код `provider_rate_limited`. При створенні він
  завершує спробу зі станом `error`, дозволяючи явну повторну відправку.
  Інтерфейс RU/DE пояснює, що запрошення не відправлені й спробу слід
  повторити пізніше. HTTP 406 також класифікується як остаточна відмова.
  HTTP 408/5xx та невизначені транспортні помилки не дозволяють автоматичний
  повтор POST. Відповідь 429 під час синхронізації лишає запит активним.
- Видалення блокується HTTP 409 із кодом `document_signature_file_protected`
  для результатів підписання та джерел запитів у станах `submitting`,
  `submission_unknown`, `pending`, `completed`, `needs_review`. Це зберігає
  також DEMO та застарілі докази. Джерела відхилених/відкликаних запитів без
  результату можна видаляти за звичайними правилами.
- Перевірка зв'язків виконується в транзакції після блокування рядка
  документа й до переміщення файлу. Створення запиту й архівування
  використовують те саме блокування, що захищає від одночасного видалення.
  Відмову серверу пояснено в інтерфейсі російською та німецькою.
