# Створення та перегляд рахунків — 07.09.2026

## Причина суперечливого повідомлення

Модалка перевіряла лише `billing_release_status`, а сервер додатково
вимагав `approved` для вибраних послуг фінального/проміжного рахунку.
Дозвіл бухгалтерії тому не означав готовність до створення рахунку.

Форма тепер перевіряє обидві умови. Перед POST виконується свіжа перевірка
вибраних джерел послуг; відсутні дані не трактуються як дозвіл.
Передоплата зберігає серверне правило: затвердження послуг для неї
не обов'язкове, але дозвіл бухгалтерії потрібний.

## Інтерфейс і доступні пропозиції

- Заголовки з помаранчевими маркерами, компактні секції та грошові суми
  моноширинним шрифтом у формі й картці рахунку.
- У таблиці позицій приховано розгорнуті описи послуг; залишено назви,
  податкову інформацію і суми. Висоту рядків зменшено.
- API-помилка та причина блокування розміщені в закріпленому футері
  поряд зі створенням. Повторна перевірка очищає стару помилку.
- Для неузгоджених послуг є перехід у відповідний розділ замовлення;
  відкриття в іншій вкладці зберігає чернетку. Повернення оновлює дані.
- Комбобокс створення приховує повністю виставлені, відхилені,
  прострочені й пропозиції лідів без пацієнта. Історичні фільтри рахунків
  зберігають ці записи.
- Активний фінальний рахунок виключає повторне виставлення за цією
  пропозицією. Активний авансовий виключає другий аванс, але пропозиція
  лишається доступною для розрахункового рахунку. Скасовані рахунки
  не блокують повторне виставлення.
- Наявні API-поля залишку кількості визначають доступний обсяг. Сам факт
  оплаченої передоплати не означає, що весь обсяг уже виставлено.
- При оновленні фінальна форма перераховує весь доступний залишок;
  примітка й дата зберігаються. Вичерпана пропозиція знімається з вибору.

## PDF

У таблиці лишаються назва позиції, кількість, ціна, ПДВ та сума.
Розгорнуті `line_items.notes` більше не потрапляють у PDF. Примітки до
рахунку, платіжні реквізити й підсумки збережено. Передперегляд,
завантаження і PDF пацієнта використовують спільний генератор.

Під час візуальної перевірки виявлено обрізання IBAN у компактній сітці.
Платіжні реквізити перенесено до рядків повної ширини, щоб друкувати
ідентифікатори без скорочення.

## Перевірка

- Vitest: 51 тест у спільному прогоні документів і рахунків.
- Playwright: 15 сценаріїв пройшли — створення, вибір доступної пропозиції, погодження,
  відновлення після помилки, оновлення залишку, видимості футера та PDF.
  RU/DE, ширина 390 і 1440 px; відповіді API підставні.
  Валідна попередньо вибрана пропозиція дозволяє створення без штучних змін.
- TypeScript, ESLint, rustfmt, перевірка diff і production-збірка пройшли.
- Rust: текстове вилучення із фактично згенерованого PDF перевіряє назву
  позиції, кирилицю, суму, повний IBAN і відсутність розгорнутого опису.
- PDF відрендерено Poppler і переглянуто; браузерні скриншоти збережено
  в `artifacts/design-qa/invoice-create*` та `invoice-detail*`.

Після останнього збільшення відступу між реквізитами і приміткою Rust
успішно скомпілювався, але Windows Application Control заблокував запуск
тестового EXE (`os error 4551`), зокрема при повторі з дозволом на запуск
поза sandbox. Текстовий PDF-тест із повним IBAN проходив до цієї останньої
правки відступу. Остаточний повтор PDF-тесту залишається непідтвердженим.

Зміни локальні. Реальні рахунки не створювались і платежі не змінювались.
