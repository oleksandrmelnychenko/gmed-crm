Зміни підготовлені в робочому дереві. У DEV/PROD їх не розгорнуто, робочі
фінансові записи не змінено. Початкові знахідки збережено в

## Узгоджений процес ліда

Підписані документи та надходження передоплати — окремі стани. Відсутня,
часткова або прострочена передоплата не зупиняє конвертацію ліда, виконання
замовлення чи повторну роботу з пацієнтом. Перевірки документів і дозвіл
бухгалтерії на виконання збережені; арифметичні обмеження фінансових операцій
також залишаються чинними.

- На ліді можна позначити вимогу передоплати, суму й необов'язкову дату **та час**.
  Якщо окремої суми немає, використовується сума поточного кошторису.
- Час вводиться як місцевий, передається з часовим поясом і зберігається як
  `TIMESTAMPTZ`. Порожній рядок у `prepayment_due_at` очищає термін;
  відсутнє поле залишає його без змін. Вимкнення вимоги передоплати очищає термін.
- Окремі статуси: передоплата не потрібна, не налаштована сума, очікується
  рахунок, очікується оплата, частково оплачено, оплачено, термін протягом
  24 годин, прострочено. У статусів терміну пріоритет перед «частково»;
  отримана сума й залишок завжди доступні окремо.
- Статуси читаються з журналу надходжень і повернень рахунків. Поле оплати
  кошторису більше не можна редагувати як підтвердження грошей.
- Після конвертації вимога передоплати й термін залишаються на тому самому замовленні.
- Внутрішні сповіщення отримують активні CEO/бухгалтерія, призначені менеджери
  пацієнта та менеджер, який створив лід. Контроль починається для підписаних
  замовлень або замовлень із фактичними надходженнями. Після цього він
  продовжується і при скасуванні останньої оплати до нуля.
- Після зміни оплати/комерційних умов запускається синхронізація; фоновий
  обробник перевіряє настання термінів кожні 60 секунд. Збережений стан
  запобігає повторним сповіщенням без змін і після перезапуску сервера.
  Це повідомлення всередині застосунку, без email/SMS.
- При першому запуску вже оплачені замовлення та замовлення без вимоги
  передоплати фіксуються без масових сповіщень. Підписані неоплачені
  замовлення потрапляють у контроль одразу.

## Виправлені фінансові помилки

| Сценарій | Результат зміни |
| --- | --- |
| Скасування оплати використаного авансу | API та БД не дозволяють залишити активне зарахування без грошового покриття. |
| Повернення та скасування коригування | Статус рахунку перераховується з чистих надходжень після повернень. |
| Кредит звичайного рахунку після коригування | Входить у фінансову позицію компанії та узгоджується з випискою пацієнта. |
| Зміна типового банку перед сторнуванням | Сторно повторює рахунок, валюту, нетто, ПДВ та брутто початкової проводки зі зворотним знаком; працює й для неактивного початкового банку. |
| Ручна зміна банку скасованого платежу | Заборонена, щоб не розірвати пару початкової проводки та сторно. |
| Дата скасування раніше надходження | Відхиляється API та перевіркою БД. |
| Валюта рахунку | Передається в API, інтерфейс і PDF; підсумки ledger та експорт фільтруються за валютою. |
| Чернетки | Не збільшують борг; не можуть отримати зарахування авансу. |
| Ручна «оплата» кошторису | Не створює уявних грошей: показник читається з журналів рахунків, ручне редагування відхиляється. |
| Витрата Concierge без замовлення | Залишається у фінансовому зведенні й виписці пацієнта. |
| Зняття зарахування авансу | Зберігається архів операції з часом та виконавцем; історичний зріз враховує момент зняття. |
| Часткові оплати й округлення ПДВ | Проводиться приріст накопиченої суми; 33,33 + 33,33 + 33,34 дають точний ПДВ повного рахунку. |
| Міграція порожньої БД | Додано вузьку сумісність для старих demo-рядків `qty`; наявні checksum міграцій не змінено. Помилка підготовки обов'язкової тестової БД більше не маскується пропуском. |

## Межі виправлення історії

Раніше видалені зарахування авансу неможливо відновити лише новою міграцією.
Архів захищає історію наявних і майбутніх зарахувань після встановлення зміни.
Старі неправильно рознесені банківські проводки та суми, введені у кошториси
без платіжного підтвердження, автоматично не переписуються: їх треба звірити
з первинними документами. Виявлені на DEV старі 100 EUR у кошторисі не
перетворені на платіж.

Міграції: `20260819112500`, `20260907203000`, `20260907204000`, `20260907205000`.
Сервер і міграції треба випускати разом; нові запити використовують додані
функції та view. Повна відсутність інших дефектів у системі цими перевірками
не стверджується.
