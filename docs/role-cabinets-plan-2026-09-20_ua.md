# Кабінети ролей: аналіз і план виконання — 2026-09-20

Джерела: RBAC-матриця з Excel (`docs/backlog/02_rbac-matrix_ua.md`), user stories
EPIC 14 «Безпека» (`docs/requirements/03_product-backlog_ua.md`), аудит кабінетів
2026-08-11 (`docs/audits/role-cabinets-2026-08-11/`), і повний прохід коду
`crates/domain/src/role.rs`, `crates/server/src/auth/middleware.rs`,
`crates/server/src/routes/*.rs`, `frontend/src/lib/staff-route-access.ts`,
моделей сторінок і дашбордів (стан `main` на 2026-09-20).

Принцип, який фіксує бізнес: **CEO — єдина роль із повним доступом; кожна інша
роль бачить лише свій кабінет, у якому більшість екранів read-only, а зміни
дозволені тільки в її зоні відповідальності.**

## 1. Як є зараз

### 1.1 Ролі та серверний гейт

| Роль (`users.role`) | Доступ до бізнес-API сьогодні | Коментар |
|---|---|---|
| `ceo` | повний, `require_any_role` пропускає автоматично | єдина «повна» роль |
| `patient_manager`, `billing`, `concierge`, `teamlead_interpreter`, `interpreter` | повний, далі обмежується перевірками в маршрутах | «release staff roles» |
| `ceo_assistant`, `sales` | **лише** сесія + task-manager (`/concierge-operational-items`, сповіщення) | гейт `is_release_staff_role` у `middleware.rs:116-126` |
| `it_admin` | **лише** сесія; жодного бізнес- чи адмін-API | усі `/admin/*` маршрути формально дозволяють `it_admin`, але гейт його не пускає — адмінку відкриває тільки CEO |
| `patient` | портал пацієнта | окремий контур |

Наслідок: три ролі (CEO Assistant, Sales, IT Admin) фактично не мають робочого
місця, хоча в матриці для них описані кабінети.

### 1.3 Розбіжності «маршрут ↔ модель сторінки ↔ бекенд»

| Модуль | Маршрут пускає | Модель сторінки дозволяє | Бекенд дозволяє |
|---|---|---|---|
| Ліди | ceo, concierge | + patient_manager, sales (створення/редагування) | patient_manager, sales, concierge (читання) |
| Документи | ceo, concierge, billing | 8 ролей (upload PM/teamlead/interpreter/it_admin) | 8 ролей з row-level policy |
| Контракти/пропозиції | ceo, billing | + ceo_assistant (читання), patient_manager (керування) | ceo, ceo_assistant, PM, billing |
| Звіти | ceo, billing | + ceo_assistant, PM, sales | stats: ceo, ceo_assistant, PM, billing, sales |
| SOP | ceo, billing | створення PM/teamlead, перегляд усі | список для всіх 10 ролей |
| Сервіси | ceo, concierge, billing | + PM, it_admin | ceo, PM, concierge, billing |

Отже, частина дозволів на бекенді й у моделях — мертвий код: користувач ролі
не може дійти до екрана. І навпаки: `it_admin` має UI-права на пацієнтів і
повний CRUD записів (`appointments/model/selectors.ts:141-160`), що суперечить
матриці «IT Admin: ні, крім тестових даних».

### 1.4 Дашборди

- CEO → `ExecutiveBusinessMap`; решта → `RoleDashboardPage` з 8 пресетами
  (`role-dashboard-config.ts`). Невідома роль мовчки отримує пресет PM.
- «Швидкі посилання» = перші 4 пункти меню за порядком правил, тобто майже
  завжди task-manager / проєкти / 2FA / інциденти, а не робочі модулі ролі.
- `it_admin` ніколи не бачить живу чергу задач (не входить у `TASK_MANAGER_ROLES`).

### 1.5 Користувачі, паролі, 2FA — що є

| Функція | Стан |
|---|---|
| Створення користувача, зміна ролі, деактивація, розблокування, скидання пароля | є, **лише CEO** (`routes/users.rs`, `require_exact_role`) |
| Політика пароля | 8–256 символів, великі/малі/цифра/символ; історія 5 паролів; строк 90 днів (`password_expire_days`, 0 = вимкнено) |
| `password_reset_required` | є: 401 на кожному запиті до зміни пароля |
| **Зміна власного пароля користувачем** | **немає** — ані API `/me/password`, ані сторінки профілю |
| **Сторінка профілю (ім'я, email, аватар, мова)** | **немає**; мова — глобальний перемикач без збереження |
| **Перегляд/відкликання власних сесій** | **немає** в UI (API `/auth/sessions` є); адмін бачить усі сесії |
| 2FA TOTP | самообслуговування для всіх staff; обов'язковість за ролями через `system_settings.mfa_totp_required_roles`; банер-нагадування не блокує |
| Логін з підтвердженням адміна (`users.mfa_required`) | є, керує IT Admin/CEO |
| Автоблокування після невдалих входів | є (`max_failed_login_attempts`, `locked_until`) |
| Запрошення/онбординг нового співробітника | немає — CEO вводить пароль вручну |
| Захист від деактивації/зниження останнього CEO | немає |
| Матриця доступу до полів (`/admin/access`) | є для 8 ролей; `ceo` та `it_admin` жорстко «повні», у матриці відсутні |

Два рішення, які потрібно підтвердити з бізнесом (у матриці вони неоднозначні):

1. **IT Admin і користувачі.** Матриця дає IT Admin «Адміністрування» і user story

## 3. Механізм «read-only кабінету»

Сьогодні read-only реалізується випадково: або маршрут не пускає, або в моделі
сторінки прописано `canEdit=false`, або бекенд повертає 403 уже після натискання.
Потрібен один механізм, який використовують і бекенд, і фронтенд:

1. **Серверний реєстр можливостей (capabilities).** Один модуль
   `crates/domain/src/access/capabilities.rs`: перелік `Capability`
   (`patients.view`, `patients.edit`, `invoices.create`, `users.manage`, …) і
   таблиця `role → set<Capability>`, згенерована з матриці вище. Усі
   `can_read_*` / `can_manage_*` у маршрутах замінюються на
   `auth.can(Capability::X)`; `require_any_role` лишається тільки для
   виняткових випадків. Один тест `rbac_capability_matrix_matches_product_matrix`
   розширюється на всю таблицю.
2. **`GET /me` повертає `capabilities: []`.** Фронтенд більше не тримає
   `role === "ceo"` у 40 файлах: `useCan("invoices.create")`. Меню, кнопки,
   колонки й режим форм виводяться з одного джерела.
3. **Режим перегляду форм.** Спільна обгортка `ReadOnlyScope` (React context):
   усередині всі `Input/Select/Textarea/Button[type=submit]` стають disabled, а
   кнопки дій ховаються. Кожна сторінка вмикає її однією умовою
   `!can("<module>.edit")`. Це і є «рід онлі для інших».
4. **Row-level scope** лишається як є (`policy::check_access`, assignment,
   `ShareStatus`, маскування полів) — capabilities відповідають на «чи є
   екран/кнопка», policy — на «чи цей запис».
5. **Знімок для перевірки.** Скрипт `scripts/rbac_snapshot.py` виводить
   таблицю «роль × capability» з коду; він порівнюється з `02_rbac-matrix_ua.md`
   у CI (job `hygiene`), щоб матриця й код не розходилися знову.

## 4. План виконання

Порядок вибрано так, щоб кожен етап можна було викотити окремо й перевірити на DEV.

### Етап 0 — Узгодити цільову таблицю (виконано 2026-09-20)
- Рішення підтверджено власником: (1) IT Admin керує користувачами — створення,
  блокування, скидання паролів/2FA, сесії; призначати роль `ceo` і змінювати
  існуючого CEO може лише CEO. (2) CEO Assistant — усе read-only плюс
  task-manager і терміни CEO, без змін у пацієнтах, фінансах, документах.
- Зафіксувати, які ролі мають 2FA обов'язково (пропозиція: усі staff, крім
  `interpreter`; пацієнти — ні).

### Етап 1 — Самообслуговування акаунта (2 дні)
- API `PUT /me/password` (поточний пароль + новий; політика й історія ті самі, що
  в `reset_password`; відкликати інші сесії), `GET/PUT /me/profile` (ім'я,
  телефон, мова), `GET /me/sessions` + відкликання власних (обгортка над
  `/auth/sessions`).
- Сторінка `/account`: профіль, зміна пароля, 2FA (перенести з
  `/security/two-factor` + QR-код), мої сесії, мова з персистенцією.
- Примусова зміна пароля при `password_reset_required` — окремий екран замість
  401 у кожному запиті.
- Захист «останнього CEO»: не можна деактивувати або понизити останній активний
  акаунт `ceo`.

### Етап 2 — Реєстр capabilities + серверний гейт (3 дні)
- `capabilities.rs`, `AuthUser::can`, заміна перевірок у маршрутах модуль за
  модулем (patients, leads, orders, contracts, invoices, documents, appointments,
  providers, services, sops, stats, admin).
- Прибрати `is_release_staff_role`-гейт як єдиний фільтр: `ceo_assistant`,
  `sales`, `it_admin` отримують доступ рівно до своїх capabilities.
- `it_admin`: заборонити всі медичні/фінансові дані на рівні capabilities
  (політика `DataSensitivity` вже забороняє) і прибрати з UI пацієнтів, чату
  з пацієнтами, записів.
- `GET /me` → `capabilities`; знімок у CI.

### Етап 3 — Фронтенд: одне джерело правди й read-only режим (3 дні)
- `useCan`, генерація `staff-route-access.ts` і меню з capabilities (правила
  маршрутів лишаються, але їхні списки ролей формуються з реєстру).
- `ReadOnlyScope` і його застосування: пацієнти, замовлення, контракти,
  рахунки, документи, провайдери, готелі, сервіси, SOP, ліди.
- Усунути мертві гілки з розділу 1.3 (документи, контракти, звіти, SOP, ліди,
  сервіси) — тепер вони стають досяжними або прибираються свідомо.

### Етап 4 — Кабінети ролей (4 дні, по ролі)
Для кожної ролі: лендинг-дашборд із власними KPI і швидкими діями, меню лише зі
своїх модулів, read-only там, де матриця каже R.
1. **Billing** і **Concierge** — уже найближчі до цілі; доробити швидкі дії
   дашборду, прибрати зайве (Concierge: ліди лише як сервісна сітка без деталей
   і майстра — P0 з аудиту).
2. **Patient Manager** — власні пацієнти, ліди (W), контракти (W), звіти (R).
3. **Sales** — ліди (W), партнери/провайдери (R), аналітика (R), чат; сьогодні
   роль порожня.
4. **CEO Assistant** — усе R + task-manager; терміни CEO.
5. **Teamlead / Interpreter** — планування перекладачів, звіти й години,
   затвердження; interpreter — лише свої призначення.
6. **IT Admin** — технічний кабінет: користувачі, сесії, безпека, налаштування,
   підписи, DATEV-підключення, інциденти, health; без пацієнтів.
7. **CEO** — без змін по доступу; додати керування правами (`/admin/users`
   показує capabilities ролі та індивідуальні винятки з `/staff-access`).

### Етап 5 — Керування користувачами і правами (виконано 2026-09-20)
- `/admin/users` доступний IT Admin (крім ролі `ceo`), CEO — повністю.
- Онбординг: створення акаунта з одноразовим паролем і `password_reset_required`;
  лист/посилання — опційно (потребує SMTP, якого зараз немає).
- Аудит усіх змін ролей/прав у `audit_log` уже є — додати екран перегляду для
  CEO/IT Admin (`/admin/activity` вже існує; додати фільтр «зміни доступу»).
- Матриця полів `/admin/access`: додати колонку `it_admin` з жорстким `hidden`
  для медичних/фінансових полів (сьогодні роль відсутня в матриці).

**Зроблено:**
- `POST /users` приймає `password` опційно: без нього сервер генерує стійкий
  випадковий пароль (16 символів, усі класи), ставить
  `password_reset_required = true` і повертає його один раз як
  `one_time_password`; в аудит потрапляє лише факт видачі, не секрет.
  `POST /users/{id}/reset-password` має той самий режим (`generate: true` або
  порожнє тіло) і завжди вимагає зміни пароля при наступному вході — далі
  працює екран примусової зміни з етапу 1. **Листи-запрошення не реалізовано
  (SMTP немає): одноразовий пароль адміністратор передає вручну** — UI показує
  його один раз із кнопкою копіювання (діалог створення і скидання).
- Список користувачів віддає `password_reset_required`, `totp_enrolled`,
  `active_sessions`, `last_login_at`; на `/admin/users` є розблокування,
  завершення сесій (`/admin/sessions/user/{id}/revoke`), скидання TOTP,
  (де)активація; для IT Admin рядки CEO read-only, роль `ceo` у списку
  відсутня без `users.manage_ceo`; `last_ceo_protected` та інші відмови
  сервера показуються зрозумілим текстом RU/DE.
- `GET /admin/activity?category=access` (без параметра поведінка без змін) і
  вкладка «Доступ и роли / Zugriff und Rollen» на `/admin/activity`: лише
  `create_user`, `update_user`, `deactivate_user`, `activate_user`,
  `reset_password`, `totp_reset`, `update_access_policy`, події
  `*_staff_access_*`; доступно власникам `admin.activity` (CEO, IT Admin).
- Матриця `/admin/access` і `DEFAULT_PATIENT_POLICIES`: колонка `it_admin` з
  системно заблокованим `hidden` для всіх полів пацієнта (міграція
  `20260920150000_it_admin_patient_field_policies.sql`); `ceo` лишається
  неявно «повним» і в матриці не показується. Скидання матриці тепер бере
  дефолти з того самого списку, а не з другої копії.
- Тести: `users_api.rs` (онбординг → перший вхід повертає
  `password_change_required`, `generate` при скиданні, зведення по сесіях/2FA,
  IT Admin не створює CEO), `admin_security_api.rs` (`category=access`,
  заблокована колонка `it_admin`), vitest для моделі сторінки користувачів і
  вкладки активності, Playwright `tests/e2e/admin-users.spec.ts` (mock API).

## 5. Ризики й що не робити

- Не робити read-only через окремі «viewer»-ролі — множаться ролі, а матриця
  описує саме поведінку існуючих.
- Не давати IT Admin обхідний повний доступ «для тестів»: тестові дані — на DEV,
  на PROD IT Admin працює лише з технічним кабінетом.
- Concierge і ліди: сервер має віддавати лише сервісні поля (проєкція), а не
  повний лід із приховуванням у UI.
- Зміна гейта `is_release_staff_role` торкнеться інтеграційних тестів на ролі
  (як 2026-09-19); оновлювати їх у тому самому коміті.
