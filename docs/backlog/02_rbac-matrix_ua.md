## Ключові правила доступу

- `CEO` єдина роль з реальним повним бізнес-доступом.
- `Patient Manager` працює тільки зі своїм пулом пацієнтів.
- `Interpreter` та `Concierge` не отримують повної медичної картки.
- `Interpreter` бачить лише терміни, на які його призначено перекладачем (або якими він володіє): список і календар, картку терміну, звіт, нагадування, комунікацію, конфлікти й realtime-події. Прив'язка до пацієнта, яку дає бронювання на один термін, не відкриває інших термінів пацієнта (зокрема термінів і нотаток інших перекладачів). Для свого терміну він бачить ім'я пацієнта, час, місце й брифінг (нотатки). Документ, прив'язаний до терміну, перекладач бачить лише для свого терміну (або за явним поширенням / призначенням перекладу). Замовлення й хронологію (timeline) пацієнта `Interpreter` не бачить.
- Замовлення (`/orders`): `Concierge` і `Teamlead Interpreter` мають `orders.view` лише для read-only проєкції своєї частини замовлення (`read_scope`). `Concierge` — номер, пацієнт, період, фаза, статус і послуги немедичних провайдерів (трансфер, готель, VIP) без цін, нотаток і фінансів; `Teamlead Interpreter` — те саме для послуг перекладачів (години перекладача, позиції зі звіту), бачить також замовлення з перекладачем без призначення на пацієнта. Опис потреб, кейс, контракт, суми, оплати, економіка, зміни суми, групи, пайплайн, фільтри за провайдером/лікарем, врегулювання розірвання й realtime-події замовлень їм закриті (403). Жодна запис-операція із цим доступом не з'являється.
- У картці пацієнта `Concierge` бачить вкладку термінів (лише для пацієнтів, до яких має доступ; медичні терміни — як заблоковані слоти без назви, провайдера, лікаря і типу маршруту). Замовлення і хронологію (timeline) пацієнта `Concierge` не бачить.
- `Teamlead Interpreter` бачить у командному контексті всі терміни з перекладачем (заброньованим або зі звітом перекладача) без призначення на кожного пацієнта, відкриває їхні звіти й затверджує або відхиляє їх. Командний контекст — це перегляд і рішення щодо звітів: змінювати термін (статус, перепланування, призначення перекладача, чекліст, нагадування, комунікацію) тимлід може, як і раніше, лише за призначенням на пацієнта, як власник або як призначений перекладач. Інші терміни пацієнта — лише за призначенням на пацієнта або як власник. Дашборд тимліда рахує звіти на перевірці (`pending_reports`) і частку затверджених годин від поданих (`hours_approval_rate_pct`): звіт, що чекає рішення, не дає 100 %.
- `Concierge` і `Interpreter` у task-manager (`/concierge-operational-items`, `/tasks`) бачать і змінюють лише свої задачі: призначені їм, створені ними або явно поширені через проєкт. Прив'язка до пацієнта не відкриває чужих задач цього пацієнта — ні в списку, ні в картці задачі, коментарях, чеклісті, історії, файлах чи realtime-подіях. Керівні ролі (`Patient Manager`, `Teamlead Interpreter` тощо) зберігають перегляд задач своїх пацієнтів.
- Статус задачі змінюється за одними правилами для всіх задач, зокрема задач терміну: виконавець доводить задачу до перевірки (`review`), закриває її автор або вища роль; кожна зміна потребує актуального `expected_updated_at`, заборонена для архівних задач, пишеться в історію задачі й сповіщає автора. Застарілий шлях `/tasks/{id}/status` виконує той самий обробник, що й `/concierge-operational-items/{id}/status`.
- `Billing` не бачить медичні дані, але бачить фінансові документи і підтверджені послуги.
- Позиція замовлення, створена із затвердженого звіту перекладача, не копіює текст звіту: у нотатках лише посилання (`Bericht: <id>`), години й дата терміну. Для старих позицій, де текст уже скопійовано, API віддає ролям без `patients.medical.view` (`Billing`) посилання замість тексту (картка замовлення, список послуг, звіт послуг пацієнта, пошук); збережена історія не переписується. Сам звіт лишається в терміні за його правилами доступу.
- `Patient` бачить тільки те, що було явно опубліковано або відкрито для нього.
- Журнал поширень документа (отримувачі, канал, супровідне повідомлення) бачать лише `CEO`, `Patient Manager` і `Teamlead Interpreter` (capability `documents.shares.view`); інші ролі, які можуть відкрити документ, не бачать, кому і з яким повідомленням його надіслано (мінімізація даних).
- `IT Admin` не працює з продуктивними медичними даними, окрім технічних або тестових сценаріїв.

## Наслідки для архітектури

- Авторизація має бути не тільки рольовою, а й контекстною: `role + assignment + data class + share status`.
- Для документів потрібні окремі прапори: `internal`, `external-shareable`, `patient-visible`, `medical-only`.
- Для кожної операції читання/зміни потрібен audit trail.
