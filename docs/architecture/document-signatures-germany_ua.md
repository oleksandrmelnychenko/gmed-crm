# Електронне підписання документів — Німеччина

TASK-443FE5B3, 5 вересня 2026 року. Перший адаптер: Skribble Sign API v2.

## Конфігурація

За замовчуванням інтеграція вимкнена. Налаштування підпису стоять на сторінці
зовнішніх сервісів «Администрирование → API-подключения» /
«Administration → API-Verbindungen» за адресою `/admin/api-connections` для
CEO та IT Admin (рішення власника 05.10.2026: один пункт меню, вкладка на
сервіс). Вкладка «Электронная подпись · Skribble» містить підключення до
провайдера (API-ім’я, API-ключ, режим) і представників GMED за замовчуванням;
вкладка «E-Mail · Mittaro» (`?tab=email`) — вихідну пошту
(Mittaro; ключ поки в конфігурації сервера). Окремого пункту «Электронная подпись» у меню
більше немає, стара адреса `/admin/signatures` переадресовує на цю сторінку.
Через кнопку документа «Электронная подпись» також доступне окреме вікно
«Вход / подключение Skribble» / «Skribble anmelden / verbinden» з тією самою формою.
Кнопка входу відкриває німецький кабінет `https://my.skribble.de/` окремо.
Адміністратор (CEO або IT Admin) вводить API-ім’я, API-ключ і режим,
після чого GMED перевіряє доступ і зберігає підключення. Особистий пароль
кабінету вводиться на сторінці Skribble; форма GMED використовує API-доступ
із [адміністративного розділу провайдера](https://docs.skribble.com/business-admin/api/apicreate.html).

Дані підключення зберігаються в `signature_provider_connection`, зашифровані
AES-256-GCM через серверний `KeyRegistry`. Ключ не повертається API, не
потрапляє в localStorage чи аудит. Після збереження та закриття поле ключа
очищається. Доступні перевірка з’єднання та відключення. Активні запити
блокують зміну облікового запису та відключення; заміна ключа того самого
облікового запису дозволена. Конфігурація з бази має пріоритет над env,
зокрема після відключення, і підхоплюється без перезапуску серверів.

Під час ротації серверних ключів треба залишати ключ із `key_id` цього
підключення доступним або повторно зберегти підключення новим активним
ключем до видалення старого ключа з реєстру. Стан браузерного входу в
Skribble не є станом серверного API-з’єднання.

## Запуск із реєстру та карток

Спільна дія `DocumentSignatureAction` відкриває вікно з конкретним документом,
скачуванням джерела, підписантами та статусом. Вона доступна:

- у реєстрі документів, черзі класифікації та черзі перекладів;
- у картці документа й окремому попередньому перегляді;
- у документах пацієнта, редакторі, джерелах клінічних записів і перегляді OCR;
- у списках і перегляді документів ліда;
- у документах провайдера та пов’язаних документах прийому;
- у картках договору, кошторису й замовлення через вибір збереженого PDF;
- біля документів-джерел зовнішніх рахунків і підтвердних документів послуг.

Для договору завантажуються документи його пацієнта або ліда; для кошторису
та замовлення — документи цього замовлення. PDF не вибирається автоматично.
При зміні документа чернетка підписантів і підтвердження скидаються. Відкриття
вікна не створює запрошення; запит надсилається лише після перевірки адрес і PDF.
API-стан завантажується при відкритті вікна, а не для кожного рядка списку.

Запуск доступний наявним ролям CEO, Patient Manager і IT Admin, з додатковою
серверною перевіркою прав на конкретний документ. Інші ролі не отримують
нових повноважень. Видалений, архівний, уже підписаний, попередній або не-PDF
документ показує причину недоступності. Після завершення результат залишається
у вікні; список із переданим обробником оновлюється після його закриття.

За уточненням користувача PDF-вкладення чату та задач до цього етапу не входять.
Незбережені файли й динамічні PDF рахунків спочатку мають стати документами
реєстру. Запуск підпису не створює для них прихованих копій.

Альтернатива для адміністрування нативного сервера через середовище:

```dotenv
DOCUMENT_SIGNATURES_ENABLED=true
DOCUMENT_SIGNATURES_MODE=demo
SKRIBBLE_USERNAME=api_demo_...
SKRIBBLE_API_KEY=...
```

Для Docker release задаються відповідні `GMED_DOCUMENT_SIGNATURES_ENABLED`,
`GMED_DOCUMENT_SIGNATURES_MODE`, `GMED_SKRIBBLE_USERNAME`, `GMED_SKRIBBLE_API_KEY`.
Ключ зберігається тільки в серверних секретах; його немає у фронтенді.
Для робочого QES потрібні `MODE=live` і німецький обліковий запис `api_prod...`.
Невідповідність режиму типу облікового запису зупиняє старт сервера.

Регіон фіксований: `https://api.skribble.de/v2`. Усі запити, авторизація,
PDF і звіти використовують один регіон; редиректи заборонені. У робочому
режимі запитується і перевіряється `QES` / `EIDAS`; тестовий режим використовує
`DEMO`. Німецький регіон хостингу та рівні підпису описані в
[офіційній документації Skribble](https://api.docs.skribble.com/introduction)
та [схемі Sign API v2](https://api.docs.skribble.com/api/sign-v2/2.2.0/schema.yaml).

## Життєвий цикл

`POST /documents/{id}/signature-requests` перевіряє View, Download і Edit,
права на пацієнта, актуальність версії, PDF, розмір і перевірку файлу.
Одержувачі мають унікальні email та заповнені імена; максимум шість.
Зберігаються контрольна сума джерела, його контекст і незмінний список
запитаних підписантів. Для шаблонів `framework_contract` і `single_order`
обов’язкові ролі клієнта та агентства.

Після запису в базу сервер повертає HTTP 202 і надсилає запит провайдеру.
У темі листа тип документа, версія та короткий ID, без даних пацієнта.
Підписант передається через `signer_identity_data` (ім'я, прізвище, email),
без `account_email`, щоб профіль Skribble не замінював вибрану в GMED особу.
Це персональне гостьове запрошення: документ відкривається за посиланням
із листа й не додається до кабінету наявного акаунта Skribble. Поведінку
описано в [Sign API v2](https://api.docs.skribble.com/api/sign-v2/signature).
Вкладення до повідомлень про
завершення вимкнені. Провайдер надсилає підписантам персональні запрошення;
посилання з токенами не зберігаються в GMED і не передаються іншим працівникам.

### Рамки підпису

Підписант не розміщує підпис вручну: разом із запитом сервер передає в
`visual_signature.positions` рамку для кожного місця, де ця особа підписує
(сторінка з нуля, координати й розміри в пунктах PDF від лівого нижнього
кута сторінки). Skribble фіксує підпис у цих рамках.

- Генератори документів записують місця підпису в
  `generated_bindings._signature_anchors` (ролі `client`, `agency`,
  `guardian_1`, `guardian_2`, `payer` для Kostenübernehmer); у комплекті
  сторінки зсуваються на кількість сторінок попередніх документів.
- Згенерований документ без такого запису (створений до появи рамок)
  розмічається за самим PDF: `document_signatures/frames.rs` знаходить підпис
  під лінією підпису («Unterschrift …» у договорах, замовленнях і кошторисах)
  та рядок «Unterschrift: ____» у згодах. Інші згадки слова рамок не дають.
  Лінія «Unterschrift Kostenübernehmer» дає рамку `payer`; кілька ліній
  сторони клієнта на одній сторінці (батьки як сторона договору) або лінії
  «gesetzl. Vertreter/in» нумеруються `guardian_1`, `guardian_2` у порядку
  читання, як їх записують генератори.
- Те саме діє для кожного документа пакета: рамки (записані або знайдені в
  PDF) переносяться на сторінки цього документа в об'єднаному файлі, і два
  підписанти ніколи не отримують одну рамку.
- Завантажені ззовні PDF не розмічаються: їхній підписант розміщує підпис сам.
  Лише для документа без записаних і без знайдених рамок композитор пакета
  показує попередження «немає поля для підпису».

Картка запиту показує, чи рамки передано: «Места подписи размечены…» або
попередження, що підписант розмістить підпис сам.

Працівник раз на 30 секунд вибирає до 20 запитів; звичайний інтервал
повторної перевірки запиту — хвилина, після помилки — дві. Lease і
`FOR UPDATE SKIP LOCKED` підтримують кілька процесів. Після аварійного
завершення створення lease спливає через 5 хвилин; синхронізації — 10.

Стани: `submitting`, `submission_unknown`, `pending`, `completed`,
`needs_review`, `declined`, `withdrawn`, `expired`, `error`.
Активний запит на конкретний документ може бути тільки один.
Після невизначеного POST сервер шукає запит за UUID у заголовку і перевіряє
повний `custom`, власника, підписантів та регіон облікового запису.
POST створення автоматично не повторюється. Якщо пошук не знаходить запит,
невизначений стан зберігається для розслідування адміністратором; без
підтвердження відсутності запиту його не можна вважати невідправленим.

Після `SIGNED` потрібні підписи всіх запитаних осіб, правильний рівень,
законодавство та час. Використовується останній `document_id` із запиту,
бо кожен підпис створює новий PDF у провайдера. Завантажуються PDF та
PDF-протокол, файли перевіряються і зберігаються без перегенерації.
Новий документ та завершення запиту записуються в одній транзакції.
Повторне виконання не створює нової версії. При невизначеному результаті
COMMIT записані файли не видаляються: це захищає вже збережені докази.
Очищення сиріт має перевіряти обидві таблиці, а не лише `documents`.

Джерело зберігається. Актуальний робочий результат стає його наступною
версією; контекст, класифікація та прямі/профільні ACL копіюються.
Для актуальної робочої версії також копіюються `provider_document_links`,
щоб підписаний PDF залишався в картці того самого провайдера. Тестові та
застарілі результати не додаються до цього операційного списку.
Зовнішні document_shares не створюються. `signed_by` не використовується
для імітації особи зовнішнього підписанта. Тестові й застарілі результати
зберігаються окремо як внутрішні документи `signature_evidence`, без
`signed_at` та шаблону, який міг би закрити вимогу до справжнього документа.

## Межі першого етапу

### Комплекти з інформаційними додатками

Для нових запитів `framework_contract` додається `privacy_information`, для
`order_cost_estimate` — `cost_estimate` («Предварительный расчёт медицинских расходов»).
Працівник вибирає актуальний PDF тієї самої картки (для кошторису — також того
самого замовлення) та переглядає обидва файли перед відправленням. Сервер
перевіряє доступ, версію, контекст і SHA-256; без належного додатка запит
не створюється. Старі запити не доповнюються заднім числом.

Уточнення 2026-10-03 (TASK-FB4D): медична калькуляція (`cost_estimate`) існує
лише для замовлень із медичними видами робіт. Тому вона обов'язкова для
`order_cost_estimate`, **коли для цього замовлення є актуальна калькуляція**
(`cost_calculation_available` у `package.rs`); якщо її немає, кошторис
підписується без додатка, а композер показує про це нотатку. Інформація про
захист даних (`privacy_information`) лишається обов'язковою без винятків.

Використовується [Signature Attachment API v2](https://api.docs.skribble.com/api/sign-v2/signature-attachment):
створення запиту без одержувачів → завантаження додатка → перевірка байтів →
додавання підписантів із запрошеннями через PUT. Додаток доступний у запиті,
але не зливається з основним PDF і не стає окремим об'єктом підписання.
Фази зберігаються у `document_signature_attachments`. Після невизначеного
POST/PUT мутація не повторюється: стан звіряється читанням провайдера; якщо
результат не підтверджений, запит можна відкликати після встановлення його ID.

Під інформаційними документами відображаються окремі стани: «Не отправлен»,
«Отправлен для ознакомления», «Ознакомлен». Автоматичне «відправлено» фіксується
лише після перевіреного додатка й прийнятих провайдером одержувачів; це не доказ
доставки листа в поштову скриньку чи прочитання. Менеджер/CEO окремо фіксує
отримане від клієнта підтвердження. Для відправлення поза системою є явна ручна
відмітка, яка сама не надсилає листа. Автор, час та конкретна версія зберігаються
в `document_review_events`; `documents.signed_at` не змінюється. DEMO має окрему
позначку. Повторне електронне відправлення потребує нового підтвердження.

Потрібна міграція `20260907210000_document_review_packages.sql` та узгоджене
оновлення серверу і фронтенду. Цей код сам по собі не розгортає зміни на DEV/PROD
і не створює запрошень для наявних документів.

Перевірка комплектів 07.09.2026: 10 Rust unit/mock HTTP тестів, PostgreSQL
інтеграційний сценарій (323 с), 24 Vitest та 45 Playwright сценаріїв пройшли.
Перевірені повний ланцюжок додавання вкладення до запрошення, відмова без
додатка/з неправильним типом, ручна відмітка менеджера без підпису PDF,
ідемпотентність, ACL і відсутність повторного PUT після невизначеного результату.
Міграції виконані тільки на окремій синтетичній PostgreSQL у тимчасовому
контейнері з tmpfs; тестову БД, контейнер і тунель прибрано. TypeScript та ESLint
змінених компонентів пройшли. Реальні запрошення Skribble не надсилалися.

- Автоматичні запити, підписи, повернення PDF/протоколу та статус документа.
- ~~Окремі поля бізнес-договору, замовлення, DSGVO та інших згод автоматично
  не змінюються.~~ З 2026-10-01 завершений підпис застосовує ці ефекти — див.
  «Пакети документів на підпис → Ефекти завершення».
- Доказом служать відповідь авторизованого API і незмінений протокол
  провайдера. Незалежний криптографічний валідатор PDF не інтегрований.
- Реальні QES, тариф, ідентифікація й договірні умови потребують перевірки
  на обраному німецькому обліковому записі. У цій роботі справжні документи
  та запрошення не надсилалися; інтеграція не ввімкнена й не розгорнута.

## Перевірки

Фінальний прогін: 4 Rust-тести (включно з PostgreSQL), 2 Vitest-тести
та 3 браузерні сценарії пройшли. `cargo check`, TypeScript і ESLint для
змінених компонентів пройшли. Тимчасову PostgreSQL після тесту видалено.
Реальна перевірка підписання у Skribble залишається до підключення акаунта.

- Unit-тести: відповідність облікового запису режиму, німецький API-протокол,
  ідентичність запиту, адреси, усі підписи, відмова від слабшого рівня/ZertES,
  вилучення персональних URL із відповіді, остаточна відмова провайдера.
- PostgreSQL-тест: окрема база з усіма міграціями, mock HTTP provider,
  створення, дубль, автоматичне повернення, помилка звіту/повтор,
  відмова/відкликання, невизначене відправлення, стара версія й DEMO.
  Старі seed-рахунки мають некоректні quote-зв’язки для міграції
  `20260819113000`; тест від’єднує ці зв’язки лише у власній базі перед
  виконанням цієї міграції. SQL міграцій не змінено.
  Перевіряється також шифрування збереженого API-ключа, відновлення
  підключення, адміністративні права, блокування заміни облікового запису
  за наявності запитів і знищення збереженого ключа при відключенні.
- Браузерні тести: німецький інтерфейс, перевірка одержувачів, запит із
  невизначеним результатом без дублювання, PDF/протокол, вимкнена інтеграція,
  ширина 390 px і 1440 px. Усі HTTP-виклики в браузерних тестах перехоплені.
  Окремий сценарій перевіряє вікно входу/підключення, німецьке посилання,
  збереження конфігурації, очищення поля ключа та повторне відкриття.

## Пакети документів на підпис (рішення власника 2026-10-01)

Кілька документів **одного пацієнта або одного ліда** підписуються одним
запитом: сервер об'єднує їхні PDF в один файл, Skribble підписує його один
раз, підписанти отримують одне запрошення. Документи різних пацієнтів чи
лідів в один пакет не потрапляють (`signature_package_scope_mismatch`);
документ без пацієнта й ліда підписується лише окремо.

### API

- `GET /signature-packages/candidates?document_id=|patient_id=|lead_id=` — PDF
  цього пацієнта/ліда, які користувач може надіслати (права View, Download,
  Edit): політика підписантів, мінімальний рівень, поля підпису
  (`frame_roles`), розмір, `pending_elsewhere`, `electronic_form_excluded`;
  інформаційні додатки окремо; запропонований комплект
  (`preset_document_ids`), підписанти й мова запрошення, ліміти.
- `POST /signature-packages` — `document_ids[]` (порядок = порядок сторінок,
  перший документ — головний), `signers`, `attachment_ids[]`, `level`
  (`QES`/`AES`), `expires_at`, `message`, `language`. Перевіряються: 1–10
  документів без повторів; права Edit на **кожен** документ
  (`signature_document_access(.., true)`); актуальна версія, PDF, ще не
  підписаний і не в іншому активному запиті (`signature_already_pending` з
  `document_ids`); спільний пацієнт/лід; найсуворіша політика підписантів
  (`SignerPolicy::combine`; внутрішній AML/PEP-документ разом із документами
  для пацієнта — `signature_policy_conflict`); рівень; обов'язкові
  інформаційні додатки; PDF без цифрового підпису
  (`signature_pdf_already_signed`); об'єднаний PDF ≤ 18 МБ
  (`signature_bundle_too_large`).
- Кошторис замовлення їде разом із замовленням (TASK-FB4D, 2026-10-03):
  `preset_document_ids` після `single_order` (як основного документа або як
  члена комплекту ліда) додає найновіший придатний `order_cost_estimate` того
  самого замовлення. Якщо працівник прибрав кошторис із пакета, композер показує
  підказку з кнопкою «Добавить смету». Разом із кошторисом як додаток іде
  калькуляція цього замовлення, якщо вона є.
- Старий `POST /documents/{id}/signature-requests` працює далі. Попередні
  комплекти (договір ліда + замовлення + згоди; для неповнолітнього —
  замовлення + `consent_data_release_child`/`_single`) лишаються пропозицією
  й перевіряються як раніше; створення йде тим самим шляхом, що й
  `POST /signature-packages`.
- `POST /document-signature-requests/{id}/delivered` — працівник один раз
  фіксує, як підписанти отримали підписану копію (`skribble`, `email`,
  `portal`, `in_person`, `post`); лише для завершеного не-тестового запиту.
- Статус запиту (`GET /documents/{id}/signature-requests`) містить
  `members[]` (документ, позиція, сторінки, результат), `attachments[]`,
  `level`, `language`, `expires_at`, `invitation_note`, `signed_at`,
  `delivered_to_signers_at`. Назви документів, до яких глядач не має
  доступу, не показуються. Перегляд, протокол, оновлення, відкликання й
  рішення щодо перевірки авторизуються за будь-яким документом запиту (зміни —
  з правом Edit).

### Канонічний підписаний пакет

Підписаний PDF — юридичний оригінал. Для пакета він зберігається **один раз**
як окремий документ (`ursprung = electronic_signature_package`,
`art = signed_document_package`, категорія `signature`). Розділяти його не
можна: будь-який витяг уже не містив би кваліфікованого підпису. Тому:

- кожен документ пакета лишається своїм рядком, отримує `signed_at`,
  `compliance_kind` і посилання на пакет
  (`document_signature_members.result_document_id`, `page_start`,
  `page_count`; головний документ — `source_page_count` і
  `result_document_id` запиту);
- копій PDF на кожен документ і нових версій документів пакета немає;
- доступ до пакета — найсуворіший серед документів: видимий пацієнтові, лише
  якщо всі документи видимі пацієнтові й немає медичних; медичний, якщо хоч
  один медичний; record-level заборона будь-якого документа переноситься на
  пакет, дозвіл — лише якщо він є для всіх документів;
- окремий документ без пакета, як і раніше, стає новою версією свого джерела.

Об'єднання копіює сторінки, шрифти й ресурси без змін; форми (AcroForm),
структурне дерево й ідентифікація PDF/A документів пакета в об'єднаний файл
не переносяться. PDF із цифровим підписом у пакет не приймається.

### Ефекти завершення

У тій самій транзакції, що й архівування (`effects.rs`), і лише для живого,
перевіреного й актуального підпису (ніколи в режимі DEMO і ніколи в стані
`needs_review`):

- документ отримує `signed_at` і `compliance_kind` (`framework_contract`,
  `dsgvo`, `confidentiality_release`, `enhanced_due_diligence`) через спільну з
  «Отметить подписанным» функцію `record_document_signature_tx`;
- `patients.legal_status`, `consent_records` (доказ: хто з боку пацієнта
  підписав, коли, рівень, ID запиту в GMED і Skribble),
  `leads.compliance_status`;
- рамковий договір (`framework_contracts.status = signed` через
  `orders.contract_id` або останній договір пацієнта/ліда) і статус договору
  пацієнта;
- `orders.signed_patient` / `signed_agency` (+ `*_at`) для `single_order` за
  ролями з доказів Skribble;
- рядок аудиту на кожен документ (`document_signature_effects_applied`).

Прийняття запиту в `needs_review` (`resolve-review`, `accept`) робить
архівований результат робочим підписаним документом і застосовує ті самі
ефекти; відхилення залишає його лише доказом.

### Підпис на папері (TASK-FB4D, 2026-10-03)

Коли документ підписано від руки (або закон виключає електронну форму,
`electronic_form_excluded`), працівник завантажує скан підписаного примірника:
`POST /documents/{id}/paper-signature` (multipart: `file` — PDF/JPG/PNG до
25 МБ, необов'язковий `signed_on` — `YYYY-MM-DD`, не в майбутньому). Код —
`document_signatures/paper.rs`, блок «Подписано на бумаге» у панелі підпису.

- Права ті самі, що й для е-підпису: CEO і Patient Manager з правом
  редагування документа (`signature_document_access`).
- Скан стає **наступною версією** документа (як і результат е-підпису):
  `replaces_document_id`, `version_number + 1`, `ursprung = 'paper_signature'`,
  шаблон і `generated_bindings` зберігаються; попередня версія лишається в
  історії. `signed_at` — дата підпису, `signed_by` — працівник, який вніс скан.
- Наслідки ті самі, що після е-підпису, через спільну
  `effects::apply_business_effects`: договір → `signed`, для `single_order` —
  підписи обох сторін у заказі, згоди й `legal_status`, `consent_records`
  з `source = paper_signature` і SHA-256 скана, статус compliance ліда.
- Відмови: `document_already_signed`, `document_superseded`,
  `document_unavailable`, `informational_document_not_signable`,
  `signature_already_pending` (документ у відкритому е-запиті — спершу
  відкликати), `paper_signature_scan_required` / `_scan_type` /
  `_scan_too_large` / `_date_invalid`, `signature_scan_failed` (антивірус).
- Аудит: `document_paper_signature_recorded` у тій самій транзакції.
- Стан панелі (`GET /documents/{id}/signature-requests`) містить
  `can_sign_on_paper`.
- Один скан покриває один документ. Якщо на папері підписано кілька
  документів одним файлом, скан завантажується до кожного з них.
- Незмінність байтів скана тригером (як для е-підписаних PDF) не вводилася:
  оригінал на папері зберігається в агентстві, скан — його копія.

Старий шлях «Отметить подписанным» (`POST /documents/{id}/mark-signed`, без
файла) лишається для підтвердження посвідчення особи й випадків без скана.

### Інші зміни

- Документ в активному запиті не можна версіонувати, перегенерувати чи
  архівувати: 409 `signature_pending` (локалізоване повідомлення в UI).
- Помилка читання сховища під час архівування — тимчасова: запит лишається
  `pending` з `last_error = signature_storage_read_error` і повторюється, а не
  переходить у `needs_review`.
- `abandon` спершу відкликає запит у Skribble, якщо там є його ID
  (`provider_not_found` — нічого відкликати; інша помилка — 502
  `signature_withdraw_failed`, запит лишається відкритим).
- Сповіщення ініціатору й CEO: підписано / тестовий підпис, потрібна
  перевірка, відхилено, відкликано, строк минув, помилка.
- Аудит у транзакції зі зміною, рядок на кожен документ:
  `document_signature_requested`, `_withdrawn`, `_status_changed`,
  `_abandoned`, `_review_resolved`, `_copy_delivered`;
  `document_signature_archived` — на пакет. Реєстр одержувачів
  (Art. 15/19 DSGVO) враховує всі документи пакета й додатки.
- Розміри: надісланий PDF ≤ 18 МБ, підписаний PDF і протокол ≤ 40 МБ
  (`provider_response_too_large` показується в UI).
- Підписантів з боку пацієнта може бути кілька: усі записані законні
  представники неповнолітнього (зазвичай двоє, § 1629 Abs. 1 BGB), за бажанням —
  неповнолітній пацієнт (роль `minor`, приблизно з 14 років; ніколи не
  обов'язково і ніколи без представника). Поля підпису розподіляються так,
  що два підписанти ніколи не отримують одне поле: перший клієнт — поле
  `client`, далі `guardian_N`; агентство — поле `agency`. Документ без полів
  показує попередження; тоді Skribble сам розміщує підпис.
- Kostenübernahmeerklärung (`cost_coverage_declaration`) підписують платник
  (роль `payer`, власне поле підпису `payer`, підписує першим) і GMED
  (`SignerPolicy::PayerAndAgency`, мінімум QES). У пакеті з договором чи
  згодою потрібні клієнт, платник і GMED (`ClientPayerAndAgency`). Платника
  пропонує замовлення (`invoice_recipient_resolve`, гілка платника); доказом
  згоди пацієнта платник не вважається.
- Сторона договору (`contracting_party`, гілка платника): договір, який
  укладають батьки від свого імені, має поля `guardian_1`/`guardian_2` без поля
  `client`; кожен записаний законний представник підписує своє поле.
- Опитувальник бере й `submission_unknown` (індекс `document_signature_poll`).
- Кнопку підпису бачать лише CEO і Patient Manager (IT Admin налаштовує
  підключення в адмініструванні).

Міграція: `20261002100000_signature_packages.sql`.

## Правові вимоги

Нижче — інженерна реалізація правових вимог, **не юридична консультація**.
Переліки й формулювання має підтвердити юрист.

| Вимога | Норма | Реалізація |

| Рівень підпису за типом документа; QES за замовчуванням | eIDAS Art. 25 Abs. 2, Art. 26; §§ 126a, 126b, 127 BGB | `legal::minimum_level`: QES — договори, замовлення, Kostenübernahme/Schuldbeitritt і все інше; AES дозволено лише для згод і кошторисів (рішення власника). Пакет бере найвищий мінімум (`level < minimum` → 422 `signature_level_too_low`); UI не дає вибрати нижчий рівень. Застосований рівень і мінімум зберігаються в запиті (`level`, `minimum_level`, CHECK у БД), докази Skribble — в `evidence`. |
| Електронна форма виключена | § 766 S. 2 BGB (Bürgschaft), § 623 BGB (Kündigung/Auflösungsvertrag eines Arbeitsverhältnisses), § 630 S. 3 BGB (Arbeitszeugnis) | `legal::electronic_form_excluded` за шаблоном/типом → 422 `electronic_form_excluded` зі `statute`; кандидат позначений у композиторі. ### Потрібна перевірка юриста

- Перелік документів із виключеною електронною формою; чи потрібні інші
  (напр. Verbraucherdarlehen, Schuldbeitritt споживача до кредиту).
- Чи достатньо AES для згод (DSGVO, Schweigepflichtsentbindung) і кошторисів;
  чи потребує нове формулювання платника (Schuldbeitritt) QES.
- Widerrufsbelehrung для договорів на відстані: у шаблонах її немає, власних
  текстів ми не створювали — **відкрите правове питання**.
- Чи достатньо листа Skribble про завершення як «dauerhafter Datenträger» і
  чи потрібне автоматичне відкриття підписаного пакета в порталі пацієнта.
- Строк видалення в Skribble після архівування (рекомендація 30 днів),
  договір AV і зобов'язання за § 203 StGB зі Skribble.
- Підпис неповнолітнього приблизно з 14 років як додаткового (необов'язкового)
  підписанта.

### Звірка зі схемою Sign API v2 (2.2.0), 2026-10-02

Звірено з опублікованою схемою
(`https://api.docs.skribble.com/api/sign-v2/2.2.0/schema.yaml`), без живого
запиту:

- `message` у `POST /signature-requests` — так називається й у схемі.
- `quality`: `QES`, `AES`, `SES`, `AES_MINIMAL`, `DEMO`, `PART11`; `AES` —
  «every signer uses AES».
- `language` підписанта: `en`, `de`, `fr`, `it` — збігається з
  `provider::LANGUAGES`.
- Строк дії: у схемі поле називається `expires_at` (дата, не довше 6 місяців)
  і є «early access» — без увімкненої в Skribble функції запит відхиляється з
  403 `feature-not-enabled`. Тому GMED це поле не надсилає, а строк контролює
  сам: опитувальник відкликає в Skribble відкритий запит, у якого минув
  `expires_at`, і закриває його як `expired` (аудит і сповіщення — як для
  інших завершень). Якщо відкликання не вдалося (останній підписант щойно
  підписав), наступне опитування бере остаточний статус Skribble.
- `DELETE /signature-requests/{id}` за схемою працює лише для запиту зі
  `status_overall=OPEN`. Видалення **завершених** запитів через API схема не
  описує: їх прибирає політика зберігання бізнес-акаунта Skribble
  (`auto_delete_at`, налаштовується в адмініструванні Skribble). Тому
  `signature_provider_deletion_enabled` лишається `false`; строк видалення
  треба задати в акаунті Skribble.

### Перевірити наживо перед використанням на PROD

- Підпис рівня AES гостьовим підписантом без акаунта Skribble: чи проходить
  і чи повертається `signed_quality: "AES"`. На демо-акаунті це перевірити
  неможливо — там якість завжди `DEMO`.
- Рамки підпису на своїх місцях (початок координат — лівий нижній кут).
- Підписаний PDF пакета до 18 МБ (ліміт завантаження 40 МБ).
