# Санкційний скринінг ЄС і політика заблокованих країн

Рішення власника від 2026-10-03. Код: `crates/server/src/sanctions/`,
`crates/server/src/routes/sanctions.rs`, міграція
`migrations/20261004110000_sanctions_screening.sql`, фронтенд
`frontend/src/pages/sanctions/`.

## Коротко

- Скринінг виконуємо **самі**: офіційний консолідований фінансовий санкційний
  список ЄС завантажується на наш сервер, порівняння відбувається локально.
  Жодних платних KYC-сервісів, жодної ліцензії OpenSanctions, жодних даних
  пацієнтів третім сторонам.
- Перевіряються: пацієнт ліда, для неповнолітнього — батьки/опікуни
  (довірені контакти ліда з відношенням parent/guardian), сторонній платник
  і пацієнти.
- Можливий збіг (`open`) і підтверджений збіг (`confirmed`) блокують на сервері
  кваліфікацію і конвертацію ліда, підпис агентства та роботу за
  замовленнями і договорами. **Підтверджений збіг — остаточна зупинка**: його не
  знімає ніхто, навіть CEO. Знімає блокування лише рішення «хибний збіг»
  (`false_positive`), ухвалене, поки збіг відкритий.
- Політика заблокованих країн (налаштування `blocked_countries`, типово `["RU"]`)
  блокує кваліфікацію, конвертацію і підпис агентства; CEO може зняти її для
  одного ліда з обов'язковою причиною.
- Збіг імені — не встановлення особи. Рішення ухвалює CEO.

## Джерело списку (перевірено 2026-10-03)

- Financial Sanctions Files (FSF) Європейської комісії,
  `https://webgate.ec.europa.eu/fsd/fsf`. Список охоплює транспозицію санкцій
  ООН у праві ЄС.
- Посилання на «full sanctions list» публікуються в RSS
  `https://webgate.ec.europa.eu/fsd/fsf/public/rss`; вони містять фіксований
  публічний токен `token=dG9rZW4tMjAxNw` (base64 від `token-2017`). Це не
  персональний обліковий запис: **EU Login для завантаження не потрібен**.
  Сам портал FSF (пошук, підписки) — за EU Login.
- Використовуємо XML версії 1.1:
  `https://webgate.ec.europa.eu/fsd/fsf/public/files/xmlFullSanctionsList_1_1/content?token=dG9rZW4tMjAxNw`.
  Є також XML 1.0, CSV 1.0/1.1 і PDF за тим самим шаблоном.
- Запит `HEAD` 2026-10-03: `200 OK`, `Content-Type: application/xml`,
  ~25,8 МБ, `Last-Modified: Tue, 22 Sep 2026`, ім'я файлу
  `20260922-FULL-1_1(xsd).xml`. Файл сам не завантажували (лише заголовки);
  розбір перевірено на синтетичному файлі того самого формату
  (`crates/server/src/sanctions/testdata/synthetic_fsf_1_1.xml`).
- Формат: корінь `export` (`generationDate`, `globalFileId`), записи
  `sanctionEntity` (`logicalId`, `euReferenceNumber`, `unitedNationId`,
  `designationDate`) з дочірніми `subjectType` (`person` | `enterprise`),
  `nameAlias` (`wholeName`, `firstName`, `middleName`, `lastName`, `gender`,
  `nameLanguage`), `birthdate` (`birthdate`, `year`, `monthOfYear`,
  `dayOfMonth`, `circa`), `citizenship` (`countryIso2Code`, `00` = невідомо),
  `regulation` (`programme`, `numberTitle`, `publicationDate`,
  `entryIntoForceDate`, дочірній `publicationUrl` → EUR-Lex), `remark`.
- **FiSaLis** (`https://www.finanz-sanktionsliste.de/fisalis/`, портал юстиції
  Німеччини) шукає по тому ж списку ЄС, але API не має (HTML-форма POST для
  судів і органів). Ми **ніколи не скрейпимо** FiSaLis і **не передаємо туди
  дані автоматично**; він лише для ручної перевірки CEO (див. нижче).

## Оновлення і версії

- Фонова задача `sanctions::download::spawn_list_scheduler` (запуск у
  `main.rs`): перша перевірка через 2 хвилини після старту, далі щогодини;
  завантаження — якщо останнє успішне старше 20 годин (тобто щодня). Advisory
  lock не дає двом інстансам завантажувати одночасно.
- Обмеження завантаження: лише HTTPS, тайм-аут 300 с, максимум 150 МБ, тип
  XML. Розбір: без DTD/власних entity, ліміти вкладеності й кількості вузлів.
- Кожен успішний імпорт — нова версія (`sanctions_list_versions`: дата списку
  за Europe/Berlin, `globalFileId`, SHA-256, розмір, кількість записів і
  фізичних осіб, хто завантажив). Активна рівно одна версія.
- **Остання справна версія лишається**: помилка мережі, інший формат або
  «підозріло малий» файл (< 50 % записів активної версії) нічого не
  замінюють; помилка записується в `sanctions_list_sync_state`.
- Той самий файл (SHA-256) не створює нову версію.
- Записи (`sanctions_list_entries`) зберігаються для трьох найновіших версій;
  старіші видаляються, рядок версії лишається (на нього посилаються збіги).
- Ручне завантаження (резервний шлях, також без інтернету): CEO в
  «Настройки системы» або на сторінці «Санкционные проверки» → вкладка
  «Список ЕС» завантажує XML 1.1 (або ZIP з ним). Обмеження nginx — 30 МБ:
  поточний XML (~26 МБ) проходить, на майбутнє — ZIP.
- Змінні середовища: `SANCTIONS_LIST_URL` (інше HTTPS-посилання),
  `SANCTIONS_LIST_DOWNLOAD=false` (вимкнути автоматичне завантаження).
- Після нової версії всі відкриті суб'єкти перевіряються знову
  (`rescreen_all`).

## Двигун збігів (`sanctions::normalize`, `sanctions::matching`)

Нормалізація (однаково для списку і наших даних):

1. Регістр, діакритика (NFKD), пунктуація, апострофи, дефіси → токени.
2. Кирилиця (рос., укр., біл.) → латиниця за спрощеною схемою BGN/PCGN.
3. Згортання варіантів транслітерації: `sch`/`tsch`/`zh` (німецька/англійська),
   `kh`→`h`, `x`→`ks`, `w`→`v`, `ou`→`u`, `j`/`y`→`i`, кінцеве `-off`/`-eff`,
   `c`→`k` (крім `ch`), подвоєні літери. Приклади: Ivanov / Iwanow / Ivanoff,
   Yuri / Juri / Iouri / Юрий, Zhukov / Schukow, Aleksandr / Alexandr.
4. Токени інших писемностей (арабська, китайська) відкидаються — список має
   латинські аліаси.

Порівняння:

- Схожість токенів — Jaro-Winkler; токени до 3 літер мають збігатися точно;
  довгі токени з однаковим «скелетом» приголосних (Mohammed / Muhammad)
  отримують `SKELETON_SIMILARITY`; по батькові (`-ovich`, `-ovna`…) не може
  заміщати прізвище (`PATRONYMIC_MISMATCH_CAP`).
- Порядок токенів не важливий (жадібне однозначне зіставлення). Обов'язкові:
  перше ім'я і принаймні один токен прізвища; друге ім'я/по батькові
  необов'язкові з обох боків.
- Оцінка = найслабша схожість обов'язкових токенів, мінус штрафи за зайві
  токени, плюс/мінус дата народження і громадянство.
- Особи порівнюються лише з особами списку, організації (платник без імені) —
  лише з організаціями (без правових форм ООО, GmbH, LLC…).

Пороги (константи в `matching.rs`, покриті тестами):

| Константа | Значення | Зміст |
|---|---|---|
| `TOKEN_MATCH_MIN` | 0,85 | нижче токен не вважається збігом |
| `POSSIBLE_MATCH_THRESHOLD` | 0,90 | від цієї оцінки — «можливий збіг» |
| `SKELETON_SIMILARITY` | 0,92 | однаковий скелет приголосних |
| `PATRONYMIC_MISMATCH_CAP` | 0,80 | по батькові проти прізвища |
| `DOB_EXACT_BOOST` / `DOB_YEAR_BOOST` | +0,08 / +0,04 | дата / рік народження збігаються (для `circa` ±1 рік) |
| `DOB_CONFLICT_PENALTY` | −0,15 | у списку інша дата народження |
| `CITIZENSHIP_MATCH_BOOST` / `_CONFLICT_PENALTY` | +0,03 / −0,02 | спільне / різне громадянство |
| `EXTRA_SUBJECT_TOKEN_PENALTY` | −0,02 | наш токен прізвища, якого немає в списку |
| `EXTRA_LIST_TOKEN_PENALTY` | −0,01 | кожен зайвий токен списку понад перший |

Наслідок: поширене ім'я без дати народження дає «можливий збіг»; суперечлива
дата народження його знімає; схоже, але інше прізвище (Kornienko проти
Korneev) без додаткових ознак — «збігів немає». Синтетичні приклади — у тестах
`matching.rs`.

## Суб'єкти і тригери

| Суб'єкт | Дані | `subject_kind` |
|---|---|---|
| Пацієнт ліда | ім'я, по батькові, прізвище, дата народження, `leads.citizenships` + `registration_country` майстра | `lead_patient` |
| Батьки/опікуни неповнолітнього (вік < 18 за Europe/Berlin) | довірені контакти з відношенням parent/guardian (рос./укр./нім./англ.): ім'я, дата народження; `citizenships`/`country`, якщо колись з'являться в контакті | `lead_guardian` |
| Сторонній платник | `lead_payer_declarations` (`payer_kind = 'third_party'`): ім'я, прізвище (або назва організації), дата народження, громадянство, країна | `lead_payer` |
| Пацієнт (активний або неактивний) | ім'я, прізвище, дата народження, `patients.citizenships` + `nationality` | `patient` |

Проспективний пацієнт ліда окремо не перевіряється — його покриває лід.
Рішення «хибний збіг» щодо пацієнта ліда переходить на пацієнта після
конвертації, поки дані ті самі.

Тригери:

- Кабінет ліда пише в ті самі таблиці, тож окремого виклику не потрібно:
  ім'я, дата народження, громадянства й країна пацієнта (`leads`) і названий
  там платник — третя особа (`lead_payer_declarations`) потрапляють у чергу
  тими самими тригерами (тест `the_cabinet_states_who_pays_and_every_person_goes_to_the_sanctions_screening`).
- Тригери БД на `leads` і `patients` ставлять запис у чергу
  `sanctions_screening_queue`, щойно змінюється перевірюване поле (будь-який
  запис: майстер, публічна анкета, портал пацієнта, імпорт). Фоновий обробник
  (`spawn_screening_worker`, кожні 15 с) перевіряє чергу.
- Живу перевірку в кроці 1 майстра (`POST /sanctions/check`) викликає
  фронтенд з debounce 700 мс, щойно ім'я і прізвище мають по 2 літери; вона
  нічого не зберігає й відповідає лише `clear` / `possible_match` /
  `unavailable` і датою версії списку — без деталей списку. Якщо передано
  `lead_id`, сервер одразу перевіряє збережені дані ліда.
- Новий збіг створюється й при відкритті банера ліда (лід у черзі) і
  безпосередньо перед кожною точкою рішення (кваліфікація, конвертація, підпис
  агентства) — так перевіряється й щойно доданий платник.
- Нова версія списку → повторна перевірка всіх відкритих лідів і
  активних/неактивних пацієнтів.
- `lead_payer_declarations` створює окрема робота (платник). Завантажувач
  читає таблицю лише якщо `to_regclass('public.lead_payer_declarations')` не
  `NULL`, рядок читається як JSON (додаткові колонки не ламають скринінг).
  Тригер черги для цієї таблиці міграція чіпляє, якщо таблиця вже існує;
  інакше функцію `sanctions_enqueue_lead_of_payer()` треба причепити
  міграцією платника (TODO в PR). До того платника перевіряють точки рішення
  і щоденна повторна перевірка.

## Збіги і рішення CEO

- `sanctions_hits`: власник (лід або пацієнт), вид суб'єкта, знімок наших
  даних, знімок запису списку (імена, дати, громадянства, акти з посиланням
  EUR-Lex, номери ЄС/ООН, примітка), версія списку, оцінка й деталі, статус
  `open` | `false_positive` | `confirmed`, `decided_by` / `decided_at`,
  обов'язкова причина (≥ 10 символів).
- **Рішення остаточне**: тригер БД `sanctions_hits_decision_is_final` не дає
  змінити статус чи причину ухваленого збігу. Повторна перевірка лише оновлює
  `still_matches` і `last_screened_at`.
- Відкритий збіг, який після зміни даних більше не знаходиться, лишається
  відкритим (позначка «совпадение больше не находится») — щоб перейменування
  не обходило перевірку; CEO закриває його рішенням.
- «Хибний збіг» діє для конкретних даних: зміна імен, дати народження чи
  громадянства людини або запису у списку (новий аліас, дата) створює новий
  відкритий збіг.
- Аудит у тій самій транзакції: `sanctions_hit_created`,
  `sanctions_hit_decided` (рішення і причина), `sanctions_list_imported`,
  `sanctions_blocked_countries_updated`, `sanctions_country_block_lifted`,
  `sanctions_country_block_lift_revoked`; спроба, заблокована гейтом, —
  `sanctions_gate_blocked`. Імена людей в аудит не пишуться.
- Новий можливий збіг → сповіщення всім активним CEO (`user_notifications`,
  kind `sanctions_possible_match`, без імені людини), посилання на
  `/sanctions`.

Сторінка CEO «Санкционные проверки» (`/sanctions`, пункт меню лише для CEO,
capability `sanctions.review`): відкриті й вирішені збіги, порівняння поруч
(наші дані / запис списку з посиланням на EUR-Lex), кнопки «Ложное
совпадение» / «Подтвердить совпадение» з причиною, «Проверить в FiSaLis»,
вкладка країн (зняття/повернення блокування) і вкладка списку.

## Ручна перевірка у FiSaLis

Кнопка «Проверить в FiSaLis» копіює ім'я людини в буфер обміну і відкриває
`https://www.finanz-sanktionsliste.de/fisalis/` у новій вкладці. Ім'я ніколи не
потрапляє в URL; CEO вставляє його в пошук сам. Якщо копіювання не вдалося,
ім'я виділяється на сторінці для ручного копіювання. Інтерфейс показує
застереження: FiSaLis шукає по тому ж списку ЄС; збіг імені — не
встановлення особи; рішення ухвалює CEO.

## Що блокується (сервер)

Єдине місце — middleware `sanctions::gate::middleware` на захищеному роутері
(після автентифікації, до хендлерів). Відповідь — `409` з кодом
`sanctions_confirmed`, `sanctions_review_pending` або `blocked_country`;
фронтенд показує його мовою користувача.

| Блок | Кваліфікація / конвертація | Підпис агентства | Інша робота за замовленнями/договорами |
|---|---|---|---|
| Підтверджений збіг (назавжди, ніхто не знімає) | так | так | так |
| Відкритий збіг (до рішення CEO) | так | так | так |
| Заблокована країна (CEO знімає для ліда) | так | так | ні |

- Кваліфікація/конвертація: `POST /leads/{id}/qualify` зі статусом `qualified`,
  `/convert`, `/wizard-convert`.
- Підпис агентства: `POST /orders/{id}/commercial-basis` з
  `signed_agency: true`; рамковий договір зі статусом `signed`
  (`POST /framework-contracts`, `/framework-contracts/{id}/status`); пакети й
  запити електронного підпису з підписантом `agency`; паперовий підпис
  (`POST /documents/{id}/paper-signature`) документа замовлення чи договору
  (рамковий договір, разове замовлення, декларація про покриття витрат або
  будь-який документ замовлення). Паперовий підпис інших документів (згоди) —
  «інша робота».
- Інша робота: створення замовлення (`POST /orders`,
  `/patients/{id}/order-intakes`), будь-які зміни замовлення
  (`/orders/{id}/…`), кошториси, рамкові договори, пакети підпису без
  агентства.
- Завжди дозволено (згортання роботи й облік): скасування замовлення
  (`status: cancelled`) або послуги, розірвання рамкового договору, відхилення
  чи видалення кошторису, вхідні рахунки постачальників, борги/нагадування,
  розгрупування.
- Сфера перевірки: лід, пацієнт, у якого лід конвертовано або проспективний
  пацієнт, і навпаки.
- Без завантаженого списку перевірка неможлива: це не блокує роботу, але
  банер і сторінка показують попередження (налаштування за замовчуванням,
  див. «Юридичні питання»).

Банер у майстрі ліда показує стан для всіх ролей із доступом до ліда;
бейдж у списку лідів — «Санкции: проверка», «Санкции», «Страна»,
«Страна: снято».

## Політика заблокованих країн

- Налаштування `blocked_countries` (ISO 3166-1 alpha-2, типово `["RU"]`)
  змінює лише CEO (`PUT /sanctions/settings/blocked-countries`, картка в
  «Настройки системы»); загальна сторінка налаштувань IT-адміна цей ключ не
  змінює.
- Застосовується, якщо **будь-яке** громадянство або країна проживання
  пацієнта, батька/опікуна неповнолітнього чи стороннього платника є в
  списку. Старі значення країн у вигляді назв (Russland, Россия…)
  нормалізуються в коди.
- CEO знімає блокування для одного ліда (або пацієнта без ліда) з обов'язковою
  причиною; зняття покриває країни, заблоковані в цей момент (нова заблокована
  країна блокує знову), може бути повернене з причиною. Банер у майстрі
  показує, хто і коли зняв блокування і чому.

## Юридичні застереження

- Санкції ЄС спрямовані проти конкретних осіб, організацій і секторів. Вони
  **не забороняють** медичні послуги громадянам Росії як таким. Відмова за
  громадянством чи країною проживання — **ділове рішення** власника з ризиком
  дискримінації за AGG § 19 (доступ до послуг, походження) і автоматизованого
  рішення за DSGVO ст. 22. Потрібна перевірка юриста; тому блокування за
  країною завжди можна зняти рішенням людини (CEO) з причиною.
- Правова підстава скринінгу: ст. 6 (1) (c) DSGVO (заборона надавати кошти й
  економічні ресурси особам зі списку, регламенти ЄС, напр. 269/2014,
  833/2014) та (f) (законний інтерес не порушувати санкції).
- Мінімальні дані: лише ім'я, дата народження, громадянство, країна
  проживання; список приходить до нас, наші дані нікуди не йдуть.

## Захист даних і строки зберігання

- Збіги, рішення і зняття блокувань країни зберігаються стільки ж, скільки
  лід або пацієнт: видалення ліда (`purge_lead_and_prospect_in_tx` — правило
  14 днів, правило 180 днів, ручне видалення) і анонімізація пацієнта (ст. 17)
  видаляють їх у тій самій транзакції разом зі сповіщеннями CEO
  (`docs/compliance/04_loeschkonzept.md`).
- Аудит зберігає події без імен людей на свій строк.
- Записи списку — публічні дані; зберігаються три останні версії.

## Відкриті питання (юрист / власник)

1. Відмова за країною (AGG § 19, DSGVO ст. 22): чи прийнятна, формулювання для
   пацієнта, документування рішень CEO.
2. Чи треба зберігати **підтверджений** збіг довше, ніж лід/пацієнта (доказ
   для органів, обов'язок повідомлення, напр. ст. 8 Рег. 269/2014 —
   Bundesbank / Zoll), замість видалення разом із лідом.
3. Поведінка без завантаженого або застарілого списку (зараз — лише
   попередження, без блокування).
4. Рахунки (`invoices`) за вже надані послуги при підтвердженому збігу не
   блокуються (облік, GoBD); надходження коштів від особи зі списку —
   питання до юриста/банку.
5. Пакети підпису, надіслані до збігу, можуть завершитися в Skribble; CEO має
   відкликати їх вручну.
6. Довірені контакти не мають полів громадянства/країни — для батьків/опікунів
   країнова політика поки спирається лише на дані, якщо вони з'являться.
