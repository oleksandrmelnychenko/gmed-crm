# Статуси: терміни, перекладачі, сервіси, задачі (довідник для тестування)

> Довідник описує **поточний код** (сервер `crates/server`, UI `frontend/src`) станом на 2026-09-28. Сервер — джерело правди: UI лише не пропонує переходів, які сервер відхиляє. Ролі й доступи — [RBAC matrix](../../backlog/02_rbac-matrix_ua.md). Дати — Europe/Berlin, формат DD.MM.YYYY. Мітки подано як RU / DE (UI має лише ці мови).
>
> Позначки в колонці «Хто»: **A** — виконавець задачі (`assigned_to`), **R** — автор задачі (`assigned_by`) або вища роль над автором. «Доступ на зміну» терміну — CEO завжди; PM, тимлід, консьєрж — як власник (куратор) терміну або за призначенням на пацієнта; заброньований перекладач — для своїх дій. Кожна перелічена зміна пише рядок аудиту (`audit_log`), якщо не сказано інше.

## 1. Термін (`appointments.status`)

Типи: `medical`, `non_medical`, `internal`. Консьєрж бачить медичний термін як заблокований слот (дата, час, тип, статус; без назви, провайдера, лікаря, нотаток) і нічого в ньому не змінює. Статусу `no_show` немає.

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `planned` | Запланирован | Geplant | Створено, не підтверджено з клінікою/партнером |
| `confirmed` | Подтверждён | Bestätigt | Підтверджено; відкриває звіт перекладача; надсилаються документи підготовки |
| `in_progress` | В процессе | Läuft | Візит триває (ставиться вручну) |
| `completed` | Завершён | Abgeschlossen | Надано (фінальний) |
| `cancelled` | Отменён | Abgesagt | Скасовано (фінальний) |

Та сама мітка й колір — у календарі, списку, картці терміну і вкладці «Терміни» картки пацієнта. Портал пацієнта: Запланировано / Подтверждено / В работе / Завершено / Отменено (Geplant / Bestätigt / In Bearbeitung / Abgeschlossen / Storniert).

| Перехід | Хто | Як |
|---|---|---|
| `planned` → `confirmed` → `in_progress` → `completed` (лише вперед, можна перескочити) | CEO, PM (capability `appointments.status`) з доступом на зміну | Кнопки статусу / «Завершити» |
| будь-який нефінальний → `cancelled` | ті самі | Кнопка «Скасувати» (з підтвердженням) |
| `completed`, `cancelled` → будь-що | ніхто | Сервер 409, тригер БД `enforce_appointment_terminal_status_transition` |
| `planned`/`confirmed` з датою від сьогодні → `cancelled` | автоматично | Скасування замовлення (причина `order_cancelled`) |
| хвіст серії → `cancelled` | автоматично | Зміна правила повторення серії скорочує серію |

Умови завершення (для кожного цільового терміну серії): дата терміну ≤ сьогодні (інакше 422, код `appointment_completion_before_date`) і всі пункти чекліста терміну закриті (422). Для серії (`recurrence_scope` = `single` / `following` / `series`) змінюються лише нефінальні терміни серії. Тимлід і консьєрж статус не змінюють (лише розклад у межах `can_edit`).

Заборонено на фінальному терміні (409): перенесення/редагування, призначення перекладача, відповідь перекладача, додавання й закриття пунктів чекліста. На скасованому також не можна додати нагадування (409); на завершеному — можна (нагадування follow-up).

Видалення: CEO, PM; лише `planned` / `confirmed` / `cancelled` і лише без звіту перекладача зі статусом `pending` або `approved` (409 — «скасуйте замість видалення»). Документи, задачі, рядки білінгу й сервіси консьєржа відв'язуються; нагадування й чекліст видаляються разом із терміном.

**Каскади.**
- `→ confirmed`: автоматичне надсилання документів підготовки провайдера.
- `→ completed`: медичний — позиції замовлення з терміну; немедичний — сервіси консьєржа терміну (крім скасованих) → `completed`, білінг `draft` → `ready`; задача «Billing handoff: …» першому активному користувачеві Billing. Задачі й нагадування терміну лишаються відкритими.
- `→ cancelled` (вручну, серія, замовлення):
  - звіти перекладача `pending` → `rejected` (причина `appointment_cancelled`);
  - пункти чекліста терміну → закриті (ким скасовано);
  - відкриті задачі терміну **разом із підзадачами** → `cancelled` з записом в історії задачі (причина `appointment_cancelled`); пов'язані пункти workflow-чекліста → «не потрібно» (`task_cancelled`);
  - нагадування → закриті;
  - автоматичні сервіси консьєржа (`appointment_bootstrap`) → `cancelled`, білінг `draft` → `waived`;
  - прив'язка перекладача до пацієнта через бронювання закінчується, якщо немає іншого активного бронювання.
- Зміна типу `non_medical` → інший: автоматичні задачі/нагадування/сервіс консьєржа закриваються так само.

Аудит: `update_appointment_status` (з `from` / `to`) на кожен змінений термін, `update_appointment_series_status` для серії. Realtime: `appointment.status_changed`.

Лічильники: «найближчі терміни» на дашбордах — `planned` + `confirmed`. Список «потребує уваги»: минулий нефінальний термін; відкриті пункти чекліста; перекладач без `accepted` за ≤ 2 дні; прострочені нагадування (не для скасованих); відкриті задачі минулого терміну (без видалених); відкрита комунікація минулого нескасованого терміну; звіт перекладача не затверджено.

## 2. Бронювання перекладача (`appointments.interpreter_response`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| (порожньо) | — | — | Перекладача не призначено |
| `pending` | Ожидается | Ausstehend | Призначено, відповіді немає |
| `accepted` | Подтверждено | Bestätigt | Перекладач прийняв |
| `declined` | Отклонено | Abgelehnt | Перекладач відмовився (перекладач лишається в терміні до перепризначення) |
| `discussion_requested` | Нужно уточнение | Klärung erforderlich | Потрібне уточнення (коментар обов'язковий, ≤ 1000 знаків) |

| Перехід | Хто | Як / умови |
|---|---|---|
| → `pending` | CEO, PM, тимлід з доступом на зміну | Призначення іншого перекладача; створення терміну з перекладачем; конвертація запиту; редагування терміну, якщо змінився перекладач або розклад (дата, час, місце, провайдер, лікар). Якщо є звіт `pending`/`approved` і перекладач той самий — відповідь не скидається |
| `pending`/будь-яка → `accepted` / `declined` / `discussion_requested` | заброньований перекладач (роль interpreter або teamlead_interpreter) | Кнопки відповіді; не на завершеному/скасованому терміні (409); `declined` неможливий, якщо його звіт `pending`/`approved` (409) |
| → `accepted` | автоматично | Подання звіту перекладачем |

Консьєрж при перенесенні не змінює бронювання: той самий перекладач або відсутнє поле зберігають бронювання, інший перекладач — 403.

**Побічні дії.** `declined` закінчує прив'язку перекладача до пацієнта через бронювання; `accepted` / уточнення / подання звіту — відновлюють її. Зміна перекладача (кнопка призначення або редагування терміну): звіт попереднього перекладача `pending` → `rejected` (причина `interpreter_changed`), його відкриті нагадування в цьому терміні закриваються (лише роль interpreter), прив'язка закінчується, якщо немає іншого бронювання.

**Сповіщення** (PM і тимліди, що є куратором терміну чи призначені на пацієнта; якщо таких немає — CEO): `discussion_requested` → «Переводчику нужно уточнение / Dolmetscher benötigt eine Klärung»; `declined` → «Переводчик отказался от назначения / Dolmetscher hat den Einsatz abgelehnt» (раз на відмову, з коментарем). Призначення перекладача сповіщення не надсилає.

Аудит: `assign_interpreter`, `interpreter_response` (`from` / `to`).

## 3. Звіт перекладача (`interpreter_reports.approval_status`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `pending` | Ожидает проверки | Prüfung ausstehend | Подано, чекає рішення (чернетки немає) |
| `approved` | Согласовано | Freigegeben | Затверджено; години йдуть у білінг |
| `rejected` | Отклонено | Zurückgewiesen | Повернуто на доопрацювання (сповіщення: «возвращён на доработку») |

| Перехід | Хто | Умови |
|---|---|---|
| (новий) → `pending` | лише роль interpreter, заброньована на термін | Термін `confirmed` / `in_progress` / `completed` (інакше 409 `appointment_report_status_not_open`); дата ≤ сьогодні (422 `appointment_report_before_date`); години 0,25–24 кроком 0,25; один активний (`pending`/`approved`) звіт на термін |
| `pending` → `approved` | CEO, тимлід (командний контекст), PM з доступом до терміну | Ті самі умови статусу й дати; далі синхронізація в позицію замовлення (одразу й планувальником) |
| `pending` → `rejected` | ті самі | Нотатка рецензента; перекладач подає новий звіт (новий рядок) |
| `pending` → `rejected` | автоматично | Скасування терміну (`appointment_cancelled`); зміна перекладача (`interpreter_changed`) |

`approved` і `rejected` фінальні, редагування звіту немає. Термін зі звітом `pending`/`approved` не можна видалити й перенести на майбутню дату (422 `appointment_reported_future_date`).

Сповіщення: подано → PM/тимліди терміну (запасний — CEO); затверджено/повернуто → перекладач. Аудит: `submit_interpreter_report`, `approve_interpreter_report`, `reject_interpreter_report` (для автоматичних — з `reason`, у тій самій транзакції).

## 4. Запит пацієнта на термін (`patient_appointment_requests.status`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `requested` | Запрошено | Angefragt | Пацієнт надіслав запит |
| `approved` | Согласовано (портал: Одобрено) | Freigegeben (портал: Genehmigt) | Погоджено, чекає планування |
| `rejected` | Отклонено | Abgelehnt | Відхилено |
| `converted` | Запланировано | Geplant | Створено термін |
| `cancelled` | Отменено | Abgebrochen (портал: Storniert) | Зарезервовано; код цей статус не ставить |

| Перехід | Хто | Як |
|---|---|---|
| (новий) → `requested` | пацієнт у порталі (також з рекомендації) | Один відкритий (`requested`/`approved`) запит на пацієнта, автора, тип і care path — інакше 409 |
| `requested` → `approved` / `rejected` | CEO, PM з доступом | Черга запитів; перевірка статусу в самому UPDATE (паралельний розгляд — 409) |
| `approved` → `converted` | CEO, PM | «Запланувати»: створює термін (перекладач — `pending`) |

Пацієнт отримує сповіщення про рішення й про створений термін. Черга персоналу показує `requested` і `approved`.

## 5. Комунікація терміну (`appointment_communications.status`)

`planned` Запланировано / Geplant · `sent` Отправлено / Gesendet · `answered` Получен ответ / Beantwortet · `closed` Закрыто / Geschlossen · `cancelled` Отменено / Abgebrochen.

Будь-який перехід (зокрема повторне відкриття) — CEO, PM, тимлід, консьєрж з доступом на зміну; `answered` ставить час відповіді, `closed`/`cancelled` — час закриття. Скасування терміну комунікацію не закриває (вона може бути повідомленням клініці), але список «потребує уваги» ігнорує скасовані терміни.

## 6. Чекліст терміну (`appointment_checklists`)

Фази: `preparation` / `execution` / `followup`. Стан: відкрито — «Открыто / Offen», закрито — «Завершено / Abgeschlossen» (+ час).

| Дія | Хто | Умови |
|---|---|---|
| Додати пункт, закрити пункт | CEO, PM, консьєрж з доступом на зміну (не на заблокованому слоті) | Не на завершеному/скасованому терміні (409); повторного відкриття немає |
| Закрити всі | автоматично | Скасування терміну (ким скасовано); закриття автоматичного workflow консьєржа |

Відкриті пункти блокують завершення терміну. Для немедичних термінів із консьєржем пункти створюються автоматично. Аудит: `complete_appointment_checklist_item`.

## 7. Нагадування терміну (`reminders`)

Стан: `is_completed` = false — «В ожидании / Ausstehend», true — «Завершено / Abgeschlossen». Окремого «скасовано» немає.

| Дія | Хто | Умови |
|---|---|---|
| Створити | CEO, PM з доступом на зміну | Одержувач може відкрити термін і закрити нагадування (перекладач — лише заброньований, не `declined`, термін не скасовано; ніколи Billing, IT Admin, CEO Assistant; інакше 422). Не на скасованому терміні (409) |
| Закрити | CEO, PM — будь-яке; інші (тимлід, перекладач, консьєрж) — лише своє | Доступ на зміну терміну |
| Закрити автоматично | — | Скасування терміну; зміна перекладача (нагадування попереднього перекладача); закриття автоматичного workflow консьєржа |

При завершенні терміну можна одразу запланувати нагадування follow-up (1 тиждень / 1 місяць / 6 місяців). Планувальника доставки нагадувань немає: одержувач бачить їх у терміні й у списку «потребує уваги». Аудит: `complete_reminder`.

## 8. Задачі та події work center (`tasks.status`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `open` | Открыто | Offen | Нова |
| `in_progress` | В работе | In Arbeit | Виконується |
| `on_hold` | На паузе | Pausiert | Призупинено |
| `review` | На проверке | Zur Prüfung | Виконавець передав на перевірку |
| `completed` | Выполнено | Erledigt | Закрито автором або вищою роллю |
| `cancelled` | Отменено | Storniert | Скасовано |

Ті самі мітки — у менеджері задач, картці задачі, списках задач пацієнта, провайдера, терміну й замовлення, у workflow проєкту (пауза — окрема колонка, коли в ній є задачі). Чекліст і хронологія картки пацієнта показують стан задачі загальними мітками картки: В работе / In Bearbeitung, Завершено / Abgeschlossen, інші — як вище. «Відкриті» в лічильниках — усе, крім `completed` і `cancelled` (разом із `on_hold`, `review`).

| З \ в | open | in_progress | on_hold | review | completed | cancelled |
|---|---|---|---|---|---|---|
| open | — | A, R | A, R | — | — | R |
| in_progress | R | — | A, R | A, R | R | R |
| on_hold | R | A, R | — | — | — | R |
| review | — | A, R | — | — | R | R |
| completed | — | R (повторне відкриття) | — | — | — | — |
| cancelled | R (повторне відкриття) | — | — | — | — | — |

Вища роль над автором: CEO — над усіма; CEO Assistant, Billing, PM, Sales — над задачами, створеними консьєржем; тимлід — над задачами перекладачів. Кожна зміна вимагає актуального `expected_updated_at` (409), заборонена для архівної задачі (409), пише запис в історію задачі й сповіщає автора, якщо змінював не він. Легасі-шлях `/tasks/{id}/status` — той самий обробник. Консьєрж і перекладач бачать і змінюють лише свої задачі.

- **Архів**: автор або вища роль; лише `completed` / `cancelled`; відновлення з архіву.
- **Видалення**: м'яке, ставить `cancelled`; не для задачі з підзадачами чи прив'язаної до пункту workflow-чекліста.
- **Підзадачі**: нова — лише під активною (не закритою, не архівною) задачею; зв'язок незмінний. Закриття батьківської не закриває підзадачі автоматично; при завершенні чи архівуванні UI питає і закриває їх окремою дією (`completed` / `cancelled`, історія з причиною `parent_closed`). Завершення підзадачі батьківську не змінює (UI лише пропонує).
- **Автоматичні зміни** (з історією задачі):
  - скасування терміну: відкриті задачі терміну та їх підзадачі → `cancelled` (`appointment_cancelled`); закриття автоматичного workflow консьєржа — задачі «Coordinate concierge service» / «Collect concierge receipts» (`concierge_workflow_closed`);
  - закриття пункту workflow-чекліста: пов'язана відкрита задача → `completed` у тій самій транзакції (`checklist_item_completed`, сповіщення автора); скасовану чи архівну задачу не змінює;
  - «не потрібно» / етап пройдено на пункті чекліста → задача `cancelled`; повторне відкриття пункту → задача `open`;
  - бронювання провайдера для сервісу: `open` → `in_progress` (`provider_booked`); `on_hold`/`review` лишаються; закрита чи архівна задача, або задача з підзадачами — 409.
- **Автоматично створені задачі**: немедичний термін з консьєржем — «Coordinate concierge service: …», «Collect concierge receipts: …»; завершення немедичного терміну — «Billing handoff: …»; пункти workflow-чекліста; задачі сервісів консьєржа.

Чекліст усередині задачі (`is_completed`) на статус задачі не впливає.

## 9. Передача в білінг

Немедичний термін при завершенні створює задачу «Billing handoff: <назва>» для першого активного користувача Billing (одна на термін), термін — одразу. Медичний термін при завершенні створює позиції замовлення; задачі Billing не створює. Billing ніколи не отримує нагадувань до терміну.

## 12. Сервіс консьєржа (`concierge_services`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `planned` | Запланировано | Geplant | Запит, ще не заброньовано |
| `booked` | Забронировано | Gebucht | Бронювання запитано в партнера |
| `confirmed` | Подтверждено | Bestätigt | Партнер підтвердив (потрібні номер, контакт або нотатка) |
| `in_service` | Выполняется | In Durchführung | Надається |
| `completed` | Завершено | Abgeschlossen | Надано |
| `cancelled` | Отменено | Storniert | Скасовано |

| Перехід | Хто | Як |
|---|---|---|
| `planned` → `booked` / `confirmed`, `booked` → `confirmed` | CEO, консьєрж (через задачу сервісу — також PM) | Лише ендпоінт бронювання провайдера (звичайне збереження з `booked`/`confirmed` — 409, якщо статус змінюється) |
| `planned` / `confirmed` → `in_service`; `in_service` → `completed` | CEO, PM, консьєрж з доступом до сервісу | Форма сервісу |
| `planned` / `booked` / `confirmed` / `in_service` → `cancelled` | ті самі; пацієнт — свій запит з порталу (`planned`, без бронювання) | Форма сервісу / портал |
| `completed` → `in_service`, `cancelled` → `planned` | CEO, PM | Повторне відкриття |
| нефінальний → `completed` | автоматично | Завершення немедичного терміну (скасовані сервіси не змінюються) |
| автоматичний сервіс терміну → `cancelled` / назад `planned` | автоматично | Скасування терміну / зміна типу на немедичний |

UI пропонує лише дозволені переходи (форма сервісу, секція консьєржа в терміні).

**Білінг сервісу (`billing_status`)**: `draft` Черновик / Entwurf · `ready` Готово / Bereit · `billed` Выставлен счёт / In Rechnung gestellt · `settled` Оплачено / Beglichen · `waived` Списано / Erlassen. Встановлюють CEO, PM, Billing (консьєрж — ні) без обмежень переходів. Автоматично: завершення сервісу чи терміну — `draft` → `ready` (повторно надісланий незмінний `draft` цьому не заважає); автоматичне скасування — `draft` → `waived`. Видалити можна лише сервіс з білінгом `draft`, без витрат і без історії ключів чи контактів з партнером (409 — скасуйте).

**Ключі (`key_status`)**: `received` Ключ получен / Schlüssel erhalten · `stored` Ключ на хранении / Schlüssel verwahrt · `handed_over` Ключ передан / Schlüssel übergeben · `returned` Ключ возвращён / Schlüssel zurückgegeben. Переходи: (немає) → received; received → stored / handed_over / returned; stored → handed_over / returned; handed_over → returned; returned → received. Хто: CEO, PM, консьєрж (консьєрж — лише себе відповідальним). Журнал подій лише доповнюється.

**Контакти з партнером (`outcome`)**: `no_answer` Не ответили / Nicht erreicht · `reached` Связались / Erreicht · `quote_requested` Цена запрошена / Angebot angefragt · `quote_received` Цена получена / Angebot erhalten · `follow_up_needed` Нужен повторный контакт / Rückmeldung erforderlich · `booking_requested` Бронирование запрошено / Buchung angefragt · `booking_confirmed` Бронирование подтверждено / Buchung bestätigt · `declined` Отказ / Abgelehnt · `cancelled` Отменено / Storniert. Два `booking_*` пише лише бронювання провайдера. Журнал лише доповнюється.

Бронювання, ключі, контакти й ціни через задачу сервісу змінюють лише ролі з `services.edit` (CEO, PM, консьєрж); CEO Assistant — лише перегляд. Аудит: зміни сервісу, бронювання, ключі, контакти, `mark_concierge_service_ready_for_billing` (завершення терміну).

## 13. Рекомендації пацієнту (`patient_recommendations`)

| Поле | Значення (RU / DE) |
|---|---|
| `status` (портал, сторінка персоналу) | `active` Активно / Aktiv · `completed` Завершено / Abgeschlossen · `declined` Отклонено / Abgelehnt · `cancelled` Отменено / Storniert · `superseded` Заменено / Ersetzt |
| `lifecycle_status` (клінічна вкладка) | `aktiv` Активна / Aktiv · `erfolg` Выполнена / Erfolg · `nicht_erfolgt` Не выполнена / Nicht erfolgt · `unbekannt` Неизвестно / Unbekannt |
| `patient_decision` | `schedule` · `already_done` · `need_consultation` · `declined` |

- Персонал (CEO, PM з призначенням) змінює `status` і `lifecycle_status` довільно; поля незалежні.
- Рішення пацієнта: `already_done` → `completed`, `declined` → `declined`, інші → `active`; `schedule` створює запит на термін (дубль — 409).
- Нове сповіщення пацієнту — лише для рекомендації, видимої в порталі.
- Нагадування (планувальник): лише `status = active` і `lifecycle_status = aktiv`, коли настала дата `reminder_at` або `valid_to − reminder_lead_days` (Europe/Berlin); кожне надсилається один раз (рядок позначається в тому самому запиті). Автор і призначений персонал — завжди, пацієнт — лише для видимої в порталі.

## 14. Етапи follow-up терміну (`appointments.followup_milestone`)

`post_1w`, `post_1m`, `post_6m`, `doctor`, `package_end` або порожньо — мітка терміну-контролю, не статус. Статус етапу зберігається в кроках follow-up замовлення (§11) і змінюється вручну. При завершенні терміну можна запланувати нагадування «1 тиждень / 1 місяць / 6 місяців».
