# Статуси: терміни, перекладачі, сервіси, задачі (довідник для тестування)

> Довідник описує **поточний код** (сервер `crates/server`, UI `frontend/src`) станом на 2026-09-28 (доповнено рішенням 2026-09-29 про скасування з діючим білінгом). Сервер — джерело правди: UI лише не пропонує переходів, які сервер відхиляє. Ролі й доступи — [RBAC matrix](../../backlog/02_rbac-matrix_ua.md). Дати — Europe/Berlin, формат DD.MM.YYYY. Мітки подано як RU / DE (UI має лише ці мови).
>
> Позначки в колонці «Хто»: **A** — виконавець задачі (`assigned_to`), **R** — автор задачі (`assigned_by`) або вища роль над автором. «Доступ на зміну» терміну — CEO завжди; PM, тимлід, консьєрж — як власник (куратор) терміну або за призначенням на пацієнта; заброньований перекладач — для своїх дій. Кожна перелічена зміна пише рядок аудиту (`audit_log`), якщо не сказано інше.

## 1. Термін (`appointments.status`)

Типи: `medical`, `non_medical`, `internal`. Консьєрж бачить медичний термін як заблокований слот (дата, час, тип, статус; без назви, провайдера, лікаря, нотаток) і нічого в ньому не змінює. Статусу `no_show` немає.

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `planned` | Запланирован | Geplant | Створено, не підтверджено з клінікою/партнером |
| `confirmed` | Подтверждён | Bestätigt | Підтверджено; відкриває звіт перекладача; надсилаються документи підготовки |
| `in_progress` | В процессе | Läuft | Візит триває (ставиться вручну) |
| `completed` | Завершён | Abgeschlossen | Надано (фінальний) |
| `cancelled` | Отменён | Abgesagt | Скасовано (фінальний) |

Та сама мітка й колір — у календарі, списку, картці терміну і вкладці «Терміни» картки пацієнта. Портал пацієнта: Запланировано / Подтверждено / В работе / Завершено / Отменено (Geplant / Bestätigt / In Bearbeitung / Abgeschlossen / Storniert).

| Перехід | Хто | Як |
|---|---|---|
| `planned` → `confirmed` → `in_progress` → `completed` (лише вперед, можна перескочити) | CEO, PM (capability `appointments.status`) з доступом на зміну | Кнопки статусу / «Завершити» |
| будь-який нефінальний → `cancelled` | ті самі | Кнопка «Скасувати» (з підтвердженням). Термін зі **затвердженим** звітом перекладача, білінг якого діє (позиція замовлення не сторнована або ще не створена), скасувати не можна: 409 `appointment_cancel_billed_report` з назвою звіту, позиції й замовлення; UI показує це повідомлення (рішення 2026-09-28, Q8). **Скасування зі сторно білінгу (рішення 2026-09-29):** з `reverse_billing: true` і `billing_reversal_reason` (3–1000 символів, інакше 422) у тій самій транзакції позиція кожного затвердженого звіту скасовується (не виставлена — просто `cancelled`; у випущеному рахунку — кредит-нота, лише CEO; PM отримує 403 `order_service_reversal_requires_finance`; у чернетці рахунку — 409), звіт лишається `approved` і отримує `billing_reversed_at/by/reason` (аудит `reverse_interpreter_report_billing`), потім термін скасовується. Без прапорця — 409, як і раніше, але відповідь містить `reverse_billing_available` і `reversal` (що буде: сума кредит-ноти, блокування); UI відкриває діалог підтвердження з причиною замість помилки |
| `completed`, `cancelled` → будь-що | ніхто | Сервер 409, тригер БД `enforce_appointment_terminal_status_transition` |
| `planned`/`confirmed` з датою від сьогодні → `cancelled` | автоматично | Скасування замовлення (причина `order_cancelled`); термін зі затвердженим і не сторнованим звітом перекладача лишається (він відбувся) |
| хвіст серії → `cancelled` | автоматично | Зміна правила повторення серії скорочує серію |

Умови завершення (для кожного цільового терміну серії): дата терміну ≤ сьогодні (інакше 422, код `appointment_completion_before_date`) і всі пункти чекліста терміну закриті (422). Для серії (`recurrence_scope` = `single` / `following` / `series`) змінюються лише нефінальні терміни серії. Тимлід і консьєрж статус не змінюють (лише розклад у межах `can_edit`).

Заборонено на фінальному терміні (409): перенесення/редагування, призначення перекладача, відповідь перекладача, додавання й закриття пунктів чекліста. На скасованому також не можна додати нагадування (409); на завершеному — можна (нагадування follow-up).

Видалення: CEO, PM; лише `planned` / `confirmed` / `cancelled` і лише без звіту перекладача зі статусом `pending` або `approved` (409 — «скасуйте замість видалення»). Документи, задачі, рядки білінгу й сервіси консьєржа відв'язуються; нагадування й чекліст видаляються разом із терміном.

**Каскади.**
- `→ confirmed`: автоматичне надсилання документів підготовки провайдера.
- `→ completed`: медичний — позиції замовлення з терміну; немедичний — сервіси консьєржа терміну (крім скасованих) → `completed` через свою задачу (системний крок `appointment_completed`), білінг `draft` → `ready`; задача «Billing handoff: …» першому активному користувачеві Billing. Задачі й нагадування терміну лишаються відкритими.
- `→ cancelled` (вручну, серія, замовлення):
  - звіти перекладача `pending` → `rejected` (причина `appointment_cancelled`);
  - пункти чекліста терміну → «закрито без виконання» (`closed_reason = appointment_cancelled`, хто закрив — у `completed_by`);
  - відкриті задачі терміну **разом із підзадачами** → `cancelled` з записом в історії задачі (причина `appointment_cancelled`); пов'язані пункти workflow-чекліста → «не потрібно» (`task_cancelled`);
    задачі сервісів консьєржа цей каскад не чіпає — вони йдуть за правилами сервісу (§12);
  - нагадування → «закрито без виконання» (`closed_reason = appointment_cancelled`);
  - заброньований (не `declined`) перекладач отримує сповіщення про скасування;
  - автоматичні сервіси консьєржа (`appointment_bootstrap`) без бронювання в партнера → `cancelled` через свою задачу, білінг → `waived`; сервіси персоналу й порталу лишаються; бронювання в партнера не скасовується, а позначається для рішення (§12, Q4);
  - прив'язка перекладача до пацієнта через бронювання закінчується, якщо немає іншого активного бронювання.
- Зміна типу `non_medical` → інший: автоматичні задачі/нагадування/сервіс консьєржа закриваються так само.

Аудит: `update_appointment_status` (з `from` / `to`) на кожен змінений термін, `update_appointment_series_status` для серії. Realtime: `appointment.status_changed`.

Лічильники: «найближчі терміни» на дашбордах — `planned` + `confirmed`. Список «потребує уваги»: минулий нефінальний термін; відкриті пункти чекліста; перекладач без `accepted` за ≤ 2 дні; прострочені нагадування (не для скасованих); відкриті задачі минулого терміну (без видалених); відкрита комунікація минулого нескасованого терміну; звіт перекладача не затверджено.

## 2. Бронювання перекладача (`appointments.interpreter_response`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| (порожньо) | — | — | Перекладача не призначено |
| `pending` | Ожидается | Ausstehend | Призначено, відповіді немає |
| `accepted` | Подтверждено | Bestätigt | Перекладач прийняв |
| `declined` | Отклонено | Abgelehnt | Перекладач відмовився (лишається в терміні до перепризначення, але слот перекладача не блокує і в лічильниках заброньованого не рахується) |
| `discussion_requested` | Нужно уточнение | Klärung erforderlich | Потрібне уточнення (коментар обов'язковий, ≤ 1000 знаків) |

| Перехід | Хто | Як / умови |
|---|---|---|
| → `pending` | CEO, PM, тимлід з доступом на зміну | Призначення іншого перекладача **або повторне призначення того самого, який відмовився** (коментар відмови очищується); створення терміну з перекладачем; конвертація запиту; редагування терміну, якщо змінився перекладач або розклад (дата, час, місце, провайдер, лікар). Якщо є звіт `pending`/`approved` і перекладач той самий — відповідь не скидається; повторне призначення перекладача з `accepted`/`discussion_requested` відповідь не змінює |
| `pending`/будь-яка → `accepted` / `declined` / `discussion_requested` | заброньований перекладач (роль interpreter або teamlead_interpreter) | Кнопки відповіді; не на завершеному/скасованому терміні (409); `declined` неможливий, якщо його звіт `pending`/`approved` (409); повернення з `declined`, коли слот перекладача вже зайнято іншим бронюванням, — 409 |
| → `accepted` | автоматично | Подання звіту перекладачем |

Консьєрж при перенесенні не змінює бронювання: той самий перекладач або відсутнє поле зберігають бронювання, інший перекладач — 403.

**Відмова звільняє слот** (рішення 2026-09-28, Q7): бронювання `declined` не враховується у перевірці накладок (сервер, обмеження БД `appointments_interpreter_schedule_excl`, перегляд конфліктів) і в лічильниках (KPI тимліда, операційний профіль перекладача, історії перекладач↔пацієнт, підказки перекладачів).

**Побічні дії.** `declined` закінчує прив'язку перекладача до пацієнта через бронювання; `accepted` / уточнення / подання звіту — відновлюють її. Зміна перекладача (кнопка призначення або редагування терміну): звіт попереднього перекладача `pending` → `rejected` (причина `interpreter_changed`), його відкриті нагадування в цьому терміні закриваються (лише роль interpreter), прив'язка закінчується, якщо немає іншого бронювання.

**Сповіщення** (PM і тимліди, що є куратором терміну чи призначені на пацієнта; якщо таких немає — CEO): `discussion_requested` → «Переводчику нужно уточнение / Dolmetscher benötigt eine Klärung»; `declined` → «Переводчик отказался от назначения / Dolmetscher hat den Einsatz abgelehnt» (раз на відмову, з коментарем).

**Сповіщення самому перекладачу** (рішення 2026-09-28, Q2; не про власну дію; серія — одне сповіщення з кількістю термінів):
- `interpreter_booking_assigned` — «Вас назначили переводчиком / Sie wurden als Dolmetscher gebucht»: призначення, повторне призначення після відмови, створення терміну/серії чи конвертація запиту з перекладачем, нові терміни серії;
- `interpreter_booking_removed` — «Вас сняли с назначения / Ihre Dolmetscherbuchung wurde aufgehoben»: призначено іншого або прибрано перекладача (крім того, хто сам відмовився); без посилання на термін;
- `interpreter_appointment_cancelled` — скасування (вручну, хвіст серії, замовлення) чи видалення терміну;
- `interpreter_appointment_rescheduled` — змінились дата, час, місце, провайдер чи лікар (з попереднім слотом; якщо відповідь скинуто — прохання підтвердити знову);
- `interpreter_report_auto_rejected` — звіт відхилено автоматично (з причиною).

Аудит: `assign_interpreter`, `interpreter_response` (`from` / `to`).

## 3. Звіт перекладача (`interpreter_reports.approval_status`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `pending` | Ожидает проверки | Prüfung ausstehend | Подано, чекає рішення (чернетки немає) |
| `approved` | Согласовано | Freigegeben | Затверджено; години йдуть у білінг |
| `rejected` | Отклонено | Zurückgewiesen | Повернуто на доопрацювання (сповіщення: «возвращён на доработку») |

| Перехід | Хто | Умови |
|---|---|---|
| (новий) → `pending` | заброньований перекладач — роль interpreter або teamlead_interpreter (рішення 2026-09-28, Q6) | Термін `confirmed` / `in_progress` / `completed` (інакше 409 `appointment_report_status_not_open`); дата ≤ сьогодні (422 `appointment_report_before_date`); години 0,25–24 кроком 0,25; один активний (`pending`/`approved`) звіт на термін |
| `pending` → `approved` | CEO, тимлід (командний контекст), PM з доступом до терміну; **не автор звіту** (свій звіт тимліда перевіряє інший тимлід, PM або CEO — інакше 403 `interpreter_report_self_review`, UI кнопок не показує) | Ті самі умови статусу й дати; далі синхронізація в позицію замовлення (одразу й планувальником) |
| `pending` → `rejected` | ті самі | Нотатка рецензента; перекладач подає новий звіт (новий рядок) |
| `pending` → `rejected` | автоматично | Скасування терміну (`appointment_cancelled`); зміна перекладача (`interpreter_changed`) |

`approved` і `rejected` фінальні, редагування звіту немає. Сторно білінгу затвердженого звіту (разом зі скасуванням терміну, §1, рішення 2026-09-29) не змінює статус звіту: він лишається записом годин, а `billing_reversed_at` означає, що планувальник білінгу його більше не виставляє, навіть якщо позиції ще не було. Термін зі звітом `pending`/`approved` не можна видалити й перенести на майбутню дату (422 `appointment_reported_future_date`).

Сповіщення: подано → PM/тимліди терміну, крім автора (запасний — CEO); затверджено/повернуто → перекладач; автоматично відхилено → перекладач (`interpreter_report_auto_rejected`). Аудит: `submit_interpreter_report`, `approve_interpreter_report`, `reject_interpreter_report` (для автоматичних — з `reason`, у тій самій транзакції).

## 4. Запит пацієнта на термін (`patient_appointment_requests.status`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `requested` | Запрошено | Angefragt | Пацієнт надіслав запит |
| `approved` | Согласовано (портал: Одобрено) | Freigegeben (портал: Genehmigt) | Погоджено, чекає планування |
| `rejected` | Отклонено | Abgelehnt | Відхилено |
| `converted` | Запланировано | Geplant | Створено термін |
| `cancelled` | Отменено | Abgebrochen (портал: Storniert) | Пацієнт відкликав або персонал скасував (зберігаються хто, коли, причина) |

| Перехід | Хто | Як |
|---|---|---|
| (новий) → `requested` | пацієнт у порталі (також з рекомендації) | Один відкритий (`requested`/`approved`) запит на пацієнта, автора, тип і care path — інакше 409 |
| `requested` → `approved` / `rejected` | CEO, PM з доступом | Черга запитів; перевірка статусу в самому UPDATE (паралельний розгляд — 409) |
| `approved` → `converted` | CEO, PM | «Запланувати»: створює термін (перекладач — `pending`) |
| `requested`/`approved` → `cancelled` | пацієнт (свій запит) | Портал «Отозвать запрос / Anfrage zurückziehen» (з підтвердженням; причина необов'язкова); сповіщення PM/CEO пацієнта (`appointment_request_withdrawn`); аудит `withdraw_appointment_request` |
| `requested`/`approved` → `cancelled` | CEO, PM з доступом | Черга «Отменить запрос» з обов'язковою причиною (3–1000 знаків); сповіщення пацієнту; аудит `cancel_appointment_request` |

Перевірка статусу — у самому UPDATE (паралельна дія — 409). Пацієнт отримує сповіщення про рішення, створений термін і скасування. Черга персоналу показує `requested` і `approved` (рішення 2026-09-28, Q5).

## 5. Комунікація терміну (`appointment_communications.status`)

`planned` Запланировано / Geplant · `sent` Отправлено / Gesendet · `answered` Получен ответ / Beantwortet · `closed` Закрыто / Geschlossen · `cancelled` Отменено / Abgebrochen.

Будь-який перехід (зокрема повторне відкриття) — CEO, PM, тимлід, консьєрж з доступом на зміну; `answered` ставить час відповіді, `closed`/`cancelled` — час закриття. Скасування терміну комунікацію не закриває (вона може бути повідомленням клініці), але список «потребує уваги» ігнорує скасовані терміни.

## 6. Чекліст терміну (`appointment_checklists`)

Фази: `preparation` / `execution` / `followup`. Стан: відкрито — «Открыто / Offen», закрито — «Завершено / Abgeschlossen» (+ час), **закрито без виконання** — «Закрыто без выполнения / Ohne Erledigung geschlossen» з причиною (`closed_reason`: `appointment_cancelled`, `concierge_workflow_closed`), сірим, не рахується як виконане (рішення 2026-09-28, Q13).

| Дія | Хто | Умови |
|---|---|---|
| Додати пункт, закрити пункт | CEO, PM, консьєрж з доступом на зміну (не на заблокованому слоті) | Не на завершеному/скасованому терміні (409); повторного відкриття немає |
| Закрити всі без виконання | автоматично | Скасування терміну; закриття автоматичного workflow консьєржа |

Відкриті пункти блокують завершення терміну. Для немедичних термінів із консьєржем пункти створюються автоматично. Аудит: `complete_appointment_checklist_item`.

## 7. Нагадування терміну (`reminders`)

Стан: `is_completed` = false — «В ожидании / Ausstehend», true — «Завершено / Abgeschlossen»; true з `closed_reason` (`appointment_cancelled`, `interpreter_unbooked`, `concierge_workflow_closed`) — «Закрыто без выполнения / Ohne Erledigung geschlossen» (Q13). `sent_at` — коли нагадування доставлено.

| Дія | Хто | Умови |
|---|---|---|
| Створити | CEO, PM з доступом на зміну | Одержувач може відкрити термін і закрити нагадування (перекладач — лише заброньований, не `declined`, термін не скасовано; ніколи Billing, IT Admin, CEO Assistant; інакше 422). Не на скасованому терміні (409) |
| Закрити | CEO, PM — будь-яке; інші (тимлід, перекладач, консьєрж) — лише своє | Доступ на зміну терміну |
| Закрити автоматично (без виконання) | — | Скасування терміну; зміна перекладача (нагадування попереднього перекладача); закриття автоматичного workflow консьєржа |
| Доставити | автоматично (планувальник, щохвилини) | Настав момент `remind_at` (введений як час Europe/Berlin), нагадування відкрите, не доставлене, термін не скасовано, одержувач активний і досі може працювати з терміном (ті самі правила, що при створенні) → сповіщення `appointment_reminder` («Напоминание по приёму / Terminerinnerung»), `sent_at`, аудит `deliver_appointment_reminder` в одній транзакції; рівно один раз (Q12) |

При завершенні терміну можна одразу запланувати нагадування follow-up (1 тиждень / 1 місяць / 6 місяців). Доставлене нагадування лишається відкритим, доки його не закриють; видно також у терміні й у списку «потребує уваги». Аудит: `complete_reminder`, `deliver_appointment_reminder`.

## 8. Задачі та події work center (`tasks.status`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `open` | Открыто | Offen | Нова |
| `in_progress` | В работе | In Arbeit | Виконується |
| `on_hold` | На паузе | Pausiert | Призупинено |
| `review` | На проверке | Zur Prüfung | Виконавець передав на перевірку |
| `completed` | Выполнено | Erledigt | Закрито автором або вищою роллю |
| `cancelled` | Отменено | Storniert | Скасовано |

Ті самі мітки — у менеджері задач, картці задачі, списках задач пацієнта, провайдера, терміну й замовлення, у workflow проєкту (пауза — окрема колонка, коли в ній є задачі). Чекліст і хронологія картки пацієнта показують стан задачі загальними мітками картки: В работе / In Bearbeitung, Завершено / Abgeschlossen, інші — як вище. «Відкриті» в лічильниках — усе, крім `completed` і `cancelled` (разом із `on_hold`, `review`).

| З \ в | open | in_progress | on_hold | review | completed | cancelled |
|---|---|---|---|---|---|---|
| open | — | A, R | A, R | — | — | R |
| in_progress | R | — | A, R | A, R | R | R |
| on_hold | R | A, R | — | — | — | R |
| review | — | A, R | — | — | R | R |
| completed | — | R (повторне відкриття) | — | — | — | — |
| cancelled | R (повторне відкриття) | — | — | — | — | — |

Вища роль над автором: CEO — над усіма; Billing, PM, Sales — над задачами, створеними консьєржем; тимлід — над задачами перекладачів. CEO Assistant — лише читання: бачить задачі консьєржа, але редагує, закриває й архівує тільки створені ним самим (сервер і UI; рішення 2026-09-28, Q14). Коли автор (чи вища роль) приймає рішення по задачі в `review` (→ `completed`, → `in_progress`/`open`, → `cancelled`), виконавець отримує сповіщення `operational_task_review_decision` («Задача принята / возвращена на доработку / отменена после проверки»; Q9). Кожна зміна вимагає актуального `expected_updated_at` (409), заборонена для архівної задачі (409), пише запис в історію задачі й сповіщає автора, якщо змінював не він. Легасі-шлях `/tasks/{id}/status` — той самий обробник. Консьєрж і перекладач бачать і змінюють лише свої задачі.

- **Архів**: автор або вища роль; лише `completed` / `cancelled`; відновлення з архіву.
- **Видалення**: м'яке, ставить `cancelled`; не для задачі з підзадачами чи прив'язаної до пункту workflow-чекліста.
- **Підзадачі**: нова — лише під активною (не закритою, не архівною) задачею; зв'язок незмінний. Закриття батьківської не закриває підзадачі автоматично; при завершенні, **скасуванні** чи архівуванні UI питає і закриває їх окремою дією (`completed` / `cancelled`, історія з причиною `parent_closed`). Дія застосовує правило перевірки до кожної підзадачі: закриваються лише ті, де діючий — автор або вища роль; решта лишається відкритою й повертається як `skipped` (UI про це повідомляє) (Q9). Завершення підзадачі батьківську не змінює (UI лише пропонує).
- **Автоматичні зміни** (з історією задачі):
  - скасування терміну: відкриті задачі терміну та їх підзадачі → `cancelled` (`appointment_cancelled`); закриття автоматичного workflow консьєржа — задачі «Coordinate concierge service» / «Collect concierge receipts» (`concierge_workflow_closed`);
  - закриття пункту workflow-чекліста: пов'язана відкрита задача → `completed` у тій самій транзакції (`checklist_item_completed`, сповіщення автора); скасовану чи архівну задачу не змінює;
  - «не потрібно» / етап пройдено на пункті чекліста → задача `cancelled`; повторне відкриття пункту → задача `open`;
  - бронювання провайдера для сервісу: `open` → `in_progress` (`provider_booked`); `on_hold`/`review` лишаються; закрита чи архівна задача, або задача з підзадачами — 409.
  - задача сервісу консьєржа: кожна зміна статусу в тій самій транзакції виводить статус і білінг сервісу (§12, Q1); скасування задачі виставленого (`billed`/`settled`) сервісу — 409 `concierge_service_billed`; зміна статусу на поверхнях сервісу — крок задачі з історією (`service_status_changed`), сповіщення автору.
- **Автоматично створені задачі**: немедичний термін з консьєржем — «Coordinate concierge service: …», «Collect concierge receipts: …»; завершення немедичного терміну — «Billing handoff: …»; пункти workflow-чекліста; задачі сервісів консьєржа.

Чекліст усередині задачі (`is_completed`) на статус задачі не впливає.

## 9. Передача в білінг

Немедичний термін при завершенні створює задачу «Billing handoff: <назва>» для першого активного користувача Billing (одна на термін), термін — одразу. Медичний термін при завершенні створює позиції замовлення (організація лікування з каталогу агенції), а затверджений звіт перекладача — позицію годин перекладача; задачі Billing медичний термін не створює: Billing бачить медичні візити через ці позиції замовлення в черзі білінгу (рішення 2026-09-28, Q16 — документацію виправлено, код без змін). Billing ніколи не отримує нагадувань до терміну.

## 12. Сервіс консьєржа (`concierge_services`)

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `planned` | Запланировано | Geplant | Запит, ще не заброньовано |
| `booked` | Забронировано | Gebucht | Бронювання запитано в партнера |
| `confirmed` | Подтверждено | Bestätigt | Партнер підтвердив (потрібні номер, контакт або нотатка) |
| `in_service` | Выполняется | In Durchführung | Надається |
| `completed` | Завершено | Abgeschlossen | Надано |
| `cancelled` | Отменено | Storniert | Скасовано |

**Задача — єдине джерело правди (рішення власника 2026-09-28, Q1).** Статус сервісу й готовність до білінгу виводяться з його задачі (канонічна задача — найстаріша невидалена задача work center з `concierge_service_id`, спершу операційна) у тій самій транзакції, хоч би звідки змінилась задача (work center, чекліст, каскад терміну, закриття підзадач, поверхні сервісу). Сервіс без задачі отримує її при першій дії (бронювання, ключ, контакт, витрата, зміна статусу); лише застарілий сервіс у медичному контексті (`task_eligible = false`) лишається без задачі й живе за переходами сервісу. Суперечливий статус сервісу БД відхиляє (тригер `guard_concierge_service_state`). Кожна виведена зміна пише `derive_concierge_service_from_task` в аудит у тій самій транзакції (з користувачем дії, якщо його назвав API).

| Статус задачі | Статус сервісу | Білінг |
|---|---|---|
| `completed` | `completed` | `draft` → `ready` |
| `cancelled` | `cancelled` | `draft` / `ready` → `waived`; `billed` / `settled` — звичайне скасування відхиляється (409 `concierge_service_billed`), лише «скасування зі сторно білінгу» (нижче): `billed` / `settled` → `reversed` |
| `open` / `in_progress` / `on_hold` / `review` | прогрес бронювання лишається (`planned` / `booked` / `confirmed` / `in_service`) | без змін |
| повторно відкрито з `completed` | `in_service` | `ready` → `draft` |
| повторно відкрито з `cancelled` | `planned` | `waived` / `reversed` → `draft` (новий цикл білінгу) |

Зміна статусу на поверхнях сервісу (робоче місце консьєржа, форма сервісу, секція консьєржа терміну) — це крок задачі за правилами work center (§8): виконавець запускає (`in_service` → задача `in_progress`), автор задачі або вища роль завершує, скасовує й відкриває повторно; інакше 403 (`concierge_service_task_author` / `concierge_service_task_participant`). Список і картка сервісу повертають `allowed_statuses` (що може цей користувач зараз), `allowed_billing_statuses`, `financial_locked`, `linked_task_id` / `linked_task_status`; UI пропонує лише їх. Сервіс лишається в робочому місці консьєржа з усіма кроками й після появи задачі (кнопка «Открыть задачу / Aufgabe öffnen»); календар і карта показують такий сервіс як його задачу.

| Перехід сервісу | Кроки задачі | Хто |
|---|---|---|
| `planned` → `booked` / `confirmed`, `booked` → `confirmed` | `open` → `in_progress` | CEO, консьєрж (через задачу — також PM); лише ендпоінт бронювання провайдера (звичайне збереження з `booked`/`confirmed` — 409) |
| `planned` / `confirmed` → `in_service` | `open` / `on_hold` → `in_progress` | виконавець, автор або вища роль |
| `in_service` → `completed` | → `completed` (з `open` через `in_progress`) | автор або вища роль |
| `planned` / `booked` / `confirmed` / `in_service` → `cancelled` | → `cancelled` | автор або вища роль; пацієнт — свій запит з порталу (`planned`, без бронювання), системним кроком з історією (`patient_cancelled`) |
| `completed` → `in_service`, `cancelled` → `planned` | `completed` → `in_progress`, `cancelled` → `open` | автор або вища роль |
| нефінальний → `completed` | системний крок `appointment_completed` | автоматично: завершення немедичного терміну (скасовані сервіси не змінюються) |
| автоматичний сервіс терміну → `cancelled` / назад `planned` | системний крок `appointment_cancelled` / `appointment_type_changed`, назад `appointment_reactivated` | автоматично: скасування терміну або зміна типу (див. нижче) / зміна типу на немедичний |

Нове посилання задачі на вже закритий сервіс — 409 (спершу відкрийте сервіс).

**Скасування терміну (рішення власника 2026-09-28, Q4).** Сервіси, створені персоналом чи пацієнтом у порталі, скасування терміну переживають. Автоматичний сервіс (`appointment_bootstrap`) без бронювання в партнера скасовується через свою задачу (білінг `waived`). Сервіс із бронюванням у партнера (`booked` / `confirmed` / `in_service`, номер бронювання або контакт `booking_*`) чи вже виставлений у рахунок автоматично не скасовується: ставиться `booking_decision_required_at`, консьєрж сервісу (виконавець задачі й призначений консьєрж; якщо нікого — координатор пацієнта) отримує сповіщення «Термин отменён — проверьте бронирование консьержа / Termin abgesagt – Concierge-Buchung prüfen», а термін стоїть у списку «потребує уваги» (`appointments_attention_reason_concierge_booking_decision_count`), доки хтось не вирішить: «Сохранить бронирование / Buchung behalten» (`POST /concierge-services/{id}/keep-booking`, CEO, PM, консьєрж з доступом; аудит `keep_concierge_service_booking`) або скасувати сервіс (закриття сервісу знімає позначку). Задачі сервісів загальний каскад скасування терміну не скасовує. Так само при зміні типу терміну з немедичного.

**Білінг сервісу (`billing_status`, рішення власника 2026-09-28, Q3)**: `draft` Черновик / Entwurf · `ready` Готово / Bereit · `billed` Выставлен счёт / In Rechnung gestellt · `settled` Оплачено / Beglichen · `waived` Списано / Erlassen · `reversed` Сторнировано / Storniert (рішення 2026-09-29). Переходи: `draft` → `ready` → `billed` → `settled`; `waived` лише з `draft` або `ready`. Готовність виводиться із задачі (вручну `draft` → `ready` — лише для завершеного сервісу; назад у `draft` — лише через повторне відкриття задачі). Вручну встановлюють CEO, PM, Billing (консьєрж — ні); інші переходи — 409. Скасування сервісу ставить `waived`; виставлений (`billed` / `settled`) сервіс звичайним шляхом не скасовується (409) — лише зі сторно білінгу (нижче). Суми (`cost_estimate`, `actual_cost`, `quantity`, `unit_price`, `currency`, послуга каталогу) після `billed` заблоковані (409 `concierge_service_amounts_locked`; незмінні значення форма може надсилати), UI робить поля лише для читання. Правила переходів і блокування сум дублює БД. Видалити можна лише сервіс з білінгом `draft`, без витрат і без історії ключів чи контактів з партнером (409 — скасуйте).

**Скасування виставленого сервісу зі сторно білінгу (рішення власника 2026-09-29).** Для сервісу з білінгом `billed` / `settled` (зазвичай завершеного) CEO і PM мають дію «Отменить со сторно начисления / Mit Abrechnungsstorno stornieren» (робоче місце консьєржа). `GET /concierge-services/{id}/billing-reversal-options` повертає позиції замовлень пацієнта, що могли виставити сервіс (сервісні, не медичні, не скасовані; спершу позиції замовлення терміну), з прев'ю скасування кожної (3.2 довідника продажів і фінансів). `POST /concierge-services/{id}/cancel-with-billing-reversal` (`reason` 3–1000, `order_leistung_id` або `null` — «виставлено поза GMED», `issue_credit_note`) в одній транзакції: скасовує обрану позицію (у випущеному рахунку — з кредит-нотою, лише CEO/Billing; у чернетці — 409), ставить білінг `reversed` з `billing_reversed_at/by`, `billing_reversal_reason`, `billing_reversal_order_leistung_id` і скасовує сервіс через його задачу за правилами work center (лише автор задачі або вища роль; завершену задачу — кроками `in_progress` → `cancelled`); аудит `reverse_concierge_service_billing` (плюс `derive_concierge_service_from_task`, `cancel_order_service`, `credit_note_created`) у тій самій транзакції. Сервіс без білінгу `billed`/`settled` — 409 `concierge_service_not_billed` (звичайне скасування). `reversed` вручну не встановлюється; БД дозволяє `billed`/`settled` → `reversed` і `reversed` → `draft` (повторне відкриття). Міграція `20260929100000_order_service_billing_reversal`.

**Задача запиту з порталу (рішення власника 2026-09-28, Q15)**: автор (`assigned_by`) задачі запиту пацієнта — координатор пацієнта: перший призначений консьєрж, інакше перший PM, інакше CEO (`concierge_service_coordinator_id`); без призначеного консьєржа він же виконавець. Пацієнт ніколи не автор і не виконавець задачі, сповіщення work center йому не йдуть.

**Міграції.** `20260928212000_concierge_service_follows_task`: тригери виведення й захисту; відновлення наявних даних — закритий на боці сервісу сервіс із відкритою задачею закриває задачу (історія `service_already_closed`, аудит `close_concierge_task_of_closed_service`; задачі пунктів чекліста — навпаки), решта сервісів виводяться зі своєї задачі (аудит `derive_concierge_service_from_task`, `reason = backfill`). `20260928212100_concierge_task_author_not_patient`: задачі з пацієнтом як автором або виконавцем отримують координатора (історія `reassigned`, аудит `replace_patient_task_author`). Нічого не видаляється.

**Ключі (`key_status`)**: `received` Ключ получен / Schlüssel erhalten · `stored` Ключ на хранении / Schlüssel verwahrt · `handed_over` Ключ передан / Schlüssel übergeben · `returned` Ключ возвращён / Schlüssel zurückgegeben. Переходи: (немає) → received; received → stored / handed_over / returned; stored → handed_over / returned; handed_over → returned; returned → received. Хто: CEO, PM, консьєрж (консьєрж — лише себе відповідальним). Журнал подій лише доповнюється.

**Контакти з партнером (`outcome`)**: `no_answer` Не ответили / Nicht erreicht · `reached` Связались / Erreicht · `quote_requested` Цена запрошена / Angebot angefragt · `quote_received` Цена получена / Angebot erhalten · `follow_up_needed` Нужен повторный контакт / Rückmeldung erforderlich · `booking_requested` Бронирование запрошено / Buchung angefragt · `booking_confirmed` Бронирование подтверждено / Buchung bestätigt · `declined` Отказ / Abgelehnt · `cancelled` Отменено / Storniert. Два `booking_*` пише лише бронювання провайдера. Журнал лише доповнюється.

Бронювання, ключі, контакти й ціни через задачу сервісу змінюють лише ролі з `services.edit` (CEO, PM, консьєрж); CEO Assistant — лише перегляд. Аудит: зміни сервісу, бронювання, ключі, контакти, `mark_concierge_service_ready_for_billing` (завершення терміну).

## 13. Рекомендації пацієнту (`patient_recommendations`)

| Поле | Значення (RU / DE) |
|---|---|
| `status` (портал, сторінка персоналу) | `active` Активно / Aktiv · `completed` Завершено / Abgeschlossen · `declined` Отклонено / Abgelehnt · `cancelled` Отменено / Storniert · `superseded` Заменено / Ersetzt |
| `lifecycle_status` (клінічна вкладка) | `aktiv` Активна / Aktiv · `erfolg` Выполнена / Erfolg · `nicht_erfolgt` Не выполнена / Nicht erfolgt · `unbekannt` Неизвестно / Unbekannt |
| `patient_decision` | `schedule` · `already_done` · `need_consultation` · `declined` |

- `status` і `lifecycle_status` — один життєвий цикл (рішення 2026-09-28, Q11; обмеження БД `patient_recommendations_status_lifecycle_check`): `active` ↔ `aktiv`, `completed` ↔ `erfolg`, `declined`/`cancelled` ↔ `nicht_erfolgt`, `superseded` ↔ `unbekannt`. Персонал (CEO, PM з призначенням) змінює одне з полів — друге виводиться (`nicht_erfolgt` зберігає `declined`, інакше `cancelled`); два суперечливі зміни — 422. Міграція `20260928213400` узгодила наявні записи (клінічний результат на активній рекомендації має перевагу, інакше цикл іде за статусом) з рядком аудиту `reconcile_recommendation_lifecycle` на кожен.
- Рішення пацієнта: `already_done` → `completed`, `declined` → `declined`, інші → `active` (клінічний цикл — відповідно); `schedule` створює запит на термін (дубль — 409).
- Нове сповіщення пацієнту — лише для рекомендації, видимої в порталі.
- Нагадування (планувальник): лише `status = active` і `lifecycle_status = aktiv`, коли настала дата `reminder_at` або `valid_to − reminder_lead_days` (Europe/Berlin); кожне надсилається один раз (рядок позначається в тому самому запиті). Автор і призначений персонал — завжди, пацієнт — лише для видимої в порталі.

## 14. Етапи follow-up терміну (`appointments.followup_milestone`)

`post_1w`, `post_1m`, `post_6m`, `doctor`, `package_end` або порожньо — мітка терміну-контролю, не статус. Статус етапу зберігається в кроках follow-up замовлення (§11) і змінюється вручну. При завершенні терміну можна запланувати нагадування «1 тиждень / 1 місяць / 6 місяців».
