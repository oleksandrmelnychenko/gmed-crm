# Статуси: записи, документи, приватність і доступ

Довідник для тестувальників: статуси, переходи і побічні ефекти пацієнтів, документів, запитів DSGVO, облікових записів і партнерів. Відповідає коду гілки аудиту статусів (вересень 2026). Мітки RU/DE — як у інтерфейсі. «Хто» — ролі, яким сервер дозволяє перехід; приховування кнопки в UI сервер не замінює.

Скорочення ролей: CEO, CEO Assistant (далі Assistant), PM (Patient Manager), TL (Teamlead Interpreter), IT (IT Admin). 423 = «запис заблоковано» (Art. 18 / анонімізація), 409 = конфлікт стану.

## 1. Пацієнт (`patients`)

Статус — пара `lifecycle_status` + `is_active` (записуються разом), прапори DSGVO — у `legal_status`.

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `active` | Активен | Aktiv | Робоча карта (`is_active = true`). |
| `inactive` | Неактивен | Inaktiv | Карта закрита; `inactive_since` запускає строк зберігання. |
| `prospective` | Заявитель (фільтр «Заявители») | Interessent («Interessenten») | Проспект із ліда, `is_active = false`; у списку лише за фільтром (CEO, PM). |
| `deleted` | Удалён | Gelöscht | Лише в CHECK і фільтрі; сервер його не записує. |
| `legal_status.processing_restricted = true` | банер «Обработка данных ограничена (ст. 18 DSGVO)» | «Verarbeitung eingeschränkt (Art. 18 DSGVO)» | Карту можна зберігати й читати, змінювати — ні. |
| `legal_status.anonymized_at` | — (ПІБ і PID = `ANON-…`) | — | Залишок після виконаного видалення (Art. 17). |

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → `active` | CEO, PM: створення пацієнта | Творець отримує прив'язку `manual`. |
| — → `prospective` | Лід (identity-first) | Хард-видалення разом із лідом, поки лід не конвертовано. |
| `prospective` → `active` | Конвертація ліда (`leads.convert`) | — |
| `inactive` → `active` | Конвертація повторного ліда на існуючого пацієнта | `inactive_since` очищається. |
| `active` → `inactive` | CEO, PM: «Деактивировать пациента» / «Patient deaktivieren» | Ставить `inactive_since = now()`. Обмежену карту деактивувати можна (рішення власника 2026-09-28), анонімізовану — 423, `prospective` — 409. |
| `inactive` → `active` | CEO, PM: «Активировать пациента» / «Patient aktivieren» | Очищає `inactive_since`. Обмежена чи анонімізована — 423. |
| → обмежена | Виконання запиту `restriction` (CEO, IT) | Див. §9. |
| обмежена → знята | CEO, IT: «Снять ограничение» / «Einschränkung aufheben», причина 10–2000 символів | Аудит `processing_restriction_lifted`, подія в хронології. |
| → анонімізована | Виконання запиту `erasure` (CEO, IT) | `is_active = false`, `active` → `inactive`, `inactive_since` ставиться, якщо не було; усі прив'язки й згоди відкликаються, некомерційні файли видаляються, чат редагується. |
| видалення пацієнта | — | Завжди 409 (пряме видалення вимкнено). |

Обмежена або анонімізована карта: усі зміни пацієнта, його клінічних даних, прив'язок (крім відкликання), зміна/видалення/нове завантаження його документів персоналом і передача документів провайдерам — 423. Рішення власника 2026-09-28 (Art. 18): також 423 з поясненням «Processing of this patient's data is restricted (Art. 18 DSGVO): … is not possible until the restriction is lifted» для нових приймань (зокрема конвертації запиту з порталу), нових замовлень, відкриття документа персоналу чи перекладачу, призначення перекладу, збереження перекладеного документа (тож і автоматичного відкриття перекладу в порталі). Відкриття документа самому пацієнту дозволене. Відкликати прив'язку й деактивувати обмежену карту можна завжди. Перемикач статусу в картці показується лише CEO/PM з `patients.edit`, не для `prospective` і анонімізованої карти; для обмеженої — лише деактивація. У картці обмеженої карти кнопки нового приймання й замовлення не показуються, банер перелічує заблоковані дії.

Хронологія пацієнта показує «Карта пациента активирована/деактивирована» / «Patientenakte aktiviert/deaktiviert», події запитів DSGVO і згод (див. §9, §11). Подія «Профиль изменён: <поля>» називає лише справді змінені поля (див. [політику аудиту](../../engineering/02_audit-migration-policy_ua.md)): зміна лише телефону — «Телефон», без «Гражданства» й «Контакты» (QA 2026-10-12 B2-13).

**Мови пацієнта** (`languages`) — однаково у «Новый пациент» і в редакторі профілю (QA 2026-10-12 B2-13): той самий вибір зі списку ISO 639-1 («Добавить язык» / «Sprache hinzufügen»), коди надсилаються в нижньому регістрі без повторів; сервер приймає новий код лише зі списку, а збережене старе значення-назву («Русский») редагування лишає як є. Картка показує мови так, як їх називає вибір («Немецкий (de)»).

### Правовий статус картки (`legal_status`, «Правовой статус» / «Rechtsstatus»)

Чек-лист: DSGVO (`dsgvo_signed`), розкриття лікарської таємниці / Schweigepflichtsentbindung (`confidentiality_release_signed`), посвідчення особи (`identity_verified`), пакет документів (`document_pack_complete`), комплаєнс завершено (`compliance_completed`), статус договору (`contract_status`), нотатки.

- **DSGVO і Schweigepflichtsentbindung — лише за підписаним документом** (рішення власника 2026-10-12, продовження рішення 2026-10-11 «підписано лише з доказом», див. [продажі й фінанси §6](01_sales-finance_ua.md)). Пункт ставить `record_document_signature_tx` у транзакції підпису: «Подписано на бумаге» (`POST /documents/{id}/paper-signature`: скан, дата, звірка), електронний підпис (окремий запит чи пакет, після завершення), «Отметить подписанным» для завантаженого скану (згенерований непідписаний документ так не позначається — 409 `signature_evidence_required`). Конвертація ліда ставить обидва пункти, бо сама вимагає підписаних документів обох видів.
- `POST /patients/{id}/update` відхиляє зміну будь-якого з двох значень — поставити чи зняти — для **кожної ролі, включно з CEO**: 409 `legal_status_requires_signed_document` (поле `items` — ключі), UI показує текст RU/DE замість англійського. Відмова стосується всього збереження (інші поля того самого запиту не записуються). Значення, надіслане без змін (старий редактор профілю), або не надіслане — приймається, збережене лишається; аудит `legal_status_changed_keys` ці ключі не містить.
- **Картка** (`GET /patients/{id}`) поруч із `legal_status` віддає `legal_status_evidence` (лише тим, хто бачить `legal_status`) — для `dsgvo` і `confidentiality_release`: `set` (збережений прапор), `state`, `signed_document` (чинний підписаний документ виду: `status = active`, файл не видалено; id, номер, назва, `signed_at`, `source` = `paper_signature` / `electronic_signature` / `signed_document`), `pending_document` (найновіша поточна версія непідписаного неархівного немедичного документа цього виду — за шаблоном чи типом, як при підписі: Einverständniserklärung `privacy_consents`, `consent_data_release*`, `consent`; Schweigepflichtsentbindung `confidentiality_release`; `signature_pending`, якщо він у відкритому е-запиті) і `template_id` для генерації (`privacy_consents`, `confidentiality_release`). Стани: `signed` — прапор і чинний підписаний документ: «Подписано ДД.ММ.РРРР · скан на бумаге / электронная подпись / подписанный документ» / «Unterschrieben am … · Papierunterschrift (Scan) / elektronische Signatur / unterschriebenes Dokument» (дата — берлінський день); `manual` — прапор без чинного підписаного документа: «Отмечено вручную, подписанный документ отсутствует» / «Manuell markiert, kein unterschriebenes Dokument vorhanden»; `revoked` — згоду відкликано (див. Widerruf нижче); `missing` — «Нет подписанного документа» / «Kein unterschriebenes Dokument».
- **UI.** У розділі «Правовой статус» картки ці два пункти без галочки: стан із документа; CEO/PM із правом редагування картки й `documents.manage` бачать «Подписано на бумаге» / «Auf Papier unterschrieben» (діалог підтвердження підпису для `pending_document`), а без документа — «Создать документ» / «Dokument erstellen» (генератор із вибраним шаблоном); документ у відкритому е-запиті — «Ожидает электронной подписи», без кнопки. Лист «Обновить правовой статус» і редактор профілю показують їх лише для читання й не надсилають. Інші пункти (особа, пакет документів, комплаєнс, статус договору, нотатки) — як і раніше.
- **Позначені вручну до 2026-10-12** (дані PROD не змінювались): прапор лишається і **далі рахується** в усіх воротах — повторна перевірка перед замовленням (`GET /patients/{id}/recheck`: `compliance_ready`, `confidentiality_release_ready`), готовність повторного ліда існуючого пацієнта — щоб раптово не зупинити поточні справи; картка показує попередження й дію. Після підписаного скану чи QES стан стає `signed`.
- **Згода для неповнолітнього** (рішення власника 2026-10-12): підписана Einverständniserklärung для дитини (`consent_data_release_child`, `consent_data_release_single`, завантажена — тип `consent_data_release`) містить і Schweigepflichtsentbindung, тож ставить **обидва** пункти (`dsgvo_signed` і `confidentiality_release_signed`) і дає обидві згоди в реєстрі (`dsgvo_data_transfer`, `schweigepflicht_release`) — і скан на папері, і QES (`compliance_kind` документа лишається `dsgvo`). Картка показує цей документ як підписаний для обох пунктів, а непідписаний — як документ до підпису для обох. Готовність ліда до конвертації (`confidentiality_release_signed`) приймає такий документ так само. Ці шаблони генеруються лише для неповнолітнього (молодше 18 років на сьогоднішню дату за Europe/Berlin; без дати народження — без перевірки): діалог генерації не пропонує їх дорослому пацієнтові, а сервер відповідає 422 `child_consent_for_adult` (QA 2026-10-12 B2-05).
- **Widerruf — відкликання згоди** (рішення власника 2026-10-12). Відкликання в реєстрі згод (`POST /admin/compliance/patient/{id}/consents`, `action = revoke`) згоди `dsgvo_data_transfer` знімає пункт DSGVO, згоди `schweigepflicht_release` — пункт Schweigepflichtsentbindung; виконаний запит `third_party_revoke` (§9) знімає обидва. У тій самій дії записується час: `legal_status.dsgvo_revoked_at` / `confidentiality_release_revoked_at`; аудит `consent_revoked` (поле `legal_status_items_withdrawn`), відповідь реєстру — те саме поле. Нікому, крім того, що реєстр уже робить (відкликання відкриттів третім особам, §4), нічого не надсилається. Інші типи згод (канали `document_share_*`, `third_party_sharing`, `treatment_contract`) пунктів не знімають.
  - **Нові замовлення заблоковані**, доки немає згоди, підписаної **після** відкликання: `GET /patients/{id}/recheck` повертає `can_create_order = false`, `compliance_ready` / `confidentiality_release_ready = false`, `consent_revocations` (дати) і причину «DSGVO consent was revoked on ДД.ММ.РРРР» / «Medical confidentiality release was revoked on ДД.ММ.РРРР» (берлінський день; UI: «Согласие DSGVO отозвано ДД.ММ.РРРР — новые заказы только после согласия, подписанного позже» / «DSGVO-Einwilligung am … widerrufen – …»). Блокування діє й для пацієнта без попередніх замовлень, для якого повторна перевірка інакше не потрібна; `POST /orders` — 422 «Existing customer re-check is incomplete», як і за відсутньої згоди.
  - **Картка:** стан `revoked` із `revoked_at` — «Согласие отозвано ДД.ММ.РРРР» / «Einwilligung am ДД.ММ.РРРР widerrufen», позначка «Отозвано» / «Widerrufen», підказка «Новые заказы заблокированы, пока нет согласия, подписанного после отзыва.»; оскільки всі попередні екземпляри підписані, дія — «Создать документ» (нова згода), далі «Подписано на бумаге» або QES.
  - **«Комплаенс завершен» знімається** (QA 2026-10-12 B2-13): відкликання, що знімає пункт, у тій самій дії ставить `compliance_completed = false`, якщо він стояв, і записує чому — `compliance_reopened_reason = consent_revoked`, `compliance_reopened_at` (час відкликання), `compliance_reopened_items` (зняті ключі). Поки згоду не підписано знову, позначити комплаєнс не можна: `POST /patients/{id}/update` із переходом `false → true` дає 409 `compliance_requires_active_consents` (поле `items`; UI — текст RU/DE); надіслане без зміни значення приймається. Картка, лист «Обновить правовой статус» і редактор профілю показують комплаєнс невиконаним із поясненням «Можно отметить только после нового подписанного согласия: согласие DSGVO — отзыв ДД.ММ.РРРР» / «Erst nach einer neu unterschriebenen Einwilligung möglich: …», перемикач заблоковано; запис, відкликаний до цієї зміни (у базі ще `true`), показується так само. Після нового підпису — «Снято: согласие DSGVO — отзыв ДД.ММ.РРРР» / «Zurückgesetzt: …», доки співробітник не позначить комплаєнс знову; позначка прибирає `compliance_reopened_*`.
  - **Знову ставить пункт** лише підпис, даний пізніше за відкликання: скан із датою підпису після відкликання або QES. Скан екземпляра, підписаного до відкликання (дата підпису ≤ часу відкликання), записується як версія документа, але пункт не ставить і згоду в реєстрі не відновлює. Новий підпис знімає `*_revoked_at`. Ручне «Выдать» у реєстрі згод пункт не ставить. Конвертація ліда для пацієнта, що відкликав згоду, рахує лише документи, підписані після відкликання (`dsgvo_document_signed`, `confidentiality_release_signed`), і після конвертації прибирає `*_revoked_at`.
- **Видалення й архів.** Підписаний документ не видаляється (409 `document_delivery_protected`), тож прапор не зникає. Якщо підписану версію архівують (зміна статусу, нова версія з шаблону), прапор лишається, а картка показує `manual` і пропонує підписати нову версію. Відкликання чи закінчення е-запиту до підпису нічого не змінює. Видалення даних (Art. 17) відкликає всі згоди, але пунктів не змінює: анонімізована карта заблокована для будь-яких змін (423).

## 2. Прив'язка персоналу до пацієнта (`patient_assignments`)

| Стан | RU | DE | Значення |
|---|---|---|---|

| відкликана | Отозвано | Widerrufen | Доступу немає. |
| `source = manual` | — | — | Призначив менеджер; не спливає. |

| Перехід | Хто / як | Умови й наслідки |

Аудит `revoke_assignment` із `source`, `reason = manual`. TL кнопки не бачить. |
| — → активна `interpreter_booking` | Автоматично при бронюванні перекладача | Лише якщо поточне відкликання не ручне. Аудит у транзакції `grant_booking_patient_access`. |
| усі прив'язки співробітника → відкликані | Деактивація облікового запису (§12) | Аудит `revoke_assignment` на кожну, `reason = user_deactivated`, у транзакції деактивації. Прив'язка порталу пацієнта не зачіпається. |
| `interpreter_booking` → відкликана | Автоматично: зняття з приймання, відмова, скасування/видалення приймання; або через `interpreter_booking_access_days` (типово 14) після дати останнього заброньованого приймання (перевірка кожні 15 хв) | Аудит `end_booking_patient_access`. |
| усі → відкликані | Виконання видалення (Art. 17) | — |

## 3. Документ (`documents`)

| Поле / ключ | RU | DE | Значення |
|---|---|---|---|
| `status = draft` | Черновик | Entwurf | Скан «на разбор», завантаження перекладача, шаблон до підписання. |
| `status = active` | Активный | Aktiv | Робочий документ. |
| `status = archived` | Архивный | Archiviert | Замінений новою версією або файл видалено. |
| `visibility = internal` | Внутренний | Intern | Лише персонал. |
| `visibility = released_internal` | Выпущен внутренне | Intern freigegeben | Відкритий усередині компанії. |
| `visibility = released_external` | Выпущен внешне | Extern freigegeben | Можна передавати зовнішнім отримувачам. |
| `visibility = patient_visible` | Можно выпустить пациенту / Выпущен пациенту | Zur Patientenfreigabe bereit / Für Patienten freigegeben | Пацієнт бачить документ лише за наявності активного відкриття в порталі; без нього мітка — «Можно выпустить пациенту», з ним — «Выпущен пациенту» (`has_active_portal_release` у картці й списку документів; QA 2026-10-11 B-13, механіка відкриття не змінювалася). Згенеровані чернетки мають цю видимість за замовчуванням, але в портал самі не потрапляють. |
| файл видалено (`file_deleted_at`) | — | — | `archived` + `internal`, файл прибрано. |

Похідні стани: **«на разбор»** (черга класифікації: без категорії, категорія `portal_upload`, неконкретний тип — `document`, `uploaded_document` і кожен тип завантаження з порталу `patient_*_upload`, — скан `manual_intake` у `draft`, завантаження перекладача в `draft`; не `archived`; до 200 рядків; походження `ursprung` не враховується: класифіковане завантаження з порталу, тобто з конкретним типом і категорією, з черги виходить — рішення власника 2026-09-28, Q8; категорія, яку персонал вибрав уручну в «Редактировать документ» (інша, ніж збережена), стає й типом документа з неконкретним типом — так само, як «Применить подсказку», тож документ виходить з черги; категорія, яку вибрав пацієнт у порталі, сама цього не робить — QA 2026-10-11 B-11), **перевірка тимліда** (завантаження перекладача у `draft`), **остання версія** (немає новішої, що її замінює).

**Номер документа** (`document_number`, QA 2026-10-11 B-07/B-19): кожен новий документ — завантажений чи згенерований — отримує номер `<префікс>-<РРРРММДД>-<NNNNNN>` з однієї послідовності `document_number_seq` (функції БД `document_number_prefix`, `next_document_number`; префікс за шаблоном чи типом: `SE` Schweigepflichtsentbindung, `EW` згода на передачу даних, `DS` інформаційний лист, `ET` наклейка, `ID` документ особи, `AML`, `GWG`, інакше `DOC`). Договір, замовлення й кошторис замовлення нумеруються, як і раніше, номером договору/замовлення/кошторису з `-VNN`, попередня калькуляція — `VKS-…`. Наступна версія документа (підписаний скан, результат е-підпису, нова версія з шаблону чи завантаження) зберігає номер документа з суфіксом версії (`SE-20261011-000068-V02`, функція `document_version_number`). Наявні номери не змінювалися.

**Обов'язкові документи пацієнта** (`system_settings.required_patient_documents`, «Не хватает обязательных документов»): правило — ключ, назва, типи (`art`, порівнюються також із шаблоном `generated_template_id`), категорії і необов'язкове `signed`. Рахуються лише поточні версії активних документів пацієнта (чернетка — ні); файли іншої особи (`payer_*`, `representative_*`) — ніколи. Значення порівнюються в нижньому регістрі з `_` замість пробілів і дефісів, умлаути розписуються (`Einverständniserklärung` → `einverstaendniserklaerung`). Стандартні правила після міграції `20261011195730` (QA 2026-10-11 B-06/B-11/B-18): **паспорт** — тип `passport`, `passport_scan`, `reisepass`, `personal_passport` чи `identity` (документ особи конвертованого ліда) або категорія `identity`, `passport`, `personal_passport` («PERS · Паспорт»); **форма згоди** (`consent_form`, «Einverständniserklärung») — лише **підписаний** документ родини згоди DSGVO (`consent`, `consent_form`, `einverstaendniserklaerung`, `gdpr_consent`, `privacy_consents`, `consent_data_release`, `consent_data_release_child`, `consent_data_release_single`): версія з підписаним сканом, результат е-підпису чи документ, позначений підписаним. Категорії `administrative` і `consent` згоди більше не задовольняють (наклейка, Schweigepflichtsentbindung, інформаційний лист — не форма згоди). Правила, додані адміністратором, міграція не змінює. З QA 2026-10-12 (B2-07) правило, що називає хоч один код родини згоди DSGVO, приймає **кожну підписану згоду DSGVO** — так само, як пункт «DSGVO» правового статусу й перевірка перед замовленням: документ, підписаний як згода DSGVO (`compliance_kind = dsgvo`, зокрема згода конвертованого ліда з типом `dsgvo`), або підписаний документ будь-якого шаблону чи типу родини (`patients::DSGVO_CONSENT_DOCUMENT_CODES`). Згода, підписана до відкликання в реєстрі згод (`dsgvo_revoked_at`, поки пункт не встановлено знову), форму згоди не задовольняє — лише підписана після відкликання. Портал пацієнта («Мои документы», `/me/document-alerts`) пропонує форму завантаження лише для того, що пацієнт може надіслати сам (документ особи, звіти): бракує згоди (ключ правила з `consent`, `einverst…`, `dsgvo`, `privacy`, `schweigepflicht`, `confidentiality`) — він пише «Согласия … GMED пришлёт вам на подпись — электронно по e-mail или на бумаге. Загружать их здесь не нужно» / «Einwilligungen … schickt Ihnen GMED zur Unterschrift …» замість «Nutzen Sie das Formular unten …», бо жодна категорія завантаження порталу згоди не задовольняє (QA 2026-10-12 B2-13).

**Категорії документів у виборі** (QA 2026-10-12 B-12): три категорії першої таксономії дублювали категорії дерева під MED — `medical_report` («Медицинский отчёт») ~ `medical_bericht`, `conclusion` («Заключение / результат») ~ `medical_befund`, `lab_analysis` («Лаборатория / анализ») ~ `medical_lab`. Міграція `20261012180000` позначає їх `ref_document_categories.selectable = false` (і додає старий код до `aliases` категорії, що його замінює): вибір категорії в аркуші документа, у завантаженні й на сторінці «Документы» їх більше не пропонує, крім документа, уже записаного в таку категорію. Документи й надалі мають ці коди, портал пацієнта й імпорт клінічного документа далі записують у них (`lab_analysis`, `medical_report`), фільтр списку документів їх містить.

## 4. Відкриття документа (`document_shares`) і портал

Окремого статусу немає: відкриття **активне** (`revoked_at` порожній), **очікує підтвердження** (`requires_confirmation` без `confirmed`), **підтверджене**, **відкликане**.

| Ключ | RU | DE |

| `in_progress` | В работе | In Bearbeitung |

| З | Дозволено в | Хто |
|---|---|---|
| `pending` | `in_progress`, `completed`, `cancelled` | CEO, PM, TL, перекладач, консьєрж із правом редагування документа |

`completed` потребує перекладеного тексту. Перекладач діє лише над своїм або непризначеним запитом (кнопка «Взять себе» / «Mir zuweisen» — лише для непризначених). Інші ролі (перекладачі, `Billing`) — 403; `CEO Assistant` запускати імпорт не може (403); інтерфейс не показує їм «Сканировать и распознать», «Распознать документ» і не робить запитів, які завжди закінчилися б 403. Якщо файл уже завантажено, а запуск імпорту відхилено, користувач бачить повідомлення RU/DE, що файл лишився в документах пацієнта як медичний документ (джерело «Импорт медицинского документа»), і причину відмови без сирого тексту сервера (QA B-02/B-05). | Ключ | Панель (RU / DE) |

Запит (CEO) → `requested`; воркер кожні 2 с: `requested` → `processing` (оренда 75 с, спроба +1, максимум 3) → `ready` / назад у `requested` (повтор із затримкою) / `failed`; прострочена оренда повертає в `requested` або `failed`. «Повторить» (CEO): `failed` → `requested`, лише для тієї самої моделі, промпта й governance. Переходи тригер БД контролює, кожен пише подію життєвого циклу; `ready`/`failed` — аудит і сповіщення. Якщо AI вимкнено, воркер не стартує.

так само записи родичів **інших** пацієнтів, прив'язані до стертої карти (`related_patient_id`): без ділового запису — видаляються разом із їхніми результатами санкційної перевірки (`sanctions::screening::purge_for_relations_in_tx`), інакше лишаються в обсязі вище й відв'язуються від стертої карти, якщо до них не адресовано випущений рахунок (тоді прив'язка лишається, бо від неї залежить зафіксований одержувач); копії картки в підготовці замовлення (`order_intakes.data`, `prepared_data`, `baseline_facts`, `confirmed_facts`, `confirmation_snapshot`, `order_intake_fact_reviews`, а також `order_intake_context` збережених документів замовлення): страховка, телефон, e-mail, адреса стають порожніми, копії особи (`identity`, `patient`, `lead`) — `null`; зміст замовлення (дати, позиції, ціни, передоплата) і відповіді GwG (PEP, представник), які зберігає й сама карта, лишаються (§ 8 Abs. 4 GwG); додаткові контакти (`patient_contacts`), записи імпорту плану ліків (`patient_bmp_imports.identity_snapshot`), сповіщення про пацієнта і його стерті документи; повідомлення чату; власний вхід пацієнта в портал (і вхід опікуна, що вів лише до цього пацієнта): `deleted-patient-<id>@invalid`, «Deleted patient», непридатний пароль, відкликані сесії. Вільний текст задач і прийомів (аудит 2026-10-01, п. 1 і 15): у задачах пацієнта, його прийомів і замовлень — назва, опис, місце, коментарі й пункти чек-листа; у прийомах пацієнта — назва, місце, нотатки (підготовка, підсумок, загальні), коментар перекладача, чек-листи, комунікація з клінікою (тема, текст), звіти перекладача (текст, нотатки); у запитах пацієнта на прийом — причина, нотатки, нотатка розгляду, причина скасування. Кожна згадка пацієнта — ім'я, прізвище, повне ім'я в обох порядках, номер пацієнта, e-mail, телефони (і з додаткових контактів), номер паспорта й страховки, вулиця, контакт для екстрених випадків — замінюється анонімною міткою (`ANON-…`) як ціле слово без урахування регістру; дати, статуси, години й суми лишаються для ділових записів. Терміни коротші за 2 символи (наприклад, ім'я з однієї літери) не замінюються — свідомо, щоб не зачепити чужий текст. Поле з обмеженням довжини після заміни обрізається до межі схеми (коментар задачі 4000, пункт чек-листа задачі 500, коментар перекладача 1000, нотатка: заголовок 255, текст 20000), тож довша мітка ніколи не зриває стирання. Спільні нотатки (`internal_notes`, архівні теж) не прив'язані до пацієнта: у них шукаються лише сильні ознаки — повне ім'я (в усіх порядках), номер пацієнта, e-mail, телефони, номер паспорта й страховки, контакт для екстрених випадків — без окремого імені, прізвища й вулиці (їх може містити нотатка про іншу людину чи клініку); вкладення нотаток не змінюються. Вкладення задач пацієнта (`concierge_operational_task_attachments`): файл видаляється після коміту (як файли стертих документів), рядок лишається з типом, розміром, автором і датами, позначкою видалення (`deleted_at`, `deleted_by` = виконавець) і нейтральною назвою `erased-file.<розширення>`; раніше видалені вкладення отримують ту саму назву. Терміни беруться з картки до анонімізації, у тій самій транзакції. Сповіщення про ці задачі, прийоми й запити на прийом видаляються. Відповідь виконання й аудит `dsgvo_anonymize` містять лічильники `erased_relations` (`removed`, `kept_for_business_records`, `linked_removed`, `linked_kept`), `erased_order_intake_facts` і `scrubbed_free_text` (рядки, де текст змінено, за таблицями, зокрема `internal_notes` і `task_events`; `task_attachments_deleted`; видалені сповіщення). Історія задач пацієнта (`concierge_operational_task_events`, append-only) теж очищується (рішення власника 2026-10-12): у payload — попередній текст відредагованих і видалених коментарів, пунктів чек-листа, назви файлів вкладень, колишні назви — та сама заміна з тими самими межами довжини (`body`/`previous_body` 4000, `label`/`previous_label` 500, `file_name` 255). Це вузький виняток з append-only (міграція `20261012160000_dsgvo_erasure_task_event_scrub.sql`, [політика](../../engineering/02_audit-migration-policy_ua.md)): лише в транзакції стирання (`gmed.dsgvo_erasure = on` на час одного оновлення), лише текстові значення payload, жодних видалень чи інших колонок; поза стиранням оновлення відхиляється. Лишаються з персональними даними: рахунки (з незмінним `recipient_snapshot`), договори, замовлення, підписані оригінали (Art. 17 Abs. 3 lit. b), запис родича-платника в обсязі вище. Якщо стерта карта сама є платником рахунку чи замовлення іншого пацієнта (`payer_patient_id`), випущені рахунки зберігають зафіксованого одержувача (`recipient_snapshot`), а чернетки рахунків і замовлення відтепер показують анонімну мітку (їхній одержувач читається з карти наживо) — це свідомо (рішення 2026-10-12).

**Вивантаження даних (Art. 15, рішення власника 2026-10-12).** Є два вивантаження з однією структурою (JSON або ZIP з файлами документів): вивантаження для персоналу, що веде запит (`GET /admin/compliance/patient/{id}/export`, CEO або PM видимого пацієнта), і власне вивантаження пацієнта в порталі (`GET /me/export`). Внутрішні примітки кошторисів і рахунків (`quotes.internal_note`, `invoices.internal_note`, «Внутренняя заметка (не печатается)») — теж персональні дані про пацієнта. Тому вивантаження для персоналу містить їх у полі `internal_note` кожного кошторису й рахунку: відповідальний переглядає вивантаження й передає його суб'єкту як відповідь на запит. Портальне вивантаження їх не містить, як і будь-що інше, що пацієнт бачить напряму (картка рахунку в порталі, PDF, e-рахунок). Подія аудиту `dsgvo_data_export` фіксує `internal_notes_included` (`true` лише для вивантаження персоналу).

Кроки (Art. 12, 19) записуються окремо й статус не змінюють: перевірка особи (портал, документ, дзвінок, підписаний лист, особисто), продовження строку (лише для відкритого), повідомлення суб'єкта і отримувачів (e-mail, портал, пошта, телефон, особисто). Застарілий прямий `POST /admin/compliance/patient/{id}/anonymize` прибрано (QA 2026-10-11): стирання можливе лише через реєстр (запит → рішення → за потреби перевірка особи → виконання) з усіма перевірками. Старі записи реєстру, створені ним, і далі показуються з позначкою «Прямое удаление (старый путь)» / «Direkte Löschung (alt)» і `manual_override`.

## 13. Сесія (`token_families`)

Активна → відкликана (вихід, «выйти везде», скидання пароля/TOTP, деактивація, зміна ролі, крадіжка refresh-токена, примусово адміністратором — не для CEO від IT; `session_limit` — новий вхід понад `max_sessions_per_user` (10) закриває найдавніше використану сесію; `idle_timeout` — без оновлення довше `session_idle_days` (7), перевіряється при оновленні й сканером; `expired` — refresh-токен сплив) або спливла (refresh 30 днів, продовжується при кожному оновленні; access 60 хв). Сканер кожні 15 хв позначає прострочені й неактивні сесії відкликаними, тож кількість активних сесій (адмінка, стан системи) правильна (рішення власника 2026-09-28, Q12). У браузері — вихід після 30 хв неактивності. «Онлайн» — лише персонал з активністю за 15 хв.

## 14. Сповіщення, оголошення, відгуки, чат

**Сповіщення** (`user_notifications`): непрочитане → прочитане (одне або «Отметить все прочитанными» / «Alle als gelesen markieren»); лічильник дзвіночка — кожні 20 с. Запит DSGVO відкривається в реєстрі DSGVO (CEO, IT), інцидент — на сторінці інцидентів.

Мова сповіщень (QA 2026-10-11, A-23/E-16/E-33): сервер зберігає стабільний код (`kind`) і факти (`params`, JSONB: імена, дати, лічильники, коди статусів і джерел — міграція `20261011233000_user_notification_params.sql`, також для тригера «новий лід»); дзвіночок, сторінка «Мои уведомления» порталу й push-сповіщення пристрою формулюють текст мовою інтерфейсу глядача (RU/DE, `frontend/src/lib/notification-copy.ts` і `components/topbar-data.ts`). Коди джерел ліда («manual», «website» …) перекладаються. `title`/`body` лишаються англійським запасним текстом: для старих рядків без `params` факти зчитуються з відомих англійських шаблонів, невідомий текст показується як є. Сповіщення, які бачить пацієнт або лід, не містять причин санкцій чи ризику; сповіщення оцінки ризику отримують лише перевіряючі.

Журнал активності (`/admin/activity`) і сторінка безпеки (`/admin/security`) мають назву для кожного коду аудиту сервера (`frontend/src/lib/i18n/catalogs/audit-activity.ts`); новий, ще не перекладений код показується «олюдненим» (`update_invoice_status` → «Update invoice status»), а не «Неизвестное значение». Лічильник «Изменений данных / Datenänderungen» за 24 год рахує всі змістовні записи, що змінюють дані: рядок з HTTP-методом — лише POST/PUT/PATCH/DELETE, доменна подія без методу — якщо це не читання, перегляд, експорт, завантаження файлу чи подія входу/сесії (`ACTIVITY_DATA_CHANGE_FILTER`). На сторінці безпеки причина підозрілої події приходить кодом (`reason_code`) і перекладається; лічильники вгорі дорівнюють кількості рядків списків під ними (останні 25 підозрілих подій, останні 100 входів).

**Оголошення** (`announcements`): показується користувачам своєї аудиторії, коли ввімкнене, у вікні `starts_at`–`ends_at` і не приховане ними. Аудиторія (`audience`, «Аудитория»/«Zielgruppe»): `staff` «Сотрудники»/«Mitarbeitende», `patients` «Пациенты (портал)»/«Patienten (Portal)», `all` «Все»/«Alle» (типово; наявні оголошення отримали `all`, бо досі бачили всі). Оголошення рівня «Ошибка»/«Fehler» (`error`) не можна приховати, поки воно активне (409), кнопки приховування немає (рішення власника 2026-09-28, Q15). Статус у адмінці: «Активно»/«Aktiv», «Запланировано»/«Geplant», «Истекло»/«Abgelaufen», «Неактивно»/«Inaktiv». Створення, зміна, видалення, приховування — з аудитом; керує `admin.announcements` (CEO, IT).

**Відгук** (`patient_feedback_forms`): `submitted` «Отправлено»/«Eingereicht» → `reviewed` «Проверено»/«Geprüft» або `archived` «В архиве»/«Archiviert» (з будь-якого стану). Розглядають CEO, PM, TL (оцінки перекладачів), консьєрж (оцінки сервісу) у межах свого доступу; Assistant лише читає (403). Нотатка перевірки (`review_note`) внутрішня: портал пацієнта і realtime-подія `feedback.reviewed` її не містять (рішення власника 2026-09-28).

**Чат** (`direct_messages`): надіслано → прочитано («Прочитано»/«Gesehen»); видалено відправником; зникло за таймером (перевірка щохвилини); редаговано при видаленні даних пацієнта.

## 15. Провайдер, персонал провайдера, перекладач

| Поле | Значення | RU | DE |
|---|---|---|---|
| `providers.is_active` | активний / неактивний | Активен / Неактивен | Aktiv / Inaktiv |
| договір (`kooperationsvertrag` заповнено) | є / нема | Договор | Vertrag |
| `provider_staff.status` | `active`, `inactive`, `external`, `unknown` | Активен, Неактивен, Внешний, Неизвестно | Aktiv, Inaktiv, Extern, Unbekannt |
| статус перекладача | `active`, `vacation`, `sick`, `training`, `blocked`, `terminated` | Активен, Отпуск, Больничный, Обучение, Заблокирован, Уволен | Aktiv, Urlaub, Krank, Training, Gesperrt, Beendet |
| AVV / конфіденційність перекладача | підписано / очікує, підписано / відсутнє | Подписано / Ожидает | Unterzeichnet / Ausstehend |

Активувати/деактивувати провайдера — CEO, PM (аудит). Видалення — архівування (рішення власника 2026-09-28, Q11): провайдер стає неактивним з `archived_at`, лишається в прийомах, послугах, відкриттях і рахунках, у реєстрі видимий лише з фільтром «Неактивен»; «Активировать» повертає його з архіву (аудит `archive_provider`). Неактивний чи архівний провайдер не пропонується у списках за замовчуванням і блокує бронювання консьєржа, ціни, витрати й передачу документів, а також (422) нові прийоми (створення, конвертація запиту, запит з порталу, зміна провайдера), нові послуги замовлення й учасників групи послуг, нові консьєрж-сервіси чи зміну їхнього провайдера; наявні записи зберігають провайдера. Персонал провайдера зі статусом `external`/`unknown` не може увійти. Перекладач (і тимлід) зі статусом `blocked`/`terminated` або зовнішній (`external` чи договір `freelancer`) без підписаного AVV не отримує нових призначень (422): бронювання на прийом, призначення перекладача, запит на переклад, прив'язка до пацієнта; у виборі перекладача й підказках його немає (лишається, якщо вже вибраний), наявні призначення зберігаються (Q11). Зміни профілю перекладача аудитуються (`update_interpreter_profile`). Список документів провайдера показує документи пацієнтів і медичні документи лише тим, хто може відкрити їх за звичайними правилами документів.

Пропускає карти з `clinical_retention_until` у майбутньому і карти, чий запит від перевірки відхилено після поточного `inactive_since` (рішення власника 2026-09-28). |
