# Статуси: записи, документи, приватність і доступ

Довідник для тестувальників: статуси, переходи і побічні ефекти пацієнтів, документів, запитів DSGVO, облікових записів і партнерів. Відповідає коду гілки аудиту статусів (вересень 2026). Мітки RU/DE — як у інтерфейсі. «Хто» — ролі, яким сервер дозволяє перехід; приховування кнопки в UI сервер не замінює.

Скорочення ролей: CEO, CEO Assistant (далі Assistant), PM (Patient Manager), TL (Teamlead Interpreter), IT (IT Admin). 423 = «запис заблоковано» (Art. 18 / анонімізація), 409 = конфлікт стану.

## 1. Пацієнт (`patients`)

Статус — пара `lifecycle_status` + `is_active` (записуються разом), прапори DSGVO — у `legal_status`.

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `active` | Активен | Aktiv | Робоча карта (`is_active = true`). |
| `inactive` | Неактивен | Inaktiv | Карта закрита; `inactive_since` запускає строк зберігання. |
| `prospective` | Заявитель (фільтр «Заявители») | Interessent («Interessenten») | Проспект із ліда, `is_active = false`; у списку лише за фільтром (CEO, PM). |
| `deleted` | Удалён | Gelöscht | Лише в CHECK і фільтрі; сервер його не записує. |
| `legal_status.processing_restricted = true` | банер «Обработка данных ограничена (ст. 18 DSGVO)» | «Verarbeitung eingeschränkt (Art. 18 DSGVO)» | Карту можна зберігати й читати, змінювати — ні. |
| `legal_status.anonymized_at` | — (ПІБ і PID = `ANON-…`) | — | Залишок після виконаного видалення (Art. 17). |

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → `active` | CEO, PM: створення пацієнта | Творець отримує прив'язку `manual`. |
| — → `prospective` | Лід (identity-first) | Хард-видалення разом із лідом, поки лід не конвертовано. |
| `prospective` → `active` | Конвертація ліда (`leads.convert`) | — |
| `inactive` → `active` | Конвертація повторного ліда на існуючого пацієнта | `inactive_since` очищається. |
| `active` → `inactive` | CEO, PM: «Деактивировать пациента» / «Patient deaktivieren» | Ставить `inactive_since = now()`. Обмежена чи анонімізована карта — 423, `prospective` — 409. |
| `inactive` → `active` | CEO, PM: «Активировать пациента» / «Patient aktivieren» | Очищає `inactive_since`. Обмежена чи анонімізована — 423. |
| → обмежена | Виконання запиту `restriction` (CEO, IT) | Див. §9. |
| обмежена → знята | CEO, IT: «Снять ограничение» / «Einschränkung aufheben», причина 10–2000 символів | Аудит `processing_restriction_lifted`, подія в хронології. |
| → анонімізована | Виконання запиту `erasure` (CEO, IT) | `is_active = false`, `active` → `inactive`, `inactive_since` ставиться, якщо не було; усі прив'язки й згоди відкликаються, некомерційні файли видаляються, чат редагується. |
| видалення пацієнта | — | Завжди 409 (пряме видалення вимкнено). |

Обмежена або анонімізована карта: усі зміни пацієнта, його клінічних даних, прив'язок (крім відкликання), зміна/видалення/нове завантаження його документів персоналом і передача документів провайдерам — 423. Відкликати прив'язку можна завжди. Перемикач статусу в картці показується лише CEO/PM з `patients.edit`, не для `prospective`, обмеженої чи анонімізованої карти; решта бачить статус без меню.

Хронологія пацієнта показує «Карта пациента активирована/деактивирована» / «Patientenakte aktiviert/deaktiviert», події запитів DSGVO і згод (див. §9, §11).

## 3. Документ (`documents`)

| Поле / ключ | RU | DE | Значення |
|---|---|---|---|
| `status = draft` | Черновик | Entwurf | Скан «на разбор», завантаження перекладача, шаблон до підписання. |
| `status = active` | Активный | Aktiv | Робочий документ. |
| `status = archived` | Архивный | Archiviert | Замінений новою версією або файл видалено. |
| `visibility = internal` | Внутренний | Intern | Лише персонал. |
| `visibility = released_internal` | Выпущен внутренне | Intern freigegeben | Відкритий усередині компанії. |
| `visibility = released_external` | Выпущен внешне | Extern freigegeben | Можна передавати зовнішнім отримувачам. |
| `visibility = patient_visible` | Виден пациенту | Für Patienten sichtbar | Пацієнт бачить за наявності активного відкриття. |
| файл видалено (`file_deleted_at`) | — | — | `archived` + `internal`, файл прибрано. |

Похідні стани: **«на разбор»** (черга класифікації: без категорії, `portal_upload`, загальний тип, завантаження з порталу, скан `manual_intake` у `draft`, завантаження перекладача в `draft`; не `archived`; до 200 рядків), **перевірка тимліда** (завантаження перекладача у `draft`), **остання версія** (немає новішої, що її замінює).

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → `draft`/`active` | Завантаження персоналом | Скан `manual_intake` і завантаження перекладача — завжди `draft`; завантаження з порталу — `active` + `internal`. Для обмеженої/анонімізованої карти — 423. |
| будь-який → будь-який (`status`, `visibility`) | CEO, PM (TL — лише перевірка скану: у `active`, видимість `internal`) | Скан `manual_intake` → `active` лише з прив'язкою і класифікацією. Обмежена/анонімізована карта — 423. Аудит `update_document`. |
| `draft` → `active` | CEO, PM: «отметить подписанным» | Не для архівного чи видаленого файлу. |
| → `archived` + файл видалено | CEO, PM (Billing — лише власний незавершений імпорт рахунку), причина обов'язкова | 409, якщо були відкриття, підпис чи ознайомлення; 423 для обмеженої/анонімізованої карти. |
| остання версія → `archived` | Нова версія з шаблону | Кнопка «Новая версия» / «Neue Version» лише для останньої неархівної версії; відкриття в порталі старої версії відкликаються. |
| медична категорія → медичний | Автоматично при кожному збереженні | Рішення власника 2026-09-28 (див. RBAC). |

## 4. Відкриття документа (`document_shares`) і портал

Окремого статусу немає: відкриття **активне** (`revoked_at` порожній), **очікує підтвердження** (`requires_confirmation` без `confirmed`), **підтверджене**, **відкликане**.

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → активне (персоналу чи провайдеру) | Ролі з `documents.manage` + доступ до документа | Провайдер: активний, офіційний канал, не `internal`/`released_internal`, карта не обмежена/не анонімізована. Канали пацієнта (e-mail, телефон, WhatsApp, пошта) — лише з активною згодою на канал. |
| активне → підтверджене | Отримувач; CEO/PM від його імені — лише з доступом до документа | Зберігається час першого підтвердження; відкликане не підтверджується. |
| активне → відкликане | `documents.manage` | Аудит `revoke_document_share`. |
| відкриття в порталі | CEO, PM | `visibility` → `patient_visible` + відкриття для активного користувача порталу; архівний документ — 422. |
| відкликання з порталу | CEO, PM | Відкриття пацієнту відкликаються, `visibility` не змінюється. |

Журнал відкриттів бачать лише CEO, PM, TL.

## 5. Запит на переклад (`document_translation_requests`)

| Ключ | RU | DE |
|---|---|---|
| `pending` | Запрошен | Angefordert |
| `in_progress` | В работе | In Bearbeitung |
| `completed` | Завершён | Abgeschlossen |
| `cancelled` | Отменён | Abgebrochen |

| З | Дозволено в | Хто |
|---|---|---|
| `pending` | `in_progress`, `completed`, `cancelled` | CEO, PM, TL, перекладач, консьєрж із правом редагування документа |
| `in_progress` | `completed`, `cancelled`, `pending` | те саме |
| `completed` | `in_progress` | CEO, TL |
| `cancelled` | `pending` | як для `pending` |

`completed` потребує перекладеного тексту. Перекладач діє лише над своїм або непризначеним запитом (кнопка «Взять себе» / «Mir zuweisen» — лише для непризначених). Один відкритий запит на документ і мову: повторне відкриття за наявності іншого — 409; зміна, яку вже змінив інший, — 409. Машинний переклад синхронний (без черги): чернетка лише для `pending`/`in_progress`. Переклад запиту з порталу пацієнта автоматично відкривається пацієнту.

## 6. Електронний підпис (`document_signature_requests`, Skribble)

| Ключ | RU (панель) | DE (панель) | Значення |
|---|---|---|---|
| `submitting` | Отправка приглашений | Einladungen werden versendet | Запит збережено, надсилається. |
| `submission_unknown` | Проверяем отправку — повторно не отправляйте | Versand wird geprüft – bitte nicht erneut senden | Відповідь провайдера невідома (пакети — завжди через цей стан). |
| `pending` | Ожидание подписей | Unterschriften ausstehend | Чекає підписантів. |
| `completed` | PDF и отчёт сохранены (у списку «Подписано») | PDF und Protokoll gespeichert («Unterzeichnet») | Підписаний PDF збережено новою версією. |
| `needs_review` | Исходный документ изменён — нужна проверка | Ausgangsdokument geändert – Prüfung erforderlich | Підписано, але джерело змінилося під час підписання. |
| `declined` | Подписание отклонено | Unterschrift abgelehnt | Відхилено підписантом. |
| `withdrawn` | Запрос отозван | Anfrage zurückgezogen | Відкликано. |
| `expired` | Срок запроса истёк | Anfrage abgelaufen | Строк сплив у Skribble. |
| `error` | Ошибка подписания | Signatur fehlgeschlagen | Помилка провайдера. |

| Перехід | Хто / як | Аудит |
|---|---|---|
| — → `submitting` | CEO, PM з правом редагування документа | `document_signature_requested` |
| `submitting` → `pending` / `submission_unknown` / `error` | Автоматично після надсилання; завислий `submitting` (оренда 5 хв) → `submission_unknown` | — |
| `submission_unknown` → `pending`; `pending` → `declined`/`withdrawn`/`expired`/`error` | Опитування Skribble кожні 30 с (повтор через 1 хв, після помилки через 2 хв) | `document_signature_status_changed` (без користувача) |
| `pending`/`submission_unknown` → `completed`/`needs_review` | Опитування: підписано | `document_signature_archived` |
| `pending` → (Skribble) відкликано | CEO, PM: «Отозвать» | `document_signature_withdrawn`, далі опитування |

Кінцеві стани: `completed`, `needs_review`, `declined`, `withdrawn`, `expired`, `error` — після них можна створити новий запит. Локального строку дії немає. Активний запит блокує новий запит на документ і відключення облікового запису Skribble.

## 7. Імпорт клінічного документа (`clinical_document_imports`) і BMP

| Ключ | RU | DE |
|---|---|---|
| `queued` | В очереди | In Warteschlange |
| `processing` | Обрабатывается | Wird verarbeitet |
| `review_required` | Готово к проверке | Bereit zur Prüfung |
| `applying` | Применение зафиксировано | Übernahme vorbereitet |
| `applied` | Добавлено в карту | Übernommen |
| `failed` | Ошибка | Fehlgeschlagen |

Усі дії — лише CEO з доступом до пацієнта.

| Перехід | Як | Аудит |
|---|---|---|
| — → `queued` | Запит розпізнавання медичного документа (повтор повертає відкритий імпорт) | `clinical_document_import_requested` |
| `queued` → `processing` → `review_required`/`failed` | Окремий парсер (опитування 2 с, оренда 900 с; завислий `processing` підхоплюється знову) | — |
| `failed` → `queued` | «Повторить» | `clinical_document_import_retried` |
| `review_required`/`failed` → `queued`; `applied` → новий `queued` | «Распознать заново» | `rescan_clinical_document_import` |
| `review_required` → `applying` | Підтвердження перевірки | `clinical_document_import_prepared` |

| будь-який, крім `applying` → видалено | Видалення | `clinical_document_import_deleted` |

BMP (план медикації): попередній перегляд і підтвердження синхронно, збережений стан лише `confirmed` (аудит `bmp_carrier_import_confirmed`).

## 8. AI-аналіз медикації (`medication_ai_analyses`)

| Ключ | Панель (RU / DE) |
|---|---|
| `requested` | AI-анализ ожидает обработки… / Die KI-Analyse wartet auf Verarbeitung… |
| `processing` | AI обрабатывает обезличенные доказательства… / Die KI verarbeitet die de-identifizierte Evidenz… |
| `ready` | показується чернетка |
| `failed` | AI-анализ не прошёл безопасную обработку… / Die KI-Analyse konnte nicht sicher verarbeitet werden… |

Запит (CEO) → `requested`; воркер кожні 2 с: `requested` → `processing` (оренда 75 с, спроба +1, максимум 3) → `ready` / назад у `requested` (повтор із затримкою) / `failed`; прострочена оренда повертає в `requested` або `failed`. «Повторить» (CEO): `failed` → `requested`, лише для тієї самої моделі, промпта й governance. Переходи тригер БД контролює, кожен пише подію життєвого циклу; `ready`/`failed` — аудит і сповіщення. Якщо AI вимкнено, воркер не стартує.

## 9. Запит суб'єкта даних (`patient_privacy_requests`)

| Тип | RU (реєстр) | DE (Register) |
|---|---|---|
| `erasure` | Удаление данных (ст. 17) | Löschung (Art. 17) |
| `restriction` | Ограничение обработки (ст. 18) | Einschränkung der Verarbeitung (Art. 18) |
| `access` | Запрос на доступ к данным (ст. 15) | Auskunft (Art. 15) |
| `rectification` | Исправление данных (ст. 16) | Berichtigung (Art. 16) |
| `portability` | Перенос данных (ст. 20) | Datenübertragbarkeit (Art. 20) |
| `objection` | Возражение против обработки (ст. 21) | Widerspruch (Art. 21) |
| `third_party_revoke` | Отзыв передачи третьим лицам | Widerruf der Drittweitergabe |

| Статус | RU | DE | Значення |
|---|---|---|---|
| `requested` | Запрошено | Angefordert | Новий, чекає рішення. |
| `retention_hold` | Удержание по хранению | Aufbewahrungssperre | Відкладено через обов'язок зберігання (`retention_until`). |
| `approved` | Одобрено | Genehmigt | Погоджено, чекає виконання. |
| `rejected` | Отклонено | Abgelehnt | Кінцевий. |
| `completed` | Завершено | Abgeschlossen | Виконано, кінцевий. |

Джерело: `patient_request` — «Запрос пациента» / «Patientenantrag», `admin_intake` — «Ввод администратором» / «Admin-Erfassung» (у порталі «Рабочая область команды» / «Team-Workspace»), `legal_hold` — «Юридическое удержание» / «Rechtliche Sperre».

Строк: `due_at` = створення + `patient_erasure_due_days` (типово 30) для всіх типів; відкритий запит після строку позначається «Просрочено» / «Überfällig»; одноразове продовження +60 днів із причиною ≥ 10 символів.

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → `requested` | Персонал: CEO, IT, PM (видимий пацієнт); пацієнт — у порталі; щоденна перевірка строку зберігання | Один відкритий запит кожного типу на пацієнта (409). Аудит `privacy_request_created`. |
| `requested`/`retention_hold` → `approved`/`rejected`/`retention_hold` | CEO, IT, PM: розгляд | `retention_hold` ставить `retention_until` (типово +3650 днів). Паралельне рішення — 409. Аудит `privacy_request_reviewed`. |
| `approved` → `completed` | CEO, IT (PM — лише `access`, `rectification`, `portability`, `objection`, `third_party_revoke`) | `restriction` → обмежує карту; `erasure` → анонімізація; `third_party_revoke` → відкликає згоди `dsgvo_data_transfer`, `third_party_sharing`, `schweigepflicht_release` і відкриття провайдерам; інші типи фіксують ручне виконання. Повторне виконання — 409. Аудит `privacy_request_executed`. |
| `completed`/`rejected` → … | — | Повторного відкриття немає. |

Кроки (Art. 12, 19) записуються окремо й статус не змінюють: перевірка особи (портал, документ, дзвінок, підписаний лист, особисто), продовження строку (лише для відкритого), повідомлення суб'єкта і отримувачів (e-mail, портал, пошта, телефон, особисто). Застарілий прямий `…/anonymize` створює запит одразу `approved` → `completed` (`manual_override`).

## 10. Інцидент безпеки (`security_incidents`, Art. 33)

| Статус | RU | DE |
|---|---|---|
| `open` | открыт | offen |
| `contained` | локализован | eingedämmt |
| `resolved` | устранён | behoben |
| `closed` | закрыт | abgeschlossen |

Тяжкість: низкая/gering, средняя/mittel, высокая/hoch, критическая/kritisch. Оцінка ризику: `pending` «ещё не оценён» / «noch nicht bewertet», `no_risk`, `risk`, `high_risk` (з поясненням дії). Строк повідомлення: «Когда стало известно» / «Kenntnis seit» + 72 год. Позначки: «Решение задокументировано» (є дата повідомлення органу або причина не повідомляти), «срок 72 ч пропущен» / «72-h-Frist überschritten» (рішення нема, строк минув), інакше «осталось N ч».

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → `open` | Будь-хто з персоналу («Сообщить об инциденте») | Час обізнаності можна вказати (не в майбутньому), порожній = зараз. Сповіщення CEO і IT з терміном за берлінським часом (`ДД.ММ.РРРР ГГ:ХХ`). Аудит `security_incident_reported`. |
| будь-який → будь-який | CEO, IT | До `closed` — лише з датою повідомлення органу або причиною не повідомляти (409). Аудит `security_incident_updated`. |

## 11. Згода (`consent_records`)

Окремого статусу немає; стан рядка історії:

| Стан | RU | DE | Значення |
|---|---|---|---|
| діє | действует | aktiv | Найновіший дозвіл цього типу, не відкликаний, строк не минув. |
| сплив | истекло | abgelaufen | Найновіший дозвіл, `expires_at` минув. |
| замінено | заменено | ersetzt | Дозвіл, після якого надано новий. |
| відкликано | отозвано | widerrufen | Запис відкликання або дозвіл, після якого його відкликали. |

Надати/відкликати (CEO, PM): попередній дозвіл закривається і пишеться новий рядок в одній транзакції; строк типово 365 днів. Автоматично: підписання документа дає `dsgvo_data_transfer`, `schweigepflicht_release`, `treatment_contract` (+1 рік); конвертація ліда; видалення відкликає всі; `third_party_revoke` — три типи. Строк перевіряється під час читання, фонового завдання немає. Канали передачі пацієнту (e-mail, телефон, WhatsApp, пошта) потребують діючої згоди каналу. У хронології: «Согласие дано» / «Einwilligung erteilt», «Согласие отозвано» / «Einwilligung widerrufen».

## 13. Сесія (`token_families`)

Активна → відкликана (вихід, «выйти везде», скидання пароля/TOTP, деактивація, зміна ролі, крадіжка refresh-токена, примусово адміністратором — не для CEO від IT) або спливла (refresh 30 днів, продовжується при кожному оновленні; access 60 хв). У браузері — вихід після 30 хв неактивності. «Онлайн» — лише персонал з активністю за 15 хв.

## 14. Сповіщення, оголошення, відгуки, чат

**Сповіщення** (`user_notifications`): непрочитане → прочитане (одне або «Отметить все прочитанными» / «Alle als gelesen markieren»); лічильник дзвіночка — кожні 20 с. Запит DSGVO відкривається в реєстрі DSGVO (CEO, IT), інцидент — на сторінці інцидентів.

**Оголошення** (`announcements`): показується користувачам, коли ввімкнене, у вікні `starts_at`–`ends_at` і не приховане ними. Статус у адмінці: «Активно»/«Aktiv», «Запланировано»/«Geplant», «Истекло»/«Abgelaufen», «Неактивно»/«Inaktiv». Створення, зміна, видалення, приховування — з аудитом; керує `admin.announcements` (CEO, IT).

**Відгук** (`patient_feedback_forms`): `submitted` «Отправлено»/«Eingereicht» → `reviewed` «Проверено»/«Geprüft» або `archived` «В архиве»/«Archiviert» (з будь-якого стану). Розглядають CEO, PM, TL (оцінки перекладачів), консьєрж (оцінки сервісу) у межах свого доступу; Assistant лише читає (403).

**Чат** (`direct_messages`): надіслано → прочитано («Прочитано»/«Gesehen»); видалено відправником; зникло за таймером (перевірка щохвилини); редаговано при видаленні даних пацієнта.

## 17. Відомі обмеження (очікують рішення власника)

- Відхилений запит `erasure` від перевірки строку зберігання створюється знову наступного дня; перевірка не враховує `clinical_retention_until`.
- Відхилення запиту DSGVO не вимагає причини, пацієнт її не бачить; погоджений запит не можна відхилити; перевірка особи не обов'язкова перед виконанням.
- Нагадувань про строки запитів DSGVO, 72 год інцидентів і сплив згод немає; закритий інцидент можна знову відкрити без причини; пізнє повідомлення органу не позначається.
- Обмеження (Art. 18) не перевіряється при створенні прийомів і замовлень, внутрішніх відкриттях документів, перекладі й відкритті в порталі; деактивувати обмежену карту не можна.
- Нове бронювання повертає доступ перекладачу, якому менеджер його відкликав.
- Відкликання згоди не відкликає вже зроблені відкриття; відкриття провайдерам згоди не перевіряють.
- Завантаження з порталу пацієнта лишаються в черзі «на разбор» і після класифікації.
- `submission_unknown` без ідентифікатора Skribble може лишатися назавжди; парсер повторює завислий документ без ліміту спроб.
- Статус/AVV перекладача не блокує призначення; неактивний провайдер приймається в нових прийомах і послугах.
