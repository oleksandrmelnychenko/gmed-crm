# Статуси: записи, документи, приватність і доступ

Довідник для тестувальників: статуси, переходи і побічні ефекти пацієнтів, документів, запитів DSGVO, облікових записів і партнерів. Відповідає коду гілки аудиту статусів (вересень 2026). Мітки RU/DE — як у інтерфейсі. «Хто» — ролі, яким сервер дозволяє перехід; приховування кнопки в UI сервер не замінює.

Скорочення ролей: CEO, CEO Assistant (далі Assistant), PM (Patient Manager), TL (Teamlead Interpreter), IT (IT Admin). 423 = «запис заблоковано» (Art. 18 / анонімізація), 409 = конфлікт стану.

## 1. Пацієнт (`patients`)

Статус — пара `lifecycle_status` + `is_active` (записуються разом), прапори DSGVO — у `legal_status`.

| Ключ | RU | DE | Значення |
|---|---|---|---|
| `active` | Активен | Aktiv | Робоча карта (`is_active = true`). |
| `inactive` | Неактивен | Inaktiv | Карта закрита; `inactive_since` запускає строк зберігання. |
| `prospective` | Заявитель (фільтр «Заявители») | Interessent («Interessenten») | Проспект із ліда, `is_active = false`; у списку лише за фільтром (CEO, PM). |
| `deleted` | Удалён | Gelöscht | Лише в CHECK і фільтрі; сервер його не записує. |
| `legal_status.processing_restricted = true` | банер «Обработка данных ограничена (ст. 18 DSGVO)» | «Verarbeitung eingeschränkt (Art. 18 DSGVO)» | Карту можна зберігати й читати, змінювати — ні. |
| `legal_status.anonymized_at` | — (ПІБ і PID = `ANON-…`) | — | Залишок після виконаного видалення (Art. 17). |

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → `active` | CEO, PM: створення пацієнта | Творець отримує прив'язку `manual`. |
| — → `prospective` | Лід (identity-first) | Хард-видалення разом із лідом, поки лід не конвертовано. |
| `prospective` → `active` | Конвертація ліда (`leads.convert`) | — |
| `inactive` → `active` | Конвертація повторного ліда на існуючого пацієнта | `inactive_since` очищається. |
| `active` → `inactive` | CEO, PM: «Деактивировать пациента» / «Patient deaktivieren» | Ставить `inactive_since = now()`. Обмежену карту деактивувати можна (рішення власника 2026-09-28), анонімізовану — 423, `prospective` — 409. |
| `inactive` → `active` | CEO, PM: «Активировать пациента» / «Patient aktivieren» | Очищає `inactive_since`. Обмежена чи анонімізована — 423. |
| → обмежена | Виконання запиту `restriction` (CEO, IT) | Див. §9. |
| обмежена → знята | CEO, IT: «Снять ограничение» / «Einschränkung aufheben», причина 10–2000 символів | Аудит `processing_restriction_lifted`, подія в хронології. |
| → анонімізована | Виконання запиту `erasure` (CEO, IT) | `is_active = false`, `active` → `inactive`, `inactive_since` ставиться, якщо не було; усі прив'язки й згоди відкликаються, некомерційні файли видаляються, чат редагується. |
| видалення пацієнта | — | Завжди 409 (пряме видалення вимкнено). |

Обмежена або анонімізована карта: усі зміни пацієнта, його клінічних даних, прив'язок (крім відкликання), зміна/видалення/нове завантаження його документів персоналом і передача документів провайдерам — 423. Рішення власника 2026-09-28 (Art. 18): також 423 з поясненням «Processing of this patient's data is restricted (Art. 18 DSGVO): … is not possible until the restriction is lifted» для нових приймань (зокрема конвертації запиту з порталу), нових замовлень, відкриття документа персоналу чи перекладачу, призначення перекладу, збереження перекладеного документа (тож і автоматичного відкриття перекладу в порталі). Відкриття документа самому пацієнту дозволене. Відкликати прив'язку й деактивувати обмежену карту можна завжди. Перемикач статусу в картці показується лише CEO/PM з `patients.edit`, не для `prospective` і анонімізованої карти; для обмеженої — лише деактивація. У картці обмеженої карти кнопки нового приймання й замовлення не показуються, банер перелічує заблоковані дії.

Хронологія пацієнта показує «Карта пациента активирована/деактивирована» / «Patientenakte aktiviert/deaktiviert», події запитів DSGVO і згод (див. §9, §11).

| відкликана | Отозвано | Widerrufen | Доступу немає. |
| `source = manual` | — | — | Призначив менеджер; не спливає. |

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|

Запам'ятовується як ручне (`manually_revoked_at = revoked_at`, `revoked_by`): нове бронювання чи відповідь перекладача на бронювання доступ не повертають, доки менеджер не призначить знову (рішення власника 2026-09-28). Аудит `revoke_assignment` із `source`, `reason = manual`. TL кнопки не бачить. |
| — → активна `interpreter_booking` | Автоматично при бронюванні перекладача | Лише якщо поточне відкликання не ручне. Аудит у транзакції `grant_booking_patient_access`. |

| усі → відкликані | Виконання видалення (Art. 17) | — |

## 3. Документ (`documents`)

| Поле / ключ | RU | DE | Значення |
|---|---|---|---|
| `status = draft` | Черновик | Entwurf | Скан «на разбор», завантаження перекладача, шаблон до підписання. |
| `status = active` | Активный | Aktiv | Робочий документ. |
| `status = archived` | Архивный | Archiviert | Замінений новою версією або файл видалено. |
| `visibility = internal` | Внутренний | Intern | Лише персонал. |
| `visibility = released_internal` | Выпущен внутренне | Intern freigegeben | Відкритий усередині компанії. |
| `visibility = released_external` | Выпущен внешне | Extern freigegeben | Можна передавати зовнішнім отримувачам. |
| `visibility = patient_visible` | Виден пациенту | Für Patienten sichtbar | Пацієнт бачить за наявності активного відкриття. |
| файл видалено (`file_deleted_at`) | — | — | `archived` + `internal`, файл прибрано. |

Похідні стани: **«на разбор»** (черга класифікації: без категорії, категорія `portal_upload`, неконкретний тип — `document`, `uploaded_document` і кожен тип завантаження з порталу `patient_*_upload`, — скан `manual_intake` у `draft`, завантаження перекладача в `draft`; не `archived`; до 200 рядків; походження `ursprung` не враховується: класифіковане завантаження з порталу, тобто з конкретним типом і категорією, з черги виходить — рішення власника 2026-09-28, Q8), **перевірка тимліда** (завантаження перекладача у `draft`), **остання версія** (немає новішої, що її замінює).

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → `draft`/`active` | Завантаження персоналом | Скан `manual_intake` і завантаження перекладача — завжди `draft`; завантаження з порталу — `active` + `internal`. Для обмеженої/анонімізованої карти — 423. |
| будь-який → будь-який (`status`, `visibility`) | CEO, PM (TL — лише перевірка скану: у `active`, видимість `internal`) | Скан `manual_intake` → `active` лише з прив'язкою і класифікацією. Обмежена/анонімізована карта — 423. Аудит `update_document`. |
| `draft` → `active` | CEO, PM: «отметить подписанным» | Не для архівного чи видаленого файлу. |
| → `archived` + файл видалено | CEO, PM (Billing — лише власний незавершений імпорт рахунку), причина обов'язкова | 409, якщо були відкриття, підпис чи ознайомлення; 423 для обмеженої/анонімізованої карти. |
| остання версія → `archived` | Нова версія з шаблону | Кнопка «Новая версия» / «Neue Version» лише для останньої неархівної версії; відкриття в порталі старої версії відкликаються. |
| медична категорія → медичний | Автоматично при кожному збереженні | Рішення власника 2026-09-28 (див. RBAC). |

## 4. Відкриття документа (`document_shares`) і портал

Окремого статусу немає: відкриття **активне** (`revoked_at` порожній), **очікує підтвердження** (`requires_confirmation` без `confirmed`), **підтверджене**, **відкликане**.

| Перехід | Хто / як | Умови й наслідки |
|---|---|---|
| — → активне (персоналу чи провайдеру) | Ролі з `documents.manage` + доступ до документа | Провайдер: активний, офіційний канал, не `internal`/`released_internal`, карта не обмежена/не анонімізована (423); після відкликання передачі третім особам (`legal_status.third_party_sharing_revoked_at`) — 422, доки не надано нову згоду `dsgvo_data_transfer`, `third_party_sharing` чи `schweigepflicht_release`. Персоналу й перекладачам — не для обмеженої карти (423). Канали пацієнта (e-mail, телефон, WhatsApp, пошта) — лише з активною згодою на канал; пацієнту — і для обмеженої карти. |
| активне → відкликане | Автоматично: відкликання згоди (CEO, PM) | `document_share_<канал>` відкликає відкрите пацієнту цим каналом; `dsgvo_data_transfer`, `third_party_sharing`, `schweigepflicht_release` — усі відкриті провайдерам і ставить `third_party_sharing_revoked_at`. У транзакції згоди, аудит `revoke_document_share_bundle` (`mode = consent_revoked`). |
| активне → підтверджене | Отримувач; CEO/PM від його імені — лише з доступом до документа | Зберігається час першого підтвердження; відкликане не підтверджується. |
| активне → відкликане | `documents.manage` | Аудит `revoke_document_share`. |
| відкриття в порталі | CEO, PM | `visibility` → `patient_visible` + відкриття для активного користувача порталу; архівний документ — 422. |
| відкликання з порталу | CEO, PM | Відкриття пацієнту відкликаються, `visibility` не змінюється. |

Журнал відкриттів бачать лише CEO, PM, TL.

## 5. Запит на переклад (`document_translation_requests`)

| Ключ | RU | DE |
|---|---|---|
| `pending` | Запрошен | Angefordert |
| `in_progress` | В работе | In Bearbeitung |
| `completed` | Завершён | Abgeschlossen |
| `cancelled` | Отменён | Abgebrochen |

| З | Дозволено в | Хто |
|---|---|---|
| `pending` | `in_progress`, `completed`, `cancelled` | CEO, PM, TL, перекладач, консьєрж із правом редагування документа |
| `in_progress` | `completed`, `cancelled`, `pending` | те саме |
| `completed` | `in_progress` | CEO, TL |
| `cancelled` | `pending` | як для `pending` |

`completed` потребує перекладеного тексту. Перекладач діє лише над своїм або непризначеним запитом (кнопка «Взять себе» / «Mir zuweisen» — лише для непризначених). Один відкритий запит на документ і мову: повторне відкриття за наявності іншого — 409; зміна, яку вже змінив інший, — 409. Машинний переклад синхронний (без черги): чернетка лише для `pending`/`in_progress`. Переклад запиту з порталу пацієнта автоматично відкривається пацієнту. Для обмеженої карти (Art. 18) призначення перекладача, збереження перекладеного документа і, отже, автоматичне відкриття в порталі — 423 (рішення власника 2026-09-28).

## 6. Електронний підпис (`document_signature_requests`, Skribble)

| Ключ | RU (панель) | DE (панель) | Значення |
|---|---|---|---|
| `submitting` | Отправка приглашений | Einladungen werden versendet | Запит збережено, надсилається. |
| `submission_unknown` | Проверяем отправку — повторно не отправляйте | Versand wird geprüft – bitte nicht erneut senden | Відповідь провайдера невідома (пакети — завжди через цей стан). |
| `pending` | Ожидание подписей | Unterschriften ausstehend | Чекає підписантів. |
| `completed` | PDF и отчёт сохранены (у списку «Подписано») | PDF und Protokoll gespeichert («Unterzeichnet») | Підписаний PDF збережено новою версією. |
| `needs_review` | Исходный документ изменён — нужна проверка | Ausgangsdokument geändert – Prüfung erforderlich | Підписано, але джерело змінилося під час підписання. |
| `declined` | Подписание отклонено | Unterschrift abgelehnt | Відхилено підписантом. |
| `withdrawn` | Запрос отозван | Anfrage zurückgezogen | Відкликано. |
| `expired` | Срок запроса истёк | Anfrage abgelaufen | Строк сплив у Skribble. |
| `error` | Ошибка подписания | Signatur fehlgeschlagen | Помилка провайдера. |

| Перехід | Хто / як | Аудит |
|---|---|---|
| — → `submitting` | CEO, PM з правом редагування документа | `document_signature_requested` |
| `submitting` → `pending` / `submission_unknown` / `error` | Автоматично після надсилання; завислий `submitting` (оренда 5 хв) → `submission_unknown` | — |
| `submission_unknown` → `pending`; `pending` → `declined`/`withdrawn`/`expired`/`error` | Опитування Skribble кожні 30 с (повтор через 1 хв, після помилки через 2 хв; відповідь 404 записується як `provider_not_found`) | `document_signature_status_changed` (без користувача) |
| `pending`/`submission_unknown` → `completed`/`needs_review` | Опитування: підписано; для `needs_review` — сповіщення відправнику й CEO | `document_signature_archived` |
| `pending` → (Skribble) відкликано | CEO, PM: «Отозвать» | `document_signature_withdrawn`, далі опитування |
| неможливо відстежити → `error` (`closed_kind = auto_expired`) | Автоматично (кожні 30 с): `submission_unknown` без ідентифікатора Skribble або `provider_not_found`, старший за `signature_stuck_request_days` (типово 3, максимум 90); здоровий `pending` не зачіпається. Сповіщення відправнику й CEO | `document_signature_closed_untrackable` (у транзакції) |
| `submission_unknown` / `pending` з помилкою опитування → `error` (`abandoned`) | CEO, PM з правом редагування документа або адміністратор підпису (`admin.signatures`): «Закрыть запрос как ошибочный» / «Anfrage als fehlgeschlagen schließen», причина 10–2000 символів; здоровий `pending` — лише «Отозвать» (409) | `document_signature_abandoned` (у транзакції) |
| `needs_review` → `completed` (`review_accepted`) / `error` (`review_rejected`) | CEO, PM з правом редагування: «Принять подпись» / «Unterschrift anerkennen», «Отклонить подпись» / «Unterschrift verwerfen», причина 10–2000 символів | `document_signature_review_resolved` (у транзакції) |

Кінцеві стани: `completed`, `needs_review`, `declined`, `withdrawn`, `expired`, `error` — після них можна створити новий запит. Хто, коли, як і чому закрив запит поза Skribble — `closed_kind`, `closed_by`, `closed_at`, `close_reason`; панель показує це під запитом. Активний запит блокує новий запит на документ і відключення облікового запису Skribble; завдяки строку й закриттю вручну він більше не блокує назавжди (рішення власника 2026-09-28, Q9).

## 7. Імпорт клінічного документа (`clinical_document_imports`) і BMP

| Ключ | RU | DE |
|---|---|---|
| `queued` | В очереди | In Warteschlange |
| `processing` | Обрабатывается | Wird verarbeitet |
| `review_required` | Готово к проверке | Bereit zur Prüfung |
| `applying` | Применение зафиксировано | Übernahme vorbereitet |
| `applied` | Добавлено в карту | Übernommen |
| `failed` | Ошибка | Fehlgeschlagen |
| `abandoned` | Применение прервано | Übernahme abgebrochen |

Усі дії — лише CEO з доступом до пацієнта.

| Перехід | Як | Аудит |
|---|---|---|
| — → `queued` | Запит розпізнавання медичного документа (повтор повертає відкритий імпорт) | `clinical_document_import_requested` |
| `queued` → `processing` → `review_required`/`failed` | Окремий парсер (опитування 2 с, оренда `PARSER_LEASE_SECONDS`, у релізному стеку 1200 с; кожне захоплення +1 до `attempts`; завислий `processing` підхоплюється знову, доки `attempts` < 3) | — |
| `processing` → `failed` | Парсер: оренда минула після 3 захоплень — помилка `CLINICAL_DOCUMENT_PARSER_ATTEMPTS_EXHAUSTED` (рішення власника 2026-09-28, Q10) | — |

Активна → відкликана (вихід, «выйти везде», скидання пароля/TOTP, деактивація, зміна ролі, крадіжка refresh-токена, примусово адміністратором — не для CEO від IT; `session_limit` — новий вхід понад `max_sessions_per_user` (10) закриває найдавніше використану сесію; `idle_timeout` — без оновлення довше `session_idle_days` (7), перевіряється при оновленні й сканером; `expired` — refresh-токен сплив) або спливла (refresh 30 днів, продовжується при кожному оновленні; access 60 хв). ## 14. Сповіщення, оголошення, відгуки, чат

**Сповіщення** (`user_notifications`): непрочитане → прочитане (одне або «Отметить все прочитанными» / «Alle als gelesen markieren»); лічильник дзвіночка — кожні 20 с. Запит DSGVO відкривається в реєстрі DSGVO (CEO, IT), інцидент — на сторінці інцидентів.

**Оголошення** (`announcements`): показується користувачам своєї аудиторії, коли ввімкнене, у вікні `starts_at`–`ends_at` і не приховане ними. Аудиторія (`audience`, «Аудитория»/«Zielgruppe»): `staff` «Сотрудники»/«Mitarbeitende», `patients` «Пациенты (портал)»/«Patienten (Portal)», `all` «Все»/«Alle» (типово; наявні оголошення отримали `all`, бо досі бачили всі). Оголошення рівня «Ошибка»/«Fehler» (`error`) не можна приховати, поки воно активне (409), кнопки приховування немає (рішення власника 2026-09-28, Q15). Статус у адмінці: «Активно»/«Aktiv», «Запланировано»/«Geplant», «Истекло»/«Abgelaufen», «Неактивно»/«Inaktiv». Створення, зміна, видалення, приховування — з аудитом; керує `admin.announcements` (CEO, IT).

**Відгук** (`patient_feedback_forms`): `submitted` «Отправлено»/«Eingereicht» → `reviewed` «Проверено»/«Geprüft» або `archived` «В архиве»/«Archiviert» (з будь-якого стану). Розглядають CEO, PM, TL (оцінки перекладачів), консьєрж (оцінки сервісу) у межах свого доступу; Assistant лише читає (403). Нотатка перевірки (`review_note`) внутрішня: портал пацієнта і realtime-подія `feedback.reviewed` її не містять (рішення власника 2026-09-28).

**Чат** (`direct_messages`): надіслано → прочитано («Прочитано»/«Gesehen»); видалено відправником; зникло за таймером (перевірка щохвилини); редаговано при видаленні даних пацієнта.

Видалення — архівування (рішення власника 2026-09-28, Q11): провайдер стає неактивним з `archived_at`, лишається в прийомах, послугах, відкриттях і рахунках, у реєстрі видимий лише з фільтром «Неактивен»; «Активировать» повертає його з архіву (аудит `archive_provider`). Неактивний чи архівний провайдер не пропонується у списках за замовчуванням і блокує бронювання консьєржа, ціни, витрати й передачу документів, а також (422) нові прийоми (створення, конвертація запиту, запит з порталу, зміна провайдера), нові послуги замовлення й учасників групи послуг, нові консьєрж-сервіси чи зміну їхнього провайдера; наявні записи зберігають провайдера. Персонал провайдера зі статусом `external`/`unknown` не може увійти. Перекладач (і тимлід) зі статусом `blocked`/`terminated` або зовнішній (`external` чи договір `freelancer`) без підписаного AVV не отримує нових призначень (422): бронювання на прийом, призначення перекладача, запит на переклад, прив'язка до пацієнта; у виборі перекладача й підказках його немає (лишається, якщо вже вибраний), наявні призначення зберігаються (Q11). Зміни профілю перекладача аудитуються (`update_interpreter_profile`). Список документів провайдера показує документи пацієнтів і медичні документи лише тим, хто може відкрити їх за звичайними правилами документів.
