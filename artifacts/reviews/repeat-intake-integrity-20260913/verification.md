# Повторне звернення: виправлення цілісності

Дата: 13.09.2026. Продовження аудиту `../repeat-intake-deep-audit-20260912/report.md`.

## Реалізація

| Аудит | Виправлення |
|---|---|
| A01 | Прив'язування й створення повторного звернення перевіряють доступ менеджера до пацієнта до створення призначень. |
| A02 | Перехід на завершення не переписує медичну картку. Кожна явна медична зміна перевіряє ревізію знімка; конфлікт вимагає оновлення картки. |
| A03 | Перше збереження атомарно створює звернення, один епізод і одну чернетку замовлення для існуючого пацієнта. Читання/підготовка не запускають планування й платіжний контроль. Архівація скасовує чернетку; завершення підтверджує її. |
| A04 | Документи замовлення прив'язані до поточних дат, сторін, послуг і фінансових умов. Зміни скидають підписи; незмінені дані їх зберігають. PDF формується з даних сервера, повтор генерації повертає існуючий документ. Підпис застарілої версії відхиляється. |
| A05 | Кнопка повторного звернення пропонує продовжити збережені звернення. Активна чернетка відкривається також із таблиці замовлень пацієнта. Нове звернення створюється окремою явною дією. |
| A06 | Стабільний ключ першого збереження переживає втрату відповіді; паралельні повтори повертають один результат. |
| A07 | Медична операція має транзакційний ключ і відбиток даних. Повтор після збереження або невдалого повторного читання не додає рядків. Форма отримує серверні ID збережених записів. |
| A08 | Видалення передає конкретні ID під перевіркою ревізії. Видалені попередження/діагнози не повертаються через merge; медикаменти зберігають історію заміни. |

Повторні й одночасні запити на актуальний кошторис також повертають одну версію.

Додатково: новий договір звернення можна прив'язати до його чернетки, яка вже належить пацієнту. Старий договір іншого пацієнта не допускається. Права на медичну картку збережені: якщо сервер забороняє доступ, візард показує це та дозволяє адміністративну роботу.

Однакові етапи й медичні форми основного візарда збережені. Перевірка старих документів показується тільки при вході «Повторне звернення» з пацієнта. Очікування передоплати не блокує оформлення.

## Перевірки

- Фронтенд: усі 180 файлів / 1 353 модульні тести пройшли.
- Playwright: 29 сценаріїв повторного звернення + 10 сценаріїв попереднього візарда пройшли.
- Playwright на сторінках застосунку: вхід із пацієнта та відсутність перевірки документів на лідах — 2/2.
- ESLint, TypeScript, виробнича збірка Vite, перевірка навігації й гігієни репозиторію пройшли. Vite повідомляє попередження про розмір деяких пакетів.
- Серверні тести: `leads_api` — 36/36; `contracts_quotes_api` — 19/19; клінічні round-trip, merge, експорт, права, атрибуція й походження даних — 7/7; переходи старого візарда `order_intakes_api` — 1/1.
- Модульні перевірки Rust для лідів, замовлень і документів — 29/29. Після останніх змін повторно пройшли атомарне створення/архівація та повний цикл документів, паралельних кошторисів і завершення.
- Старий API повторного звернення — 1/1: не може створювати зайві ліди. Разом пройшли 93 окремі серверні тести; повторні запуски не додані до цієї кількості.
- `cargo fmt --all -- --check` та `cargo clippy -p gmed-server --lib --tests --offline --locked -- -D warnings` пройшли. Це цільові перевірки сервера; повний workspace/release pipeline не запускався.
- Звірено вміст усіх 12 змінених серверних/міграційних файлів між локальним checkout та тестовою копією (з нормалізацією кінців рядків).

Додаткова перевірка перед релізом (13.09.2026): новий лід без існуючого пацієнта під роллю CEO створюється одним запитом із ключем повтору, зберігає введені дані, з’являється в таблиці й повторно відкривається без ще одного POST. Також пройшов сценарій повтору помилкового автозбереження. Актуалізовано роль та селектори старого тесту під поточний інтерфейс. Разом із попереднім прогоном — 43 браузерні сценарії.

## Середовище й міграція

Браузерні тести працюють на окремому localhost:5174 з перехопленими API-запитами та проксі на недоступний порт. Серверні тести використовують одноразовий PostgreSQL у внутрішній Docker-мережі, синтетичні дані й дозволений користувачем архів коду без секретів.

Міграція `20260913090000_repeat_intake_integrity.sql` додає ключі повторів, ревізію клінічної картки, контекст документів і скасування чернетки при архівації. Вона переводить старі незавершені повторні замовлення в чернетки лише за відсутності рахунків, прийомів і фактичних оплат; наявну історію не видаляє. Після зміни правил старі PDF без підтвердженого контексту потребують актуальної версії.

Clippy знайшов дві вкладені умови та функцію після тестового модуля; зауваження виправлено без зміни бізнес-поведінки. Наприкінці перевірки договорів одноразовому PostgreSQL забракло дискового простору для наступної БД. Звільнено лише 3,3 ГБ відтворюваного incremental-кешу Rust у тестовому Docker-томі й повторено невиконані перевірки. Після завершення також прибрано новий incremental-кеш. Робочі образи та томи не очищалися; одноразові контейнери завершені. У тестовому запуску PDF-фільтр спочатку не відібрав тестів; обидва тести потім запущені за фактичним ім’ям модуля й пройшли (див. завершальний журнал).

Журнали: [основний прогін](server-tests-initial.txt), [договори та кошториси](server-tests-quotes.txt), [завершальні перевірки](server-checks-final.txt). Фронтенд перевірено окремо локально.

Після очищення на DEV-вузлі залишалося близько 2,8 ГБ вільного місця (99% зайнято). Загальне очищення серверних образів/релізів до цієї зміни не входило.

Зміни не розгорнуті. Робоча DEV/PROD база не змінювалась.
