# Поглиблений аудит повторного звернення — 12.09.2026

> Оновлення 13.09.2026: усі 8 підтверджених дефектів виправлено; [реалізація та результати перевірок](../repeat-intake-integrity-20260913/verification.md). Нижче збережено висновки початкового аудиту.

Перевірено поточний незакомічений код у цьому checkout. Висновок: сценарій ще має **8 підтверджених проблем**, зокрема ризик перезапису медичних даних, обхід прив'язки доступів і створення зайвих звернень. Проходження базових тестів не означає відсутності цих дефектів.

Продуктовий код у межах цього аудиту не змінювався. Браузерні сценарії виконані на окремому Vite 5174 з усіма API замоканими; проксі спрямований у недоступний локальний порт. Серверні перевірки — у дозволеному ізольованому каталозі DEV, з одноразовим PostgreSQL, синтетичними записами та окремою внутрішньою мережею Docker. Робочі БД та розгортання не змінювалися.

## Фактичний шлях створення

| Дія | Що робить поточний код |
| --- | --- |
| Відкрити й закрити порожнє повторне звернення | Не створює записів. |
| Перше «Далі» / збереження | Створює лід, записує анкету, прив'язує наявного пацієнта, створює епізод і замовлення. |
| Повтор прив'язки в межах того самого lead_id | Повертає той самий епізод; новий пацієнт не створюється. |
| Повтор створення замовлення для того самого lead_id | Повертає те саме замовлення. |
| Закрити збережене звернення й знову натиснути кнопку в пацієнта | Починає новий лід; прив'язка й замовлення вже мають інший ключ. |
| Відкрити завершення з заповненою причиною звернення | Зберігає медичні секції й завершує медичний intake ще до фінального підтвердження. |

Сам факт окремого нового епізоду та замовлення для нової поїздки очікуваний. Проблема — відсутність надійного розрізнення нового звернення і продовження тієї самої чернетки, а також передчасна операційна активність.

## Підтверджені дефекти

### A01 · P1 · Прив'язка дозволяє менеджеру самому отримати доступ до чужого пацієнта

Сервер спочатку забороняє PM читати непризначеного йому пацієнта (`403`). Той самий PM може створити лід із відповідними ПІБ і датою народження та виконати `/prospect` з `attach_patient_id`. Обробник не перевіряє наявне право на цільового пацієнта перед `ensure_prospect_assignments`, а сам створює призначення. Після цього читання повертає `200`.

Це суперечить правилу «Patient Manager — власні пацієнти» в RBAC. Відтворено API-тестом `deep_audit_unassigned_patient_attach_grants_access`; реальні пацієнти не використовувалися.

Код: [перевірка кандидата і прив'язка](C:/Users/oleks/Developer/gmed/crates/server/src/routes/leads.rs:3607), [призначення](C:/Users/oleks/Developer/gmed/crates/server/src/routes/leads.rs:3664). Виправлення має перевіряти доступ до пацієнта **до** призначення; передача між менеджерами — окрема дозволена дія. Аналогічно перевірити гілку вже прив'язаного prospect.

### A02 · P1 · Відкриття завершення може перезаписати свіжі медичні дані старими

Сценарій: візард завантажив алергію з реакцією «Rash»; інший співробітник змінив реакцію; перший користувач, не редагуючи алергії, відкриває «Завершение обращения». Візард читає свіжий профіль, але `mergeWarnings` для збігу реального UUID накладає старий локальний запис поверх серверного. Потім `persistMedicalDraft` надсилає всі секції на збереження. У запиті знову йде «Rash».

Відтворено браузером із UUID v4 та перехопленням свіжого читання/наступного запису. Серверне збереження оновлює рядок за ID без перевірки очікуваної ревізії. Такий самий принцип накладання використовується для діагнозів і медикаментів; для них окремий браузерний сценарій не запускався.

Потрібні збереження лише явно змінених записів і контроль конфліктів; перегляд підсумку не повинен заново записувати незмінені медичні поля.

### A03 · P1 · Незавершене звернення створює активне замовлення, яке переживає архівацію

Після першого збереження реальний сервер створює `status='active'`, `intake_state='legacy'`, `patient_id=NULL`. Воно вже є в `order_payment_tracking`, має запис підготовки планування та відповідає умові підрахунку активних замовлень. Водночас `/patients/{id}/orders` повертає порожній список: він фільтрує за `patient_id`, а цей зв'язок встановлюється лише після конвертації.

Архівація звернення через «Не подходит» змінює лід, але залишає пов'язане замовлення активним. Перевірено на ізольованій базі. Наявність у контролі оплат сама по собі не означає створення рахунку або миттєве повідомлення: повідомлення додатково залежать від підписів/коштів.

### A04 · P1 · Зміна періоду не робить старі документи неактуальними

Після зміни сервер і далі повертає `conversion_ready=true`, а оформлення успішно завершується зі старими документами замовлення/кошторису й прапорцями підписання.

Готовність перевіряє наявність активного документа потрібного типу, але не відповідність версії поточному періоду. Оновлення дат не скидає підписи. Зміни складу/сум послуг мають окремі перевірки кошторису; підтверджена тут проблема саме дат і залежних документів.

### A06 · P2 · Втрата відповіді першого створення залишає зайвий лід

Якщо сервер уже вставив лід, але відповідь втрачена, клієнт ще не знає його ID. «Повторить» надсилає такий самий `POST /leads` без стабільного ключа операції. Сервер кожного разу виконує новий INSERT. Перша копія залишається неповною; наступна може пройти прив'язку й створення замовлення. Збої після отримання ID в межах того самого відкритого візарда обробляються краще — там ID зберігається.

Підтверджено браузерною імітацією обриву відповіді та двома однаковими запитами до реального сервера в одноразовій БД. Код: [отримання ID лише з відповіді](C:/Users/oleks/Developer/gmed/frontend/src/pages/leads/ui/lead-wizard.tsx:3596), [безумовний INSERT](C:/Users/oleks/Developer/gmed/crates/server/src/routes/leads.rs:1713). Потрібен стабільний ключ створення, який сервер зберігає атомарно разом із результатом.

### A07 · P2 · Повтор збереження нового медичного запису може створити дубль

У режимі `merge` відправлення нового запису без відомого серверного ID двічі створює два рядки. Перевірено окремо для алергії й діагнозу на реальному сервері. Ризик у візарді виникає, якщо запис уже відбувся, але відповідь або наступне читання профілю не вдалися: редактор зберігає початковий запис без ID, і повтор додає його знову.

Звичайне успішне послідовне редагування після отримання серверного ID не було визнано дефектним. Код: [збереження секції та подальше читання](C:/Users/oleks/Developer/gmed/frontend/src/pages/leads/ui/lead-wizard.tsx:3494), [генерація ID алергії](C:/Users/oleks/Developer/gmed/crates/server/src/routes/patients.rs:14207). Потрібен стабільний ID нового запису або ключ операції, який переживає повтор запиту.

### A08 · P2 · Видалення медичного запису не зберігається

Кнопка видалення прибирає елемент з масиву й викликає збереження. Повторне звернення завжди використовує `mode=merge`; сервер у цьому режимі не видаляє відсутні у масиві записи. Після повторного завантаження алергія повертається. Це підтверджено UI-запитом з порожнім масивом та окремим тестом збереження рядків у PostgreSQL.

## Що пройшло перевірку

- Відкриття без збереження не створює записи.
- Звичайний повтор прив'язки одного lead_id повертає той самий case_id; повтор створення його замовлення — той самий order_id.
- Успішне завершення використовує того самого пацієнта й не перезаписує його основні дані; старий анамнез зберігається окремою версією.
- Протермінований договір, договір з недостатнім покриттям періоду та договір іншого пацієнта не задовольняють серверні перевірки.
- Звірка документів прихована у звичайному вході з «Лідів» і присутня у вході з пацієнта; перевірені також реальні сторінки, не лише тестовий компонент.
- Паспортний строк зберігається окремою явною зміною; існують перевірки граничних дат.
