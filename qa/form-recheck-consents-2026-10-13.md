## Переглянуті межі без нового підтвердженого дефекту

- Власний вхід дитини не дає їй зберегти вибір; current choice також відкидає історичний self-choice, зроблений у неповнолітньому віці. Роль батьків, спільна/одноосібна опіка та guardian мають окремі required поля й докази.
- Другий із батьків може підтвердити той самий вибір від свого імені. Clean UI draft підхоплює новий вибір, dirty draft зберігає введення.
- За власного вибору згод дорослий і дитячий PDF друкують лише явно обраних отримувачів; старий paper fallback застосовується лише без власного choice.
- Package creation перевіряє потрібних за custody підписантів і присутність особи, яка зробила choice; payer/agency ролі не підміняють client signers. У native patient використовується `birth_date` і ті ж джерела представників, що й у suggestions.
- Новий choice закриває незавершені запити згод, очищає lease; completed history зберігається. Перевірка проти нового choice повторюється перед outbox, а provider callback враховує локальне скасування.
- Базове та повторне відправлення залишаються окремими часовими межами; відправлення додаткових даних не поглинає незавершені зміни базових персональних полів.
- Узгодження організаційних полів платника у payer PDF перевіряє й виправляє окремий агент; тут ці файли не змінювалися.

## Перевірки цього проходу

- 44 focused frontend unit tests пройшли: `lead-request-consent-save.test.ts`, `lead-request-consent-form.test.tsx`, `lead-request-follow-up-model.test.ts`, `lead-request-representation-model.test.ts`.
- Targeted ESLint чотирьох змінених frontend файлів пройшов.
- У першому повному `lead_portal_api` прогоні: 31/34 пройшли. Новий `representative_follow_up_tracks_files_and_requires_current_inquiry_consent` підтвердив R-D4/R-D5. Дві нові lock-регресії R-D2/R-D3 впали в test helper до перевірок API: `pg_stat_activity.query` обрізав довгий SQL перед `FOR UPDATE`, тому rendezvous не бачив блокування. Helper виправлено на точний PID блокувальника через `pg_blocking_pids`. Повторний запуск підтвердив R-D2 (`consent_choice_after_waiting_for_submission_is_a_new_change`) та existing blacklist follow-up сценарій.
- R-D3 у повторному запуску дійшов до assertion **після actual lock scenario**; `changed_since_answer=true` при зворотному стрибку DB wall clock. Початкова інтерпретація, ніби це assertion setup до lock, була помилкова. Щоб перевіряти саме порядок заблокованого запису незалежно від сторонніх setup timestamps, лише baseline мітки полів і uploads перенесено у фіксоване минуле до отримання lock, зі збереженням значень і файлів. Новий target marker та результат API не нормалізуються. Додано строге `answered_at > target statements.at`; початкові `changed=false`, незмінний повторний timestamp і одна подія залишені. Цільовий повторний запуск root пройшов: 1/1, включно зі строгим порівнянням target marker (лог `.tmp/form-recheck/rust-follow-up-final.log`). Сукупно всі 34 різні lead_portal_api сценарії пройшли. Зворотний стрибок між target marker та самим answer і надалі спричинить явне падіння з обома timestamp, а не буде замаскований retry.
- Координатор окремо зафіксував у real-API harness зворотні стрибки часу disposable Docker PostgreSQL; порівнювані portal timestamps у коді беруться з одного DB `clock_timestamp()`, не з годинника хоста. Real UI/API consent → canonical GET → send again пройшов із read-only DB-clock settle barrier та незмінними строгими assertions.
- 3 baseline browser сценарії GwG/self-disclosure пройшли після оновлення застарілих style/text assertions. 2 baseline consent сценарії пройшли після додавання відсутнього mock свіжого GET заявки; початкові assertions збережено. Артефакти: `.tmp/form-recheck/legal-results`, `.tmp/form-recheck/consent-fixture-results`.
- Live API/пацієнтські дані, parser training, міграції вже опублікованих версій не змінювалися. Комітів/деплоїв цей агент не робив.

Відомий окремий `409` для multi-child patient portal не розширювався. Exact remote-provider creation-vs-consent race лишається попередньо задокументованою межею: є локальні lease/closure тести, але немає окремого provider-delay harness. Цей повторний перегляд не підміняє агреговані release gates.
