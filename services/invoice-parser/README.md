# OCR інвойсів — окремий локальний сервіс

**Уточнення 2026-09-05:** обрана система **DATEV Unternehmen online**;
ціль — обмін із GMed в обидва боки, перший етап — перегляд без запису в DATEV.
Основний шлях — структуровані дані та оригінали документів; цей OCR-сервіс
є додатковим компонентом для PDF/сканів без доступних реквізитів.
Шаблони постачальників не є передумовою інтеграції.
[Поточна архітектура та наступні кроки](../../docs/architecture/datev-invoice-integration_ua.md).

Поточна реалізація: XML UBL/CII або XML-вкладення PDF → структуровані реквізити;
PDF/PNG/JPEG без доступного XML → текст → реквізити за шаблоном постачальника
або явними німецькими підписами полів → JSON-чернетка для перевірки.
Працює на CPU без зовнішнього OCR API.
GMed підключає сервіс через серверний proxy; сам parser не створює інвойси й не проводить платежі.

## Перевірка інвойсу в GMed

На сторінці інвойсів кнопка імпорту відкриває модалку: оригінал ліворуч,
редаговані реквізити, клієнт і його замовлення праворуч. Після ручного
підтвердження зберігаються фінансовий документ і зовнішній інвойс із
`source_document_id`. Оригінал можна відкрити з рахунку в замовленні.
Потрібна міграція `20260905153000_external_invoice_source_document.sql`.

Після парсингу GMed шукає клієнта серед доступних у модалці: за точним ID
або повним ім'ям у блоці пацієнта/одержувача. Єдиний збіг підставляється
автоматично; однакові імена чи суперечливі дані залишаються для ручного вибору.
Вибраний вручну клієнт не перезаписується результатом OCR. Замовлення й
остаточне підтвердження прив'язки залишаються за користувачем.

Для Rust API задайте `INVOICE_PARSER_URL` (base URL без `/v1/parse`) та
`INVOICE_PARSER_API_KEY` із тим самим значенням, що в parser. Ключ залишається
на сервері. Якщо parser не налаштований, модалка дозволяє ручне заповнення.
Без відповідного шаблону працює обережний розбір німецьких підписів номера,
дат і сум. Постачальник визначається лише за однозначною юридичною назвою
в шапці. Непідтримувані та суперечливі значення залишаються порожніми.
Завантаження оригіналу і створення інвойсу — два запити: після помилки другого
повторна спроба в тій самій модалці використовує вже збережений документ.
Якщо закрити модалку після такої помилки, документ залишиться у клієнта.

## Вибір готових компонентів

### Структуровані електронні інвойси

Модалка приймає UTF-8 XML UBL Invoice/CreditNote та UN/CEFACT CII
(простори імен версії 100), зокрема приклади XRechnung. Для PDF з XML-вкладенням
на зразок ZUGFeRD/Factur-X структуровані значення мають пріоритет над OCR.
Реквізити видимого тексту PDF порівнюються з XML, розбіжності показуються
поруч із полями. Якщо порівняння неповне, потрібна ручна перевірка оригіналу.
Кілька різних XML або нечитабельне вкладення дають попередження і повернення
до розбору видимого PDF. Це не перевірка PDF/A чи повної сумісності всіх профілів.

`structured.validation=basic_checks` означає перевірку просторів імен,
неоднозначності полів, дат, валют і узгодженості сум; XSD/Schematron-валідатор
KoSIT не підключений. Зберігати можна звичайний інвойс типу 380 з невід'ємними
загальними сумами після перевірки людиною; інші типи доступні для перегляду.
`payment.amount_due` відокремлений від `amount_gross`, передоплата й округлення
видимі окремо. Запис про оплату автоматично не створюється. Податкові категорії
та рядки показуються для перевірки, але ще не переносяться в бухгалтерські проводки.

Для XML клієнт підбирається лише за повним ім'ям одержувача; номери покупця,
інвойсу чи замовлення з XML не є ID пацієнта GMed. Оригінал відображається
екранованим текстом React. Перед збереженням бекенд повторно перевіряє саме
отримані байти через parser і зберігає оригінал як `application/octet-stream`.
Це вузький виняток для фінансового імпорту; загальна заборона активного XML/HTML
для завантажень не змінена. XML без успішної перевірки не зберігається.

Ліміти XML: 5 МіБ, глибина 64, 25 000 вузлів, 500 позицій; DTD, зовнішні
сутності й processing instructions заборонені. PDF-вкладення не розпаковуються
на диск, декомпресія XML обмежена до читання. Сервіс не відкриває посилання з XML.
Тести містять офіційні синтетичні [приклади KoSIT](tests/fixtures/README.md)
UBL/CII та штучні PDF із вкладеннями, без приватних документів користувача.

Перевірено 2026-09-05:

| Компонент | Роль | Рішення для GMed |
| --- | --- | --- |
| [invoice2data](https://github.com/invoice-x/invoice2data), MIT | Поля й позиції за YAML/JSON-шаблонами постачальників | Встановлюємо `invoice2data==1.0.1`; викликаємо його текстовий parser |
| [Tesseract](https://github.com/tesseract-ocr/tesseract), Apache-2.0 | Локальне OCR зображень | Перший CPU-образ, мови DE/EN/UA/RU |
| [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR), Apache-2.0 | Альтернативний OCR і аналіз структури | Уже використовується в clinical parser; порівняти на реальних інвойсах перед додаванням сюди |
| [Docling](https://github.com/docling-project/docling) | Розбір структури PDF і таблиць | Кандидат для складних таблиць; у цей сервіс не включений |

OCR читає текст, а invoice2data знаходить у ньому поля за правилами конкретного
макета. Це не універсальна модель, яка гарантовано розуміє довільний рахунок.
Поточна версія використовує модуль `app.extraction` із
`services/clinical-document-parser`: нативний текст PDF зберігається, слабкі
сторінки переходять до OCR. Docker копіює лише модулі extraction/paddle_runtime/lab_grid
та службовий `__init__`, без клінічних правил і доступу до БД. OCR-рушій цього
сервісу зафіксований на Tesseract, без завантаження моделей під час запиту.

## Запуск Docker

На DEV сервіс також включений у `docker-compose.dev-hetzner.yml`. Скрипт
`scripts/deploy-dev-current.sh` генерує відсутній `GMED_INVOICE_PARSER_API_KEY`
у серверному `release.env`, збирає контейнер і з'єднує його з бекендом
через внутрішню мережу без публічного порту. Бекенд отримує адресу
`http://invoice-parser:8091`; інтерфейс викликає авторизований
`POST /api/v1/invoices/import-preview`.

З кореня репозиторію, PowerShell:

```powershell
$env:INVOICE_PARSER_API_KEY = '<випадковий секрет щонайменше 32 символи>'
docker compose -f services/invoice-parser/compose.yml up --build -d
```

API: `http://127.0.0.1:8091`; інтерактивна документація: `/docs`.
`GET /health` перевіряє лише роботу API. Це не перевірка якості OCR чи наявності
шаблону для певного постачальника. Контейнер працює від непривілейованого
користувача, з файловою системою тільки для читання, тимчасовим `/tmp`,
внутрішньою мережею без виходу в інтернет та портом лише на localhost.
Завантаження залежностей потрібне під час збірки образу.

У `templates/` треба додати перевірені шаблони реальних постачальників.
Шаблони `examples/templates/` призначені **тільки для синтетичних прикладів**;
вони не підключені за замовчуванням. Без відповідного шаблону API повертає
текст і `template_not_found`, а для підтримуваних німецьких підписів також
повертає реквізити з `generic_extraction_review_required`. Це обмежений
розбір підписів, а не універсальна модель довільних інвойсів.

Якщо нетто не підписано, але вказані підсумок, ПДВ та єдина валюта, нетто
обчислюється відніманням із попередженням `amount_net_derived_from_totals`.
Reverse Charge позначається `tax_treatment_requires_review`: податковий
режим не визначається. Самої згадки Reverse Charge недостатньо для ПДВ 0.
Якщо документ прямо каже, що **цей рахунок виставлено без ПДВ**, відсутній
ПДВ рахунку заповнюється як 0, а нетто — як підсумок, тільки за відсутності
суперечливих сум. `field_sources` зберігає цитату і метод
`document_without_vat`; це не визначає податкові зобов'язання одержувача.

Умови на зразок «Zahlbar innert 30 Tagen» дають пропозицію строку від дати
інвойсу з `due_date_calculated_from_invoice_date`; UI явно показує, від якої
дати виконано розрахунок. Умови від отримання/доставки, робочі дні, сконто
та суперечливі строки не перераховуються. Явна дата має пріоритет.
Дата Lastschrift повертається окремо як `payment.collection_date`, не `due_date`.

Типові таблиці з кількістю/ціною, `Pos.` з перенесеними описами та
нумеровані послуги з ПДВ розбираються без шаблону. Позиції містять назву,
суму, сторінку й доступні кількість, ціну, ставку ПДВ, період. Знижки
залишаються від'ємними, підсумкові рядки не дублюються як позиції.
`line_items_total_mismatch` повідомляє, якщо сума позицій не збігається
з нетто або підсумком рахунку. Позиції не перезаписують загальні суми.
Явні `Leistungszeitraum` / `Berechnungszeitraum` зберігаються як період послуг;
дати не виводяться з назви або кількості. Короткий суфікс назви на наступному
рядку зберігається. Назва постачальника не включає службове `Leistungen der`.

```powershell
curl.exe http://127.0.0.1:8091/v1/parse `
  -H "Authorization: Bearer $env:INVOICE_PARSER_API_KEY" `
  -H 'Content-Type: application/pdf' `
  --data-binary '@invoice.pdf'
```

Передається тіло файлу, не multipart, шлях чи URL. Для фото використовуйте
`image/png` або `image/jpeg`, для XML — `application/xml` чи `text/xml`.
TIFF, HEIC, DOCX та довільні текстові файли цей HTTP endpoint не приймає.
Не записуйте відповідь із реквізитами в загальні логи.

## Контракт відповіді

```json
{
  "schema_version": "1.0",
  "status": "needs_review",
  "requires_review": true,
  "template": "synthetic-clinic-en.yml",
  "fields": {
    "supplier_name": "GMED Synthetic Clinic",
    "external_invoice_number": "DEMO-2026-001",
    "invoice_date": "2026-09-05",
    "due_date": "2026-09-19",
    "amount_net": "100.00",
    "amount_vat": "19.00",
    "amount_gross": "119.00",
    "currency": "EUR"
  },
  "line_items": [{"name": "Consultation", "qty": "1", "price_subtotal": "100.00"}],
  "missing_fields": [],
  "warnings": [],
  "extraction_complete": true
}
```

Повна відповідь також містить `text` та `extraction`: джерело тексту кожної
сторінки, OCR-рушій, confidence і геометрію OCR-блоків. Confidence стосується
розпізнавання тексту, а не ймовірності правильності фінансових реквізитів.
`supplier_name` походить із конфігурації єдиного відповідного шаблону або
однозначної юридичної назви в шапці німецького інвойсу;
це не перевірена відповідність запису постачальника у GMed.

Суми заголовка передаються десятковими рядками. Відсутні або неоднозначні поля
мають `null`. Дати приймаються за явними форматами шаблону або німецькими
підписами з повною датою (включно з назвою місяця), валюта
не підставляється автоматично. Два відповідні шаблони дають
`ambiguous_template`; жоден не обирається довільно. Розбіжність
`net + VAT ≠ gross` понад 0.01 дає `totals_mismatch`. Відсутність попереджень
не скасовує обов'язкову перевірку людиною.

Позиції зберігають поля текстового lines parser invoice2data (наприклад,
`name`, `qty`, `price_subtotal`). Їхні локалізовані значення ще не нормалізуються
в модель рядків GMed; перевірка суми позицій і ставок ПДВ потребує правил
відповідного постачальника. Сервіс не визначає paid status, provider_id,
patient_id чи order_id і не трактує реквізити банку як платіжну інструкцію.

## Шаблони

Використовуйте `examples/templates/` як перевірені приклади формату.
Потрібні явний `issuer`, достатньо специфічні `keywords`, `fields` та
`options.decimal_separator` / `options.date_formats`.
У версії 1.0.1 keywords перевіряються як підрядки підготовленого тексту.

Для полів заголовка використовуйте `parser: regex` без `type`: адаптер сам
перетворює гроші через Decimal та суворо перевіряє дати. Мапа:

| Поле шаблону | Поле чернетки GMed |
| --- | --- |
| invoice_number | external_invoice_number |
| date | invoice_date |
| due_date | due_date |
| amount_untaxed | amount_net |
| amount_tax | amount_vat |
| amount | amount_gross |

`currency` має захоплювати явний трилітерний код; `options.currency`
допустиме лише для перевіреного шаблону з фіксованою валютою.
Бібліотечні шаблони не завантажуються автоматично: їх можна адаптувати, але
спочатку перевірити required fields, валюти, формати дат, десяткові роздільники
та помилкові збіги з іншими постачальниками. Рекурсивні папки дозволені;
імена файлів шаблонів мають бути унікальними. Шаблони перечитуються на кожен
документ. API не приймає шаблони від клієнта. PDF area readers, Camelot і
path-based plugins відключені; для позицій доступний `fields.lines`.

## Ліміти

| Налаштування | За замовчуванням |
| --- | --- |
| INVOICE_PARSER_MAX_FILE_BYTES | 25 MiB |
| INVOICE_PARSER_MAX_CONCURRENCY | 2, допустимо 1–4 на один процес API |
| INVOICE_PARSER_TIMEOUT_SECONDS | 180 секунд, включно із завантаженням тіла |
| INVOICE_PARSER_TEMPLATE_DIR | `templates` локально, `/app/templates` у Docker |
| PARSER_MAX_PDF_PAGES | 20 |
| PARSER_MAX_IMAGE_PIXELS | 25 мільйонів |
| PARSER_MAX_EXTRACTED_TEXT_CHARS | 200 тисяч |

Понад 500 позицій список обрізається з явним попередженням. JSON обмежено
4 MiB. Кожен документ обробляється окремим дочірнім процесом; timeout
завершує дерево процесів, включно з Tesseract. Сервіс не має постійного сховища
або черги завдань. Завантажені файли тримаються в пам'яті, тимчасові файли
Tesseract — у `/tmp`. stdout/stderr бібліотек не потрапляють в access/error logs.

HTTP-коди: `400` порожній файл/неправильний запит; `401` неправильний секрет;
`413` перевищення розміру; `415` формат або сигнатура; `422` помилка розбору;
`429` зайняті всі слоти; `504` timeout. Тримайте `--workers 1`; кілька процесів
API множать ліміт паралельності. Для наступного масштабу потрібна черга
у GMed та повторні спроби з обмеженням кількості й затримкою.

## Локальні тести

Python 3.12+, Tesseract та мовні пакети мають бути встановлені окремо.
З кореня репозиторію:

```powershell
python -m venv services/invoice-parser/.venv
$python = 'services/invoice-parser/.venv/Scripts/python.exe'
& $python -m pip install -e 'services/invoice-parser[dev]'
$env:PYTHONPATH = "$PWD/services/clinical-document-parser"
& $python -m pytest -q -c services/invoice-parser/pyproject.toml services/invoice-parser/tests
$env:INVOICE_PARSER_TEMPLATE_DIR = "$PWD/services/invoice-parser/examples/templates"
$env:INVOICE_PARSER_API_KEY = '<випадковий секрет щонайменше 32 символи>'
& $python -m uvicorn invoice_parser.api:app --host 127.0.0.1 --port 8091 --no-access-log
```

За потреби додайте Tesseract до PATH. Для інсталяції лише з англійськими
даними встановіть `PARSER_OCR_PRIMARY_LANGUAGES=eng` та інші
`PARSER_OCR_*_LANGUAGES=eng` для локальної діагностики. Тести роблять це самі.

CI у `.github/workflows/invoice-parser.yml` тестує API, реальний OCR
синтетичного PNG, нативний PDF, суми, дати, невідомі макети, ліміти й timeout;
далі збирає Docker та перевіряє OCR у його образі без мережі.

Локальна перевірка 2026-09-05: **37 тестів пройшли**, включно з реальним
Tesseract OCR синтетичного PNG, нативним PDF через API та завершенням
завислого процесу разом із дочірнім процесом на Windows. Docker на цій
машині недоступний, тому збірку й запуск контейнера локально ще не перевірено.

## Подальша роль OCR у GMed ↔ DATEV

Спочатку визначити продукти/API DATEV та формати двостороннього обміну за
[планом інтеграції](../../docs/architecture/datev-invoice-integration_ua.md).
Наведені нижче кроки стосуються лише тієї частини потоку, для якої
структуровані дані недоступні. Розширення шаблонів не є обов'язковим:
для невідомих макетів доступний обмежений розбір німецьких підписів.
Складні таблиці, кредит-ноти та довільні мовні макети потребують подальшої
перевірки й розширення.

1. Зібрати знеособлений тестовий набір реальних макетів інвойсів постачальників,
   включно зі сканами, фото, багатосторінковими рахунками й кредит-нотами.
2. Додати шаблони та перевірити точний збіг номера, дат, валюти, net/VAT/gross,
   позицій і хибні збіги між постачальниками. Поточні синтетичні тести не
   доводять точність на цьому наборі.
3. У Rust API додати авторизований запуск імпорту існуючого документа,
   зберігання чернетки/статусу, SHA-256 оригіналу й аудит. Секрет сервісу
   залишається на бекенді. Перевіряти прив'язку документа до пацієнта/замовлення.
4. У формі зовнішнього інвойсу показати оригінал, поля й попередження поруч;
   після перевірки використати чинний create-external-invoice flow. Перевірку
   дубля робити за постачальником + номером та окремо хешем документа.
5. Після замірів CPU/пам'яті/часу на наборі вирішити, чи потрібні PaddleOCR,
   Docling або модель для складних таблиць. XML/e-invoice формати потребують
   окремого структурованого імпорту перед OCR; у цьому MVP його немає.

Окремий Compose-файл призначений для підготовки та перевірки сервісу.
Production Compose, маршрути Rust і фінансовий інтерфейс цим додаванням
не змінюються. Публікація образу, розгортання та перевірка на реальних
інвойсах ще не виконані.
